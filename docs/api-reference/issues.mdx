Issues are crew-scoped tracker items: each carries a human-readable identifier (e.g. `ENG-42`), a status flow, and lifecycle operations for agent execution. Beyond CRUD, the API covers comments, relations, an activity log, workspace labels, and projects that group issues with tracking metadata. Under the hood, issues are stored in the `missions` table with `mission_type = 'issue'` -- they share infrastructure with missions but keep their own status flow, identifiers, and lifecycle.

<Note>
  All issue endpoints require authentication and workspace context.
</Note>

## Issues CRUD

Create, read, update, and delete issues. Most write operations require `OWNER`, `ADMIN`, or `MANAGER` role and emit a WebSocket event on `workspace:{workspaceId}`.

### List Issues (Workspace)

```
GET /api/v1/issues?workspace_id={workspaceId}
```

Returns issues across the workspace with filtering, sorting, and pagination.

**Query Parameters:**

| Parameter | Type | Default | Description |
|---|---|---|---|
| `workspace_id` | string | Required | Workspace ID |
| `mission_type` | string | `"issue"` | Filter by type (`"issue"` or `"mission"`) |
| `status` | string | -- | Comma-separated status filter (e.g., `TODO,IN_PROGRESS`) |
| `priority` | string | -- | Comma-separated priority filter (e.g., `urgent,high`) |
| `project_id` | string | -- | Filter by project |
| `crew_id` | string | -- | Filter by crew |
| `assignee_id` | string | -- | Filter by assignee |
| `label` | string | -- | Filter by label name |
| `q` | string | -- | Search in title or identifier (LIKE match), on the server |
| `search` | string | -- | Older alias of `q` |
| `sort` | string | `"created_at"` | Sort column: `created_at`, `updated_at`, `priority`, `sort_order` |
| `limit` | integer | `50` | Rows per page (1-500) |
| `offset` | integer | `0` | Pagination offset |

The body stays a bare array. The total the filter matched — before `limit`/`offset` — is in the `X-Total-Count` response header, with `X-Limit` and `X-Offset` echoing the values applied. An agent assignee carries `assignee_slug` next to `assignee_name`.

<Note>
  **Pagination (#2286):** the body is still the bare array above -- unchanged
  for every existing client -- but the response now also carries two headers:

  | Header | Description |
  |---|---|
  | `X-Total-Count` | Total rows matching the query (every filter applied, `limit`/`offset` ignored) |
  | `X-Has-More` | `"true"` when `offset + len(body)` is less than `X-Total-Count`, else `"false"` |

  A caller that only reads the array still gets identical bytes; a caller
  that wants to know whether a 100-row page was the whole story reads the
  headers instead of guessing. `crewship issue list` prints a "Showing N of
  TOTAL issues" footer from them and takes `--offset` to page further; the
  issues board (`hooks/use-issues-list.ts`) uses them to drive its own
  "Load more".
</Note>

<Note>
  **Error degradation contract (#2285):** the issues board classifies a
  failed request to this endpoint instead of rendering it as an empty
  workspace. A `403` is shown separately from a `5xx`/network failure -- it's
  reported as "the request was refused", naming a scoped agent/CLI token as
  the likely cause (`AuthKindCLIToken` in `internal/api/middleware.go` is the
  credential "an agent, CI job, or script holds"; a `403` here is what an
  agent/CLI token whose scope doesn't cover issues, or a transient token
  problem, looks like) alongside a retry action, rather than presenting a
  board with zero issues. See `hooks/use-issues-list.ts` for the
  implementation and the full reasoning.
</Note>

### Create Issue

```
POST /api/v1/crews/{crewId}/issues?workspace_id={workspaceId}
```

**Auth:** `OWNER`, `ADMIN`, or `MANAGER` role

The crew must have a LEAD agent. The issue identifier is auto-generated from the crew's `issue_prefix` (or first 3 characters of the slug) and an auto-incrementing counter.

**Request Body:**

| Field | Type | Required | Default | Description |
|---|---|---|---|---|
| `title` | string | Yes | -- | Issue title |
| `description` | string | No | `null` | Issue description |
| `priority` | string | No | `"none"` | Priority: `none`, `low`, `medium`, `high`, `urgent` |
| `assignee_type` | string | No | `null` | `"user"` or `"agent"` |
| `assignee_id` | string | No | `null` | Assignee ID |
| `due_date` | string | No | `null` | Due date (YYYY-MM-DD) |
| `project_id` | string | No | `null` | Parent project ID |
| `estimate` | integer | No | `null` | Effort/points estimate |
| `parent_issue_id` | string | No | `null` | Parent issue ID for sub-issues (validated against current workspace) |
| `milestone_id` | string | No | `null` | Associated milestone ID |
| `labels` | string[] | No | `[]` | Array of label IDs to attach |
| `routine_id` | string | No | `null` | Pipeline ID to bind for `/run-routine` (must exist in workspace) |
| `routine_inputs` | object | No | `{}` | JSON object of routine input values; rejected with 400 if set without `routine_id` |

```json
{
  "title": "Fix authentication token refresh",
  "description": "Tokens are not being refreshed before expiry",
  "priority": "high",
  "assignee_type": "agent",
  "assignee_id": "agent_789",
  "labels": ["label_bug"]
}
```

**Response:** `201 Created` -- issue object with generated `number` and `identifier`.

| Status | Condition |
|---|---|
| `400` | Missing title, crew has no lead agent, `routine_inputs` set without `routine_id`, `routine_id`/`parent_issue_id` not in workspace, or `routine_inputs` not valid JSON |
| `403` | Insufficient role |
| `404` | Crew not found |

**WebSocket event:** `issue.created` on `workspace:{workspaceId}`

### Update Issue

```
PATCH /api/v1/crews/{crewId}/issues/{identifier}?workspace_id={workspaceId}
```

**Auth:** `OWNER`, `ADMIN`, or `MANAGER` role

**Request Body:** All fields optional.

| Field | Type | Description |
|---|---|---|
| `title` | string | Issue title |
| `description` | string | Issue description |
| `status` | string | New status (must be valid transition) |
| `priority` | string | Priority level |
| `assignee_type` | string | `"user"` or `"agent"` |
| `assignee_id` | string | Assignee ID |
| `due_date` | string | Due date |
| `project_id` | string | Project ID (empty string to unlink) |
| `estimate` | integer \| null | Effort/points estimate; **`null` clears it**, a non-number is a `400` |
| `parent_issue_id` | string | Parent issue ID; empty string unlinks; cannot equal the issue itself |
| `milestone_id` | string | Milestone ID; empty string unlinks |
| `sort_order` | number | Manual sort order |
| `labels` | string[] | Replace all labels with this set of label IDs |
| `routine_id` | string | Pipeline ID to bind; empty string clears binding (also resets `routine_inputs`) |
| `routine_inputs` | object | Full-replacement JSON object for routine inputs |

**Status Transitions:**

| From | Allowed To |
|---|---|
| `BACKLOG` | `TODO`, `IN_PROGRESS`, `CANCELLED`, `DUPLICATE` |
| `TODO` | `IN_PROGRESS`, `BACKLOG`, `CANCELLED`, `DUPLICATE` |
| `IN_PROGRESS` | `REVIEW`, `DONE`, `FAILED`, `CANCELLED`, `TODO`, `DUPLICATE` |
| `REVIEW` | `DONE`, `TODO`, `IN_PROGRESS`, `FAILED`, `CANCELLED`, `DUPLICATE` |
| `DONE` | `BACKLOG` |
| `FAILED` | `BACKLOG`, `TODO`, `IN_PROGRESS` |
| `CANCELLED` | `BACKLOG`, `TODO` |
| `DUPLICATE` | *(none -- terminal)* |

When status changes to `DONE`, `CANCELLED`, or `DUPLICATE`, `completed_at` is automatically set.

Significant changes (status, assignee, priority) are logged as activity entries.

**Response:** `200 OK` -- updated issue object.

| Status | Condition |
|---|---|
| `400` | Invalid status transition, no fields to update, `parent_issue_id` equals issue itself, `parent_issue_id`/`routine_id` not in workspace, or `routine_inputs` not valid JSON |
| `404` | Issue not found |

**WebSocket event:** `issue.updated` on `workspace:{workspaceId}`

## Lifecycle Actions

Drive an issue through agent execution: start, stop, and review.

### Start Issue

```
POST /api/v1/crews/{crewId}/issues/{identifier}/start?workspace_id={workspaceId}
```

Starts execution of a `BACKLOG` or `TODO` issue. The issue must have an agent
**delegate** — `delegate_agent_id` (or an assignee resolved from the legacy
`assignee_type='agent'` pair), naming a live, non-held agent. A human
**owner** with no delegate is not enough (F62: existence of *any* assignee
used to be sufficient; it is not anymore — the delegate must specifically be
an executable agent). This:

1. Creates a synthetic chat session for the mission
2. Creates or resets tasks (resets existing tasks to PENDING for re-runs)
3. Transitions status to `IN_PROGRESS`
4. Starts the MissionEngine asynchronously

**Auth:** `OWNER`, `ADMIN`, or `MANAGER` role

**Response:** `200 OK`

```json
{
  "status": "IN_PROGRESS",
  "identifier": "ENG-42"
}
```

| Status | Condition |
|---|---|
| `400` | Issue not in BACKLOG/TODO; or no agent delegate (`"Issue must have an agent delegate before starting"`); or the delegate is not an executable agent — soft-deleted or `PENDING_REVIEW` (`"Issue delegate is not an executable agent"`) |
| `404` | Issue not found |
| `409` | Issue was already started by another request |

**WebSocket event:** `issue.started` on `workspace:{workspaceId}`

### Stop Issue

```
POST /api/v1/crews/{crewId}/issues/{identifier}/stop?workspace_id={workspaceId}
```

<Warning>
  Stops an issue cooperatively, not instantly. When the issue is
  `IN_PROGRESS` or `REVIEW`, this happens in one transaction: every
  `PENDING`/`IN_PROGRESS`/`BLOCKED` mission task is marked `CANCELLED`,
  every assignment for the issue that has not reached a terminal state —
  running, pending, or still queued behind a busy agent or the crew budget —
  gets `cancel_requested_at` stamped,
  and the issue itself moves to `CANCELLED`. There is no container kill —
  a run already executing when Stop is called keeps running. An
  assignment that hasn't started its exec yet sees the stamp first and
  never starts. One already mid-exec finishes that exec, and only then
  is recorded — as `CANCELLED`, never `COMPLETED` or `FAILED`, even if it
  reports success or a late failure after Stop was called; the stamp
  always wins. No further step is scheduled for the issue. A future hard
  kill (interrupting a run mid-exec) is a separate, not-yet-built
  capability.

  An [`@mention`](/guides/issue-mentions) can dispatch a run on an issue
  that was never started (`BACKLOG`/`TODO`) — that run is attributed to
  the issue the same way a mission-task run is. Stop reaches it too: when
  the issue is not `IN_PROGRESS`/`REVIEW` but has at least one live
  attributed assignment, Stop stamps `cancel_requested_at` on it and
  leaves the issue's own status unchanged (it does not move the issue to
  `IN_PROGRESS` or `CANCELLED`). Stop only refuses with `400` when the
  issue is neither `IN_PROGRESS`/`REVIEW` nor has any live attributed run.
</Warning>

**Request:** `crewId` and `identifier` are required path parameters; `workspace_id` selects the workspace. No request body.

**Auth:** `OWNER`, `ADMIN`, or `MANAGER` role

**Response:** `200 OK`

```json
{
  "status": "CANCELLED",
  "identifier": "ENG-42",
  "runs_stopped": 1
}
```

`status` is `CANCELLED` when the issue was `IN_PROGRESS`/`REVIEW`; otherwise
it echoes the issue's unchanged status (e.g. `BACKLOG`) for the
mention-dispatched-run case above. `runs_stopped` is the number of
assignment rows stamped.

| Status | Condition |
|---|---|
| `400` | Issue not in IN_PROGRESS or REVIEW status, and no live run is attributed to it |
| `404` | Issue not found |

### Review Issue

```
POST /api/v1/crews/{crewId}/issues/{identifier}/review?workspace_id={workspaceId}
```

Submit a review decision for an issue in `REVIEW` or `IN_PROGRESS` status.

**Auth:** `OWNER`, `ADMIN`, or `MANAGER` role

**Request Body:**

| Field | Type | Required | Description |
|---|---|---|---|
| `action` | string | Yes | `"approve"` or `"request_changes"` |
| `comment` | string | No | Review comment |
| `reassign_to` | string | No | Agent slug to reassign to (for `request_changes`) |

```json
{
  "action": "request_changes",
  "comment": "The error handling needs improvement",
  "reassign_to": "backend-dev"
}
```

- **`approve`**: Transitions issue to `DONE`, adds approval comment and activity
- **`request_changes`**: Transitions issue to `TODO`, optionally reassigns, adds comment and activity

**Response:** `200 OK`

```json
{
  "status": "ok",
  "action": "request_changes"
}
```

| Status | Condition |
|---|---|
| `400` | Invalid action, or issue not in reviewable status |
| `404` | Issue not found |

## Bulk

Apply one set of field updates across many issues from the board/list multi-select toolbar.

### Bulk Update

```
PATCH /api/v1/issues/bulk
```

Apply a single set of field updates to up to 100 issues at once. Used by the board/list views' multi-select toolbar. Each issue is processed in its own statement -- partial success is possible: a request touching 50 ids where 3 have invalid status transitions returns `{"updated": 47}` rather than rolling back.

**Auth:** `OWNER`, `ADMIN`, or `MANAGER` role (`create` permission).

**Request Body:**

| Field | Type | Required | Description |
|---|---|---|---|
| `ids` | string[] | Yes | 1-100 mission ids. Ids outside the caller's workspace are skipped silently. |
| `updates.status` | string | No | New status. Invalid transitions are skipped per-issue (not 400). When `DONE`, `CANCELLED`, or `DUPLICATE`, `completed_at` is set automatically. |
| `updates.priority` | string | No | Priority level. |
| `updates.assignee_type` | string | No | `"user"` or `"agent"`. |
| `updates.assignee_id` | string | No | Assignee id. |
| `updates.project_id` | string | No | Project id; empty string unlinks. |
| `updates.labels` | string[] | No | Replace **all** labels on each issue with this set of label ids. |

```json
{
  "ids": ["issue_abc", "issue_def", "issue_ghi"],
  "updates": {
    "status": "TODO",
    "priority": "high",
    "labels": ["label_bug", "label_blocker"]
  }
}
```

**Response:** `200 OK`

```json
{ "updated": 3 }
```

| Field | Type | Description |
|---|---|---|
| `updated` | integer | Count of issues that successfully applied **at least one** field. Issues whose `updates` resolved to a no-op are excluded. |

| Status | Condition |
|---|---|

## Outcome

<Note>Work package B6 of the Issues & Routines architecture (`docs/prd/PRD-ISSUES-AND-ROUTINES-2026.md` §9.6). `status` (above), `outcome` and `runverdict` answer three different questions and are easy to conflate — see `docs/guides/routines.mdx`'s "Status, outcome and verdict" section for the full comparison.</Note>

Every finished run — an issue-session assignment or a routine (`pipeline_runs`) run — carries an `outcome`, the deterministic routing decision the runner reports, distinct from its technical `status`:

| Outcome | Meaning | §9.6's intended routing |
|---|---|---|
| `NO_CHANGE` | Ran, nothing to do | History only |
| `SUCCEEDED` | Did the work, nothing further needed | History |
| `WORK_CREATED` | Produced or updated an issue | History (+ an issue comment, once wired — see note) |
| `PARTIAL` | Some done, some failed, no human needed yet | History (+ an issue comment, once wired — see note) |
| `NEEDS_HUMAN` | Blocked on a decision, missing input, or a credential | **Inbox** (`run_needs_human`), with an action contract — see below |
| `FAILED` | The run failed, or reported no outcome at all | Inbox once retries are exhausted (not yet wired — no retry counting exists) |
| `CANCELLED` | Stopped by a human (Tier 1 stop) or superseded | History |

<Note>
**What this table describes vs. what is wired today.** `NEEDS_HUMAN`'s inbox
routing and the session-state transition below are real, outcome-driven
effects — this PR (B6) added them. The "+ an issue comment" cells for
`WORK_CREATED`/`PARTIAL` are §9.6's stated *intent*, not yet a real,
outcome-gated effect: an issue-session assignment already gets a mission
comment posted on completion (`finishAssignment`), but that path predates
`outcome` and fires for ANY non-empty, non-error result — a `SUCCEEDED` or
`NO_CHANGE` run with output gets one too, and a routine (`pipeline_runs`)
run gets no issue comment at all regardless of outcome, since no
comment-posting path exists for that run shape yet. Gating the comment on
`outcome` specifically (and adding one for routine runs) is a follow-up, not
part of this PR.
</Note>

`outcome` is parsed from the agent's existing structured hand-off — the `---CHECKPOINT---` block a session-bearing run is instructed to emit (§11.3), or the `---HANDOFF---` block a mission-task run emits — never a second, invented block. **A run that ends cleanly (no execution error) but reports no recognised outcome is recorded `FAILED`, with `error_message` set to `"no outcome reported"`** — an absent outcome is treated as a bug, not a silent success. A run stopped by Stop (Tier 1 cooperative cancellation) or superseded always gets `CANCELLED`, regardless of what its own hand-off said.

`NEEDS_HUMAN` is the only outcome that creates an inbox item — exactly one, keyed on the run id, so a retried terminal write can never double it. The item's `payload_json` carries a §12 action contract:

```json
{
  "attention_class": "input",
  "thread_key": "run:asg_abc",
  "who_can_act": ["user:usr_123"],
  "actions": [
    {"id": "take_over", "label": "Take over", "effect": "Opens the issue for you to continue", "irreversible": false}
  ],
  "context": {"issue": "ENG-42", "run": "asg_abc"}
}
```

For a session-bearing assignment, `NEEDS_HUMAN` also moves the issue's session to `awaiting_input` (see Sessions, below) — the transition that needed this column to exist before it could be reached at all.

## Sessions

<Note>Session lifecycle: `issue_agent_sessions` is work package B1 (event log + session foundations) of the Issues & Routines architecture (`docs/prd/PRD-ISSUES-AND-ROUTINES-2026.md`), extended by B3 (#2339, the run-admission guarantee: at most one `assignments` row may be `PENDING`/`QUEUED`/`RUNNING` for a given session at a time, a partial unique index rather than a read-then-write check), B4 (#2343) and B6 (#2349, the `outcome` contract): `state` genuinely moves with its runs — `pending → active` when a run wins the admission CAS, then, once that run settles, resolved through its `outcome` — `active → idle` for `NO_CHANGE`/`SUCCEEDED`/`WORK_CREATED`/`PARTIAL`/`CANCELLED`, `active → error` for `FAILED`, and `active → awaiting_input` for `NEEDS_HUMAN` (the transition B4 could not reach until `outcome` existed) — with `active_run_id` populated for as long as a run is live, cleared once it settles. What is still NOT wired: the 14-day `idle → stale` sweep. An ephemeral agent that expires mid-session is reconciled onto `error` (was active) or `closed` (otherwise) rather than left rendered `active` over a ghost.</Note>

The durable, per-(issue, agent) cursor a mention resolves or creates. `UNIQUE(mission_id, agent_id)` on the underlying table means mentioning the same agent on the same issue twice never creates a second session — the second mention finds and reuses the first's row. `UNIQUE` on `assignments.session_id` (partial, live statuses only) means a session backs at most one live run: a mention that lands while the session's run is already going does not start a second one — its delivery is left unclaimed and is folded into exactly one new run once the live one finishes, rather than being marked seen by a run that never read it. See `docs/guides/issue-mentions.mdx`'s "Known limits in 1.0" for the full account.

| `502` | `credential-rejected` | Provider returned 401 — token revoked or expired |
| `502` | `credential-forbidden` | Token valid but lacks repository read access |
| `502` | `provider-unavailable` | Provider returned 5xx or did not answer |
| `502` | `cross-host-redirect` | The provider redirected off its own host; not followed, because the request carries a credential |

## Attachments

Attach files to an issue — a crash log, a screenshot, a repro bundle, a diff.
Everything an agent working the issue needs to see and, before this surface
existed, had to be pasted into a comment.

Three properties are worth knowing before you use it:

- **The type is decided by the file's extension, against an allowlist.** The
  request's own `Content-Type` is discarded. That header is chosen by whoever is
  uploading, and honouring it is how a stored file becomes stored XSS served from
  your own origin. Allowed today: `.txt` `.log` `.md` `.csv` `.tsv` `.json`
  `.yaml` `.yml` `.toml` `.xml` `.diff` `.patch` `.png` `.jpg` `.jpeg` `.gif`
  `.webp` `.avif` `.pdf` `.zip` `.gz` `.tgz`. `.html`, `.svg` and anything
  executable are absent deliberately, not by oversight.
- **Files are stored by content.** Two issues carrying identical bytes share one
  stored copy, and attaching the same file to the same issue twice is the same
  attachment — the second call returns `200` with the existing record rather than
  `201` or `409`, so a retry is safe. "The same file" means the same bytes *under
  the same name*: `crash-before-fix.log` and `crash-after-fix.log` can be
  byte-identical and mean opposite things, so both are attached and both get
  `201`, sharing one stored copy.
- **The uploaded filename is a label, never a path.** The stored location is
  derived entirely from the SHA-256 digest, so a filename of
  `../../../etc/passwd` is recorded as `passwd` and the bytes land where every
  other attachment's do.

Agents reach the same files through the sidecar — see
[Attachments an agent can read](/guides/issue-attachments#what-an-agent-sees).

### List attachments

```
GET /api/v1/crews/{crewId}/issues/{identifier}/attachments?workspace_id={workspaceId}
```

**Auth:** any workspace member (session or CLI token). The workspace is taken
from the authenticated session, so an issue in another workspace is a `404`.

**Request:** `workspace_id` is the required workspace query parameter. No request
body.

**Response:** `200 OK` — newest first.

```json
[
  {
    "id": "cmsf1a2b30001d5e6aa11",
    "workspace_id": "ws_abc",
    "owner_type": "issue",
    "owner_id": "issue_123",
    "filename": "crash.log",
    "content_type": "text/plain; charset=utf-8",
    "size_bytes": 20481,
    "sha256": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08",
    "uploaded_by_user_id": "user_1",
    "uploaded_by_agent_id": null,
    "uploaded_by_name": "Ada Lovelace",
    "created_at": "2026-08-06T19:22:41Z"
  }
]
```

`sha256` is part of the contract: it lets a client verify what it downloaded, and
lets an agent decide it has already read this exact file. The on-disk storage key
is deliberately not exposed.

| Status | Condition |
|---|---|
| `200` | Listed (possibly empty) |
| `400` | No workspace resolved for the caller |
| `404` | Issue not found in this workspace |

### Upload an attachment

```
POST /api/v1/crews/{crewId}/issues/{identifier}/attachments?workspace_id={workspaceId}
```

**Auth:** `OWNER`, `ADMIN`, or `MANAGER` role

**Request Body:** `multipart/form-data` with one part.

| Field | Type | Required | Description |
|---|---|---|---|
| `file` | file | Yes | The file. Maximum 25 MiB. Its extension must be on the allowlist above |

```bash
curl -X POST \
  -H "Authorization: Bearer $CREWSHIP_TOKEN" \
  -F "file=@./crash.log" \
  "https://crewship.example.com/api/v1/crews/crew_1/issues/ENG-4/attachments?workspace_id=ws_abc"
```

**Response:** `201 Created` — the stored record, the same object shape
[List attachments](#list-attachments) returns.

`200 OK` instead of `201` means this exact file — these bytes, under this
filename — was already attached to this issue: no second record was created, no
second timeline entry was written, and the returned object is the one that
already existed. The same bytes under a different filename are a different
attachment and get `201`.

| Status | Condition |
|---|---|
| `201` | Attached |
| `200` | Already attached — the same bytes under the same filename, on the same issue |
| `400` | Malformed multipart form, missing `file` part, or a filename that sanitises to nothing |
| `403` | Caller lacks the MANAGER floor |
| `404` | Issue not found in this workspace |
| `413` | Larger than 25 MiB |
| `415` | Extension not on the allowlist — the response lists what is allowed |
| `503` | This instance has no storage provider configured |

### Download an attachment

```
GET /api/v1/crews/{crewId}/issues/{identifier}/attachments/{attachmentId}?workspace_id={workspaceId}
```

**Auth:** any workspace member.

**Request:** `workspace_id` is the required workspace query parameter. The file is
addressed by the `attachmentId` path parameter. No request body.

**Response:** `200 OK` — the raw bytes, with three headers that matter:

| Header | Value |
|---|---|
| `Content-Type` | The type Crewship resolved from the extension, never the uploader's |
| `X-Content-Type-Options` | `nosniff` |
| `Content-Disposition` | `attachment; filename="crash.log"` |

An attachment belonging to a different issue — even one in the same workspace —
is a `404` through this issue's URL, not a `403`.

| Status | Condition |
|---|---|
| `200` | The file |
| `404` | Not found on this issue, or its stored bytes are missing (for example after a metadata-only restore) |
| `503` | This instance has no storage provider configured |

### Delete an attachment

```
DELETE /api/v1/crews/{crewId}/issues/{identifier}/attachments/{attachmentId}?workspace_id={workspaceId}
```

**Auth:** `OWNER`, `ADMIN`, or `MANAGER` role

**Request Body:** none. The file is addressed by the `attachmentId` path
parameter; `workspace_id` is the only query parameter.

**Response:** `200 OK` with `{"status": "ok"}`

Hard delete of the record, and of the stored bytes — but the bytes only when no
other issue, comment or chat in this workspace still references them. Removing a
file from one issue never removes it from another that carries the same file.

| Status | Condition |
|---|---|
| `200` | Removed |
| `403` | Caller lacks the MANAGER floor |
| `404` | Not found on this issue |

## Milestones

Milestones belong to projects and expose progress counts for the issues linked
to them. All routes are workspace-scoped through the project or milestone.

### List Milestones

```
GET /api/v1/projects/{projectId}/milestones?workspace_id={workspaceId}
```

**Request:** `projectId` is a required path parameter and `workspace_id` selects the workspace. No request body.

Returns `200 OK` with an array ordered by `position`, then creation time. Each
item contains `id`, `project_id`, `name`, nullable `description` and
`target_date`, `status`, `position`, `issue_count`, `done_count`,
`created_at`, and `updated_at`. A project outside the workspace returns `404`.

### Create Milestone

```
POST /api/v1/projects/{projectId}/milestones?workspace_id={workspaceId}
```

**Auth:** `OWNER`, `ADMIN`, or `MANAGER` role.

The request requires `name`; optional fields are `description`, `target_date`,
and `status` (default `active`). The response is `201 Created` with the full
milestone object and its next `position`.

### Update Milestone

```
PATCH /api/v1/milestones/{milestoneId}?workspace_id={workspaceId}
```

**Auth:** `OWNER`, `ADMIN`, or `MANAGER` role.

Any of `name`, `description`, `target_date`, `status`, and `position` may be
updated; at least one field is required. Returns `200 OK` with the updated
milestone, or `400` for invalid JSON/no fields and `404` when it is not in the
workspace.

### Delete Milestone

```
DELETE /api/v1/milestones/{milestoneId}?workspace_id={workspaceId}
```

**Auth:** `OWNER` or `ADMIN` role. Returns `204 No Content`, or `404` when the
milestone is not in the workspace.
