# Admin API

The operational surface for OWNER and ADMIN roles: workspace stats, user management, GDPR subject-access and erasure, memory administration, the Keeper security audit log, and a set of cross-cutting system and metrics endpoints. Most endpoints require the OWNER role; the GDPR and memory-admin endpoints require ADMIN or OWNER (manage permission). The Keeper Phase 2 evaluators and three system endpoints have their own auth model, noted inline.

<Note>
  Unless a section says otherwise, every endpoint on this page requires the **OWNER** role. The GDPR, memory-admin, and Keeper-requests endpoints accept **ADMIN or OWNER** (manage permission).
</Note>

## Stats & users

Read surfaces for workspace-level counts and membership. Both require the OWNER role.

## GET /api/v1/admin/stats

Returns aggregate statistics for the current workspace.

**Required role:** OWNER

**Request:** no body. **Response:** JSON object shown below.

| Status | Condition |
|--------|-----------|
| `200` | Statistics returned. |
| `403` | Caller is not OWNER. |

### Response

```json
{
  "workspaces": 1,
  "users": 12,
  "agents": 8,
  "running": 3
}
```

| Field | Type | Description |
|-------|------|-------------|
| `workspaces` | `integer` | Always 1 (scoped to current workspace) |
| `users` | `integer` | Number of workspace members |
| `agents` | `integer` | Total agents (excluding soft-deleted) |
| `running` | `integer` | Agents with a currently running agent run |

<Note>
  Stats are scoped to the current workspace to prevent cross-workspace data leakage. The `workspaces` field always returns 1.
</Note>

## GET /api/v1/admin/users

Lists the people the caller administers, one row per person. A workspace
`OWNER` or `ADMIN` gets the members of the current workspace. An **instance
administrator** (see [People and workspaces across the
instance](#people-and-workspaces-across-the-instance)) gets every account on
the instance, including accounts that belong to no workspace. The
`X-Admin-Scope` response header says which: `workspace` or `instance`.

**Required role:** ADMIN or OWNER (`manage` permission).

**Request:** no body. **Response:** JSON array shown below.

| Status | Condition |
|--------|-----------|
| `200` | People returned. |
| `401` | Missing authentication or workspace context. |
| `403` | Caller is not ADMIN or OWNER. |
| `500` | A query failed. |

### Response

```json
[
  {
    "id": "user-uuid",
    "email": "alice@example.com",
    "full_name": "Alice Chen",
    "avatar_url": "https://...",
    "created_at": "2025-01-01T00:00:00Z",
    "workspace": { "id": "ws-uuid", "name": "Engineering", "slug": "engineering" },
    "role": "ADMIN",
    "memberships": [
      { "member_id": "wm-cuid", "workspace_id": "ws-uuid", "name": "Engineering", "slug": "engineering", "role": "ADMIN", "joined_at": "2025-01-01T00:00:00Z" }
    ],
    "last_active_at": "2026-09-29T08:12:44Z",
    "active_sessions": 2,
    "cli_tokens": 1,
    "locked_until": null,
    "failed_login_count": 0,
    "email_verified": true
  }
]
```

| Field | Type | Description |
|-------|------|-------------|
| `id` | `string` | User ID |
| `email` | `string` | User email address |
| `full_name` | `string?` | Display name (nullable) |
| `avatar_url` | `string?` | Avatar URL (nullable) |
| `created_at` | `string` | When the account was created |
| `workspace` | `object?` | The membership in the caller's workspace, else the first one; null for an account in no workspace |
| `role` | `string?` | Role in that workspace (OWNER, ADMIN, MANAGER, MEMBER, VIEWER) |
| `memberships` | `array` | Every membership the caller may see: only the current workspace's for a workspace admin, all of them for the instance owner. `member_id` is the id the workspace member routes take. |
| `last_active_at` | `string?` | Latest use of a session that is not signed out |
| `active_sessions` | `int` | Signed-in devices (not revoked, not expired) |
| `cli_tokens` | `int` | Live CLI tokens (not revoked, not expired) |
| `locked_until` | `string?` | Set while a sign-in lockout is in force; null otherwise, including after a lock has run out |
| `failed_login_count` | `int` | Consecutive failed sign-ins |
| `email_verified` | `bool` | Whether the address has been verified |

## `GET /api/v1/admin/users/{userId}/sessions`

A person's signed-in devices, with device and IP address, and their live CLI
tokens (name, scopes, last use — never the secret). `current` marks the
session the caller is using.

**Required role:** ADMIN or OWNER (`manage` permission). The person must be a
member of the caller's workspace unless the caller is the instance owner;
anyone else is `404`, the same answer as an id that does not exist. An ADMIN
cannot act on an OWNER of the workspace.

**Request:** no body; `userId` is the path parameter. **Response:**

```json
{
  "sessions": [
    { "id": "sess-cuid", "created_at": "2026-09-28T07:00:00Z", "last_used_at": "2026-09-29T08:12:44Z", "expires_at": "2026-10-28T07:00:00Z", "user_agent": "Chrome on macOS", "ip": "10.0.0.7", "current": false }
  ],
  "cli_tokens": [
    { "id": "tok-cuid", "name": "laptop", "scopes": ["agents:read"], "created_at": "2026-09-01T10:00:00Z", "last_used_at": "2026-09-27T16:00:00Z", "expires_at": null }
  ]
}
```

| Status | Condition |
|--------|-----------|
| `200` | Sessions and tokens returned. |
| `400` | Missing `userId`. |
| `401` | Missing authentication. |
| `403` | Caller is not ADMIN or OWNER, or an ADMIN targets an OWNER. |
| `404` | No such person among those the caller administers. |
| `500` | A query failed. |

## `POST /api/v1/admin/users/{userId}/sessions/{sessionId}/revoke`

Signs a person out of one device. The session is marked revoked with reason
`admin_revoke`, and an audit entry `user.session_revoked` is written. Other
devices and CLI tokens are untouched.

**Required role:** ADMIN or OWNER, with the same reach rules as the sessions
list above.

**Request:** no body; `userId` and `sessionId` are path parameters.
**Response:** `204 No Content`.

| Status | Condition |
|--------|-----------|
| `204` | Signed out. |
| `400` | Missing `userId` or `sessionId`. |
| `401` | Missing authentication. |
| `403` | Caller is not ADMIN or OWNER, or an ADMIN targets an OWNER. |
| `404` | No such person, or the session is not theirs. |
| `500` | The revoke failed. |

## `POST /api/v1/admin/users/{userId}/sessions/revoke-all`

Signs a person out of every device. Sessions are marked revoked with reason
`admin_invalidate` — the reason the host-side `crewship admin
invalidate-sessions` writes — and an audit entry `user.sessions_revoked` is
written. The password stays as it is; CLI tokens are separate credentials and
stay valid.

**Required role:** ADMIN or OWNER, with the same reach rules as above.

**Request:** no body; `userId` is the path parameter. **Response:**

```json
{ "revoked": 2 }
```

| Status | Condition |
|--------|-----------|
| `200` | Signed out; `revoked` counts the sessions ended. |
| `400` | Missing `userId`. |
| `401` | Missing authentication. |
| `403` | Caller is not ADMIN or OWNER, or an ADMIN targets an OWNER. |
| `404` | No such person among those the caller administers. |
| `500` | The revoke failed. |

## `POST /api/v1/admin/users/{userId}/unlock`

Lifts a sign-in lockout: clears `locked_until` and resets the failed-attempt
counter, so the person can sign in straight away. Writes an audit entry
`user.unlocked`. Unlocking an account that is not locked succeeds and changes
nothing.

**Required role:** ADMIN or OWNER, with the same reach rules as above.

**Request:** no body; `userId` is the path parameter. **Response:** `204 No
Content`.

| Status | Condition |
|--------|-----------|
| `204` | Unlocked. |
| `400` | Missing `userId`. |
| `401` | Missing authentication. |
| `403` | Caller is not ADMIN or OWNER, or an ADMIN targets an OWNER. |
| `404` | No such person among those the caller administers. |
| `500` | The update failed. |

## People and workspaces across the instance

The routes under `/api/v1/admin/instance/` act on the whole server: every
account and every workspace, whether or not the caller belongs to it. They
take no `workspace_id`.

**Who may call them: an instance administrator.** That is:

1. the account whose email is `CREWSHIP_OWNER_EMAIL` on the server, which
   cannot be removed or suspended over the API;
2. anyone named with `PUT /api/v1/admin/instance/admins/{userId}`
   (`users.instance_role`).

The list is always explicit. On an install that names nobody and has no
`CREWSHIP_OWNER_EMAIL`, the first time anyone's status is asked the server
names the OWNERs of the oldest workspace — the people it treated as admins
before — records that in `app_settings` and in the instance audit
(`instance.admin_bootstrapped`), and never does it again. Removing every
named admin later does not bring that rule back; the way in when nobody can
administer is `crewship admin instance add-admin --local` on the host.

The last active instance administrator cannot be removed or suspended
(`409`): with no `CREWSHIP_OWNER_EMAIL`, someone named and unsuspended has to
be left.

A suspended account is never an instance administrator. Being ADMIN or OWNER
of a workspace is not enough for these routes, nor for the instance-wide
settings that also require it (log level, rate limits, re-encryption, legacy
resource pruning, Keeper's judge and evaluator models, notification
providers, instance settings and feature-flag definitions). A CLI token needs
the `instance:admin` scope, or no scope restriction, to reach them. An
instance administrator can mint an `instance:admin` token whatever their
workspace role, including with no workspace at all.

Every instance change and its audit entry are written in one transaction: if
the audit entry cannot be written, the change is undone and the route answers
`500`.

An instance administrator also passes the ADMIN floor of every other
`/api/v1/admin/` route, and need not belong to any workspace: on those routes
they may name any live workspace in `workspace_id`, member or not (an unknown
one is `404`), and the instance-wide reads — `GET /api/v1/admin/stats`,
`/admin/health`, `/admin/log-level`, `/admin/rate-limits`,
`/admin/security-posture`, `/admin/keeper/config`, `/admin/keeper/aux`,
`/admin/keeper/judge/models`, `/admin/legacy-resources`,
`/api/v1/system/keeper`, `/api/v1/system/aux-status` and
`/api/v1/notification-providers` — also answer with no workspace at all, for
the whole instance. A route about one workspace's data answers an instance
administrator who names none with `400` ("choose a workspace"). The instance
settings writes (log level, rate limits, Keeper judge, providers) need no
workspace either. Everyone else keeps the workspace rules: `400` without a
workspace, `403` outside theirs.

`GET /api/v1/admin/stats` without a workspace counts the whole instance.

Also, and `GET /api/v1/admin/users` and
`GET /api/v1/admin/workspaces` answer for the whole instance
(`X-Admin-Scope: instance`). Those two, and a person's sessions, unlock and
sign-out routes, also answer an instance administrator who names no
workspace, since they need not belong to one; anyone else still needs
`workspace_id`. Those lists carry `instance_admin` and
`instance_admin_source` (`env` or `role`),
`suspended_at`, `suspended_reason` and `setup_link_expires_at` per person, and
`owners` per workspace. `GET /api/auth/session` returns `is_instance_admin`
for the signed-in user.

Every write below adds a row to the instance audit (`instance.*` actions). It
has no workspace of its own, so the record of a deleted workspace or erased
account survives it.

## `PUT /api/v1/admin/instance/keeper/governance`

Sets the watchdog for one, several or all workspaces. `set` is a partial
update with the same fields and bounds as the per-workspace
`PUT /api/v1/admin/keeper/governance`: only the fields sent change.

- `workspaces` names the targets by id or slug. `all: true` targets every
  existing workspace. Send one or the other. Neither changes what a new
  workspace starts with; that is
  `PUT /api/v1/admin/instance/keeper/governance/defaults`.
- `dry_run: true` computes the changes and writes nothing. The console's
  confirmation dialog shows this response. Every response carries a
  `preview_id`, a fingerprint of every target's settings before and after.
  Send it back as `expect_preview` when confirming: if a workspace was
  created or a value changed since the preview, the save answers `409` and
  writes nothing.
- The save is one transaction. When the merged settings are invalid in any
  workspace, the response is `400` naming that workspace, and nothing is
  written anywhere.
- A workspace that already has the values is reported with empty `changes`
  and left alone. Each workspace that changes gets an
  `instance.keeper_governance_updated` entry in the instance audit, with the
  fields it changed from and to.
- `security_contact_user_id` and `gov_model_credential_id` name something that
  belongs to one workspace, and are refused for more than one.

**Auth:** instance administrator. **Request:**

```json
{ "all": true, "dry_run": true, "set": { "enabled": true, "deny_notify_min_risk": 5 } }
```

Confirming that preview:

```json
{ "all": true, "expect_preview": "3f9c0a1b2d4e5f6a7b8c9d0e", "set": { "enabled": true, "deny_notify_min_risk": 5 } }
```

**Response:**

```json
{
  "applied": false,
  "changed": 1,
  "preview_id": "3f9c0a1b2d4e5f6a7b8c9d0e",
  "workspaces": [
    {
      "workspace_id": "ws-cuid",
      "workspace_name": "Lab",
      "workspace_slug": "lab",
      "changes": [ { "field": "deny_notify_min_risk", "before": 7, "after": 5 } ]
    },
    { "workspace_id": "ws-cuid-2", "workspace_name": "Ops", "workspace_slug": "ops", "changes": [] }
  ]
}
```

| Status | Condition |
|--------|-----------|
| `200` | Saved, or previewed with `dry_run`. |
| `400` | No target, both `all` and `workspaces`, nothing to change, a value out of bounds or incoherent in some workspace, or a per-workspace field sent for several. |
| `401` | Missing authentication. |
| `403` | Caller is not an instance administrator. |
| `404` | A workspace in `workspaces` does not exist. |
| `409` | `expect_preview` no longer matches: the workspaces or their settings changed since the preview. Nothing was saved. |
| `500` | A write failed. Nothing was saved. |

## `GET /api/v1/admin/instance/retention`

How long every workspace keeps each kind of data, including workspaces the
caller is not a member of. Every window is a number of days, or `null` for
forever. Inbox items, chats and Keeper decisions are forever until an
administrator sets them.

| Window | Default | Can be forever | What ages out |
|--------|---------|----------------|---------------|
| `routine_runs_days` | 90 | no | Finished routine runs. The last 10 runs of every routine, runs waiting on an approval and runs another run replays are always kept. |
| `approvals_days` | 90 | yes | Decided approvals. Pending approvals and autonomy gates are never deleted. |
| `audit_days` | forever | yes | Workspace audit entries. |
| `credential_audit_days` | 90 | yes | Credential reads. The last use stays on the credential. |
| `memory_versions_days` | 30 | no | Memory version history. The instance-wide pass also ages versions out after 30 days, keeping the latest few per file. |
| `page_panel_data_days` | 7 | no | Page panel values, dropped on the panel's next push. The newest value always stays. |
| `inbox_days` | forever | yes | Resolved inbox items, and read items that block nothing. Open items are never deleted. |
| `chats_days` | forever | yes | Chats idle longer than the window that hold no open work (below). |
| `keeper_decisions_days` | forever | yes | Decided Keeper requests with their ledger rows. Pending and escalated requests, and requests backing a live credential lease, are never deleted. |

A chat holds open work, and is kept however old, while it has any delegation,
an unresolved escalation, an unresolved reply item in the inbox, a pending
approval that names it, an unfinished routine run, or an access grant issued
inside the window that is not revoked.

Query parameters:

| Parameter | Description |
|-----------|-------------|
| `ws` | A workspace id or slug. Repeat it, or separate several with commas. Without it, every workspace. |

**Auth:** instance administrator. **Request:** no body. **Response:**

```json
{
  "workspaces": [
    {
      "workspace_id": "ws-cuid",
      "workspace_name": "Lab",
      "workspace_slug": "lab",
      "windows": {
        "routine_runs_days": 90, "approvals_days": 90, "audit_days": null,
        "credential_audit_days": 90, "memory_versions_days": 30, "page_panel_data_days": 7,
        "inbox_days": null, "chats_days": null, "keeper_decisions_days": 365
      }
    }
  ],
```

## `PUT /api/v1/admin/instance/retention`

Sets retention windows for one, several or every existing workspace.
`windows` carries only the windows being changed; `null` is forever where the
window allows it.

- `workspace_ids` is required. A list names the targets by id or slug; `null`
  targets every workspace that exists now. Neither changes what a workspace
  created later starts with: that is
  `PUT /api/v1/admin/instance/retention/defaults`, a separate operation.
- `dry_run: true` computes the changes and writes nothing. The preview lists
  every workspace and, in it, every window that changes, each with
  `rows_affected_next_sweep`: how many rows the next sweep deletes under the
  new window. The rows are counted, not deleted, and backups taken
  before still hold them. For page panel data the count is what each panel's
  next push drops.
- Every response carries a `preview_id` fingerprinting the targets and every
  change. Send it back as `expect_preview` when confirming: if a workspace was
  created or a window changed since the preview, the save answers `409` and
  writes nothing. A save without `expect_preview`, or without any preview, is
  allowed; the console always previews first.
- The save is one transaction. A workspace that already has the values is
  reported with empty `changes` and left alone. Each workspace that changes
  gets an `instance.retention_updated` entry in the instance audit, with each
  window's old and new value.
- Saving a window deletes nothing by itself. The daily sweep does, at its next
  run.

## `POST /api/v1/admin/instance/backups/run`

Starts a backup now and answers at once. Every run — scheduled, catch-up or
manual, instance or workspace — is a row of the server's backup service
(never an agent), so a client that disconnects, or the CLI's 30-second
timeout, cannot cancel it; follow it with
[`GET …/backups/run/{runId}`](#get-api-v1-admin-instance-backups-run-runid).

- With `plan_id`, runs that plan now (one run per workspace for a workspaces
  plan).
- Without it, `scope` says what to back up. `instance` writes one instance
  bundle: the whole database, every file store and every crew container,
  copied in one quiet window — running work is drained first, then every
  write to protected data is held for the copy only (at most the plan's
  `hold_cap_minutes`, 20 by default) and released before packing and
  encryption. `workspaces` writes one bundle per workspace in
  `workspace_ids` (ids or slugs; default every workspace), with `preset`,
  `contents` and `env_mode` choosing what goes in. Without `preset`, an
  instance run is `complete` and a workspaces run `workspace`.

Every backup is encrypted. Give `recipient_ids` (age `age1…` public keys or
recipient ids; `recipients` is accepted as another name) or `passphrase`, not
both. Without either, the recipients of the enabled plan covering the scope
are used; with `plan_id`, keys given in the request replace the plan's for
this run. A passphrase is held in the server's memory until the run starts
and is never stored or logged: a run whose server restarts before it starts
fails and says so. When the vault keys' recovery kit is on, instance bundles
carry them. `note` is shown with the run. Written to the instance audit log
(the passphrase only as `passphrase: true`).

**Auth:** instance administrator. **Request:**

```json
{"scope": "instance", "recipient_ids": ["age1q7x…m3k"], "note": "before upgrade"}
```

**Response** — `id` and `run_id` name the first run, `run_ids` every run
queued:

```json
{"id": "br_…", "run_id": "br_…", "run_ids": ["br_…"], "status": "running"}
```

| Status | Condition |

## DELETE /api/v1/admin/users/\{userId\}/data

GDPR Art. 17 (Right to Erasure) — cascade purge every row referencing the user across the cascadable tables. Writes a `gdpr_actions` audit row with `action='delete'`. **`reason` is required** for the audit trail.

**Required role:** ADMIN or OWNER (`manage` permission).

### Request

```json
{
  "reason": "User SAR ticket #INC-1234 — Right to Erasure request"
}
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `reason` | `string` | yes | Non-empty after trim. Persisted on the `gdpr_actions` row alongside the actor and target. Used in compliance reviews. |

### Response

`202 Accepted` on full success; `207 Multi-Status` on partial success (some tables purged, others returned errors — the `gdpr_actions` row carries the full per-table summary).

```json
{
  "action_id": "gdpr-action-cuid",
  "data_subject": "user-uuid",
  "workspace_id": "ws-uuid",
  "rows_deleted": 7,
  "scope": {
    "peer_cards": 3,
    "memory_versions": 2,
    "inbox_items": 2,
    "inbox_item_reads": 9,
    "page_versions_anonymised": 5,
    "page_grants_removed": 0,
    "page_public_tokens_revoked": 0,
    "page_webhooks_revoked": 0
  }
}
```

On partial failure the same shape is returned with an additional `"error": "<first-error>"` field and HTTP 207.

| Field | Type | Description |
|-------|------|-------------|
| `action_id` | `string` | The audit row id. The same SAR re-run writes a **second** action row — idempotent in row counts (zero on second run) but the audit trail records every attempt. |
| `rows_deleted` | `int` | Sum of rows that went **away**, including the subject's own `inbox_item_reads` markers on this workspace's items. Rows the cascade only anonymised or reassigned (`page_versions_anonymised`, `pages_transferred`) are excluded — nothing was deleted there. |
| `scope` | `object` | Per-table count summary (extensible — new keys appear additively as new tables join the cascade). A key ending in `_anonymised` means the row survived without the subject's name on it; `_removed` / `_revoked` means the row is gone and any capability it carried stopped working; `credentials_reattributed` means a credential the subject created now has the erasing admin as custodian and keeps working. See the [GDPR guide](/security/gdpr) for the per-table contract. |
| `error` | `string?` | Present only on HTTP 207. First error encountered; consult the audit row for the full per-table picture. |

<Warning>
  Memory `payload_ref` content-addressed blobs on disk are **not** deleted by this endpoint — blobs are deduplicated across workspaces and require a separate sweep job (planned). The audit/index rows ARE purged so the SAR is honoured at the DB-visibility layer. See the [GDPR guide](/security/gdpr) for the operator workflow.
</Warning>

## GET /api/v1/admin/journal/verify

Walks the current workspace's journal **hash-chain** and reports whether it is
intact — the tamper-evidence check for the append-only journal (`internal/api/admin_journal_integrity.go`). Detects content mutation, in-place reorder, and mid-chain deletion; see [Audit Log → Tamper-Evidence](/security/audit#tamper-evidence-the-journal-hash-chain) for the guarantee.

**Required role:** ADMIN or OWNER (`canRole(role, "manage")`)

The endpoint takes no parameters; the workspace comes from request context (`X-Workspace-ID`). It stays `200 OK` even when the chain is broken — inspect `ok`.

### Response

```json
{
  "workspace_id": "ws-uuid",
  "ok": false,
  "count": 42,
  "broken_seq": 43,
  "broken_id": "j_9f3c…",
  "reason": "content hash mismatch at seq 43: entry was modified after write"
}
```

| Field | Type | Description |
|-------|------|-------------|
| `ok` | boolean | `true` when the whole chain verifies |
| `count` | integer | Entries walked before returning |
| `broken_seq` | integer | `seq` of the first bad entry (omitted when `ok`) |
| `broken_id` | string | `id` of the first bad entry (omitted when `ok`) |
| `reason` | string | Human-readable cause of the break (omitted when `ok`) |
| `breaks` | array | Every per-row failure (`seq`, `id`, `kind`, `reason`), capped at 100 |
| `break_count` | integer | Exact number of failures, even when `breaks` is trimmed |
| `repairable` | array | Rows whose content is proven authentic but whose live priority is unaccounted for: `seq`, `id`, `stored_priority`, `emit_priority` (the value the keyed hash proves) |
| `repairable_count` | integer | Exact number of such rows, even when the list is trimmed |

A non-empty `repairable` also produces a `priority` break, so `ok` is `false`
— see [Audit Log → Recovered is not resolved](/security/audit#recovered-is-not-resolved).

CLI parity: `crewship journal verify` (exits non-zero on a broken chain **or**
when any entry has an unresolved priority).

| Status | Condition |
|--------|-----------|
| `200` | Response reports `ok`; a broken chain is still a successful HTTP response. |
| `403` | Caller lacks `manage`. |

## `GET /api/v1/admin/memory/versions/{id}/content`

Returns the raw blob bytes for a single `memory_versions` row. Used by the dashboard's row-detail view and by compliance auditors who need the literal content (not just the metadata) -- for example, to confirm a PII scrubber fired on the offending payload.

**Required role:** ADMIN or OWNER (manage permission)

### Response

The body is the raw blob bytes (NOT JSON-wrapped). `Content-Type` is `text/markdown; charset=utf-8` for paths ending in `.md`, otherwise `application/octet-stream` so the client cannot auto-render untrusted bytes as HTML.

Audit metadata travels alongside the body via response headers:

| Header | Description |
|--------|-------------|
| `X-Memory-Sha256` | sha256 from the `memory_versions` row |
| `X-Memory-Bytes` | Length from the row (matches the row's recorded size) |
| `X-Memory-Tier` | Tier (`agent` / `crew` / `workspace` / `pins` / `learned`) |
| `X-Memory-Path` | Canonical memory path |
| `X-Memory-Written-At` | RFC3339 timestamp |
| `X-Memory-Written-By` | Writer identifier (omitted when NULL) |
| `Cache-Control` | `private, max-age=31536000, immutable` -- blobs are content-addressed |

### Example

```bash
curl -H "Authorization: Bearer $TOKEN" \
  -D - \
  https://crewship.example.com/api/v1/admin/memory/versions/mv_01HZ.../content
```

| Status | Condition |
|--------|-----------|
| `400` | Missing workspace context OR missing `id` path segment |
| `403` | MEMBER role |
| `404` | Unknown id OR cross-workspace probe (no existence leak) |
| `410` | Row exists but the blob file is missing on disk (retention sweep, restore-from-backup race) |
| `413` | Blob exceeds the 10 MB cap (DB-claimed size OR on-disk size) |
| `500` | sha mismatch (blob tampered after recording) OR `payload_ref` resolves outside the configured blob root |
| `503` | Memory versioning is not configured (lite-mode deployment without blob root) |

<Warning>
  The handler refuses to follow symlinks under `payload_ref`. The on-disk layout is fixed at `blobRoot/<sha[:2]>/<sha>`; `filepath.EvalSymlinks` is used to verify the resolved path stays inside the blob root, defending against path-traversal vectors in a corrupted or malicious `payload_ref`.
</Warning>

| `413` | Request body exceeds 16 KB |

<Note>
  The read-merge-write runs inside a SQLite `BEGIN IMMEDIATE` (serializable) transaction so concurrent PATCHes touching different keys serialise rather than last-write-wins. </Note>

## POST /api/v1/admin/memory/user-model-sync

```
POST /api/v1/admin/memory/user-model-sync
```

Runs the operator-model sweep now — the one the server otherwise runs once a day at 05:00 UTC — and returns the per-workspace summary the scheduled run only ever logs. It is the same sweep, on the same extractor (the `curator` aux slot, resolved per call, with the `memory.user_model_profile` setting read fresh), over the same set of workspaces; only the trigger and the report differ.

Why it exists: everything about the operator model fails silently by design. Nothing is written when the model proposes nothing, when every candidate is refused by the evidence gate, when the curator slot cannot be built, or when the person is below the interaction threshold — and all four look identical from outside. The summary tells them apart, now, instead of at 05:00 UTC.

The sweep is safe to re-run: the merge is idempotent and the write is capped. It runs synchronously inside the request, one model call per candidate on the slot's per-call budget, so a workspace with many active operators can take minutes — clients must not cap the request at the usual 30 s (the CLI does not).

**Auth:** ADMIN or OWNER (manage permission) in the session workspace. Without a `workspace_id` in the body the run is instance-wide, exactly like the scheduled sweep.

**Request:** optional JSON body. `?workspace_id=` in the query is the *session* workspace, as on every admin route — it is not a filter.

```json
{
  "workspace_id": "ws_01HZ…",
  "dry_run": true
}
```

| Field | Type | Description |
|-------|------|-------------|
| `workspace_id` | `string?` | Narrow the run to one workspace, by id or slug. Omitted: every active (non-deleted) workspace on the instance. |
| `dry_run` | `boolean?` | Run everything up to the write — the candidate query, the consent probe, the threshold, the extractor — and report what *would* have happened. Nothing lands on disk, in `user_models`, or in `peer_card_audit`. Also accepted as `?dry_run=true`. |

**Response:** `200 OK` with the run's report.

```json
{
  "sweep": "user_model",
  "dry_run": false,
  "workspaces": [
    {
      "workspace_id": "ws_01HZ…",
      "candidates": 3,
      "writes": 1,
      "skipped_threshold": 1,
      "skipped_empty": 1,
      "skipped_opt_out": 0,
      "purged_opt_out": 0,
      "errors": 0
    }
  ],
  "totals": { "candidates": 3, "writes": 1, "skipped_threshold": 1, "skipped_empty": 1, "skipped_opt_out": 0, "purged_opt_out": 0, "errors": 0 },
  "duration_ms": 4120
}
```

| Field | Description |
|-------|-------------|
| `sweep` | `user_model` here; `peer_card` on the sibling route. |
| `dry_run` | Echoes the request, so a report cannot be mistaken for a record of what happened. |
| `workspaces[].candidates` | Operators with a chat in the 14-day lookback window. |
| `workspaces[].writes` | Models written (or, on a dry run, that would have been). |
| `workspaces[].skipped_threshold` | Below the interaction threshold (messages and session length). |
| `workspaces[].skipped_empty` | The extractor had nothing to write. With no model on the curator slot this is every candidate. |
| `workspaces[].skipped_opt_out` / `purged_opt_out` | The operator has opted out; `purged` means an existing model was deleted (or would have been). |
| `workspaces[].errors` | Candidates that failed inside the sweep — an extractor error, a failed write. Each has a `Warn` line in the server log. |
| `workspaces[].error` | Present only when the sweep for that workspace could not run at all (the candidate query failed). The other workspaces still ran. |
| `totals` | The same counters summed over `workspaces`. |

### Example

```bash

  -H "Content-Type: application/json" \
```

## POST /api/v1/admin/memory/peer-card-sync

```
POST /api/v1/admin/memory/peer-card-sync
```

Runs the peer-card sweep now — the 04:00 UTC one — and returns the same report shape as the operator-model route above, with `"sweep": "peer_card"`. The sweep walks every (agent, operator) pair that crossed the interaction threshold, purges the cards of operators who have opted out, and writes a card where the extractor produced one. The server wires no peer-card extractor today, so a run indexes and purges without writing new bodies — which is also what the scheduled run does — and every threshold-crosser shows up under `skipped_empty`.

**Auth:** ADMIN or OWNER (manage permission) in the session workspace; instance-wide without `workspace_id`.

**Request:** the same optional body as the operator-model route — `workspace_id` (id or slug) and `dry_run`, the latter also as `?dry_run=true`.

**Response:** `200 OK` with the report — `sweep`, `dry_run`, `workspaces[]`, `totals`, `duration_ms` — where the per-workspace counters are `candidates`, `writes`, `skipped_threshold`, `skipped_empty`, `skipped_opt_out`, `purged_opt_out`, `errors`, plus `error` when that workspace's sweep could not run.

| `400` | Malformed JSON body, an unknown field, or a `dry_run` that is not `true`/`false` |

## Keeper Phase 2 — F4 evaluators

<Note>
  The four evaluator endpoints are **internal-auth** (X-Internal-Token) — they're invoked by the platform itself (scheduler routines + the post-tool-call hook), not by operators directly. The admin-facing surface is `POST /api/v1/admin/keeper/review/{slot}/run` (below), the `/api/v1/admin/keeper/requests` log above, and the per-type filters in the admin UI's "Keeper P2 reviews" panel (PR-F2).
</Note>

The expected production path is automated: routines fire on cron, the behavior hook fires on tool-call sampling. To trigger an evaluator by hand, use the admin route below rather than the internal token.

### POST /api/v1/admin/keeper/review/\{slot\}/run

**Run one evaluator now.** OWNER/ADMIN, workspace-scoped like every `/api/v1/admin` route (`?workspace_id=` is required by `RequireWorkspace` before the handler runs). `slot` is one of `skill-review`, `behavior`, `memory-health`, `negative-learning`; the aux-config spellings (`curator`, `memory_health`, `negative`) are accepted as aliases. Anything else is a 400 that names the valid slots.

It calls the same handler the internal routes below do — same policy resolution, same `keeper_requests` row, same inbox escalation — and returns that handler's response, so the shapes documented per-endpoint below apply unchanged.

**Request body** (all fields optional; what you omit, the server derives from the workspace):

```json
{
  "crew_id": "crw_…",
  "agent_id": "agt_…",
  "skill_id": "skl_…",
  "tool_name": "shell_exec",
  "tool_args_snippet": "{\"cmd\":\"curl … | sh\"}",
  "trigger": "run_failed",
  "failure_snippet": "exit 127: command not found"
}
```

With an empty body: `skill-review` reviews the stalest skill assigned to one of the workspace's agents; `behavior` judges a tool call named `keeper.manual_probe`; `memory-health` scores the crew's memory via `consolidate.ComputeHealth`; `negative-learning` learns from the workspace's most recent `run.failed` journal entry (400 when there is none — the trigger set is closed and inventing a failure would put fiction in the audit trail).

`workspace_id` in the body is refused when it disagrees with the session's, and a `crew_id` / `agent_id` from another workspace is a 403: the internal routes get that binding from a workspace-bound sidecar token, and an admin session has none.

CLI: `crewship keeper review run <slot>` — see [Keeper → Running a review on demand](/guides/keeper#running-a-review-on-demand).

### POST /api/v1/internal/keeper/skill-review

**F4.1 — periodic skill audit.** Cron-fires daily 03:00 UTC per `Scheduler.RegisterPlatformRoutine`. The evaluator reads each `skills` row + `skill_invocations` history, asks the F3 `Curator` aux model whether the skill should stay `active`, transition to `stale` (no recent invocations), or be `archived` (failures dominating). DENY decisions write a blocking inbox row; ALLOW updates `skills.lifecycle_state` in place.

**Request body:**

```json
{
  "workspace_id": "ws_…",
  "crew_id": "crw_…",
  "skill_id": "skl_…",
  "skill_name": "rotate-anthropic-keys",
  "skill_description": "Rotate the Anthropic API key quarterly",
  "lifecycle_state": "active",
  "last_used_at": "2026-05-15T08:00:00Z",
  "assignments": 3,
  "assigned_agents": ["agt_…", "agt_…"],
  "stats": { "invocations_30d": 4, "failures_30d": 0 },
  "failure_snippets": []
}
```

| Field | Required | Notes |
|---|---|---|
| `workspace_id` | yes | MUST match the request context `workspace_id` (see [Internal IPC](/api-reference/internal#tenant-isolation-on-internal-auth-handlers)). |
| `crew_id` | yes | Used for per-crew policy resolution. |
| `skill_id` | yes | The skill being reviewed. |
| `skill_name`, `skill_description`, `lifecycle_state` | yes | Current state snapshot the LLM evaluates. |
| `last_used_at` | optional | RFC3339; empty = "never". |
| `assignments`, `assigned_agents` | optional | Fan-out context for ESCALATE → inbox routing. |
| `stats` | optional | 30-day invocation + failure counts. |
| `failure_snippets` | optional | Up to 3 most-recent failure excerpts (truncated). |

**Response:**

```json
{
  "request_id": "kpr_skr_a3f8e2…",
  "decision": "ALLOW",
  "reason": "Skill still actively used (4 invocations in 30d, 0 failures)",
  "risk_score": 1,
  "verify_after_decide": true,
  "unverify_after_decide": false,
  "proposed_lifecycle": "active"
}
```

DENY routes a blocking `inbox_items` row to the assigned agents' workspace (per `assigned_agents` fan-out). ESCALATE routes a `MANAGER`-targeted blocking row.

### POST /api/v1/internal/keeper/behavior

**F4.2 — post-tool-call behavior monitor.** Fires from `behaviorhook.MaybeEvaluate` (orchestrator `EventPostToolCall` event), sampled at the per-crew rate (default 1-in-5). The evaluator reads the `(tool_name, tool_args_snippet, current crew behavior_mode)` triple and returns ALLOW / DENY / ESCALATE.

`behavior_mode=warn` (default): DENY → non-blocking inbox; agent's NEXT tool call proceeds. `behavior_mode=block`: DENY → blocking inbox + `ShouldBlock=true` in the response so the orchestrator interrupts the agent's next call. Forbidden combination `(autonomy=full + behavior_mode=block)` rejected at API + DB layer.

**Request body:**

```json
{
  "workspace_id": "ws_…",
  "crew_id": "crw_…",
  "agent_id": "agt_…",
  "agent_name": "Anna",
  "crew_name": "Ops",
  "tool_name": "shell_exec",
  "tool_args_snippet": "{\"cmd\":\"rm -rf node_modules\"}"
}
```

**Response:**

```json
{
  "request_id": "kpr_bhv_b71e9c…",
  "decision": "DENY",
  "reason": "Destructive command without scoped path; recommend restricting to a specific directory",
  "risk_score": 7,
  "should_block": true,
  "policy_decision": "block_inbox"
}
```

`policy_decision` is the resolved per-crew policy verdict (e.g. `inbox_approve`, `auto_log_inbox`, `block_inbox`) that drives whether an inbox row is written and whether it blocks.

### POST /api/v1/internal/keeper/memory-health

**F4.3 — periodic memory consolidation review.** Cron-fires daily 03:30 UTC. The evaluator consumes a `consolidate.HealthSnapshot` (the 5-metric health score: Freshness / Coverage / Coherence / Efficiency / Reachability, each in `[0, 100]`, plus the weighted `Overall`) and decides whether to auto-trigger a consolidation routine. Staleness and contradiction counts travel as separate top-level body fields, not inside `snapshot`.

**Request body:**

```json
{
  "workspace_id": "ws_…",
  "crew_id": "crw_…",
  "crew_name": "Ops",
  "agent_name": "Anna",
  "snapshot": {
    "WorkspaceID": "ws_…",
    "CrewID": "crw_…",
    "Freshness": 80,
    "Coverage": 70,
    "Coherence": 65,
    "Efficiency": 90,
    "Reachability": 87,
    "Overall": 76
  },
  "agent_md_bytes": 2840,
  "persona_md_bytes": 1120,
  "crew_md_bytes": 5120,
  "stalest_entry_days": 412,
  "contradiction_count": 3
}
```

<Note>
  `snapshot` is the `consolidate.HealthSnapshot` Go struct serialised **without JSON tags**, so its wire keys are PascalCase (`Freshness`, `Reachability`, `Overall`, …) and each metric is on a `0–100` scale — not the `reachability_pct` / `0–1` shape an external caller might guess. `stalest_entry_days` and `contradiction_count` are top-level fields alongside `snapshot`, not nested inside it.
</Note>

**Response:**

```json
{
  "request_id": "kpr_mhc_c83a4b…",
  "decision": "DENY",
  "reason": "412-day stalest entry + 3 contradictions; consolidator recommended",
  "risk_score": 6,
  "auto_consolidate": true,
  "overall_score": 38
}
```

`auto_consolidate=true` triggers `consolidator.Run` for the workspace; ESCALATE writes a blocking inbox row instead.

### POST /api/v1/internal/keeper/negative-learning

**F4.4 — failure-event lesson capture.** Fires after a guardrail trip, run failure, or explicit operator "log this lesson" action. The evaluator decides whether the failure is worth a `kind=negative` lesson in the agent's `lessons.md`. ALLOW writes through `consolidate.WriteLesson` (PR-Z Z.7) which enforces YAML schema + idempotency by ID + flock + atomic-rename.

**Self-learning gate:** ALLOW auto-applies only when the agent has `self_learning_enabled = 1` (migration v106). With `self_learning_enabled = 0` (default), ALLOW queues a blocking inbox row with the full lesson proposal in `payload_json` and the marker `"self_learning_gate": "off"` so the UI can distinguish the gate-demoted path. See [Autonomy + self-learning](/guides/autonomy-and-self-learning).

**Trigger kinds:** `run_failed`, `guardrail_warn`, `guardrail_error`, `keeper_execute_deny`.

**Request body:**

```json
{
  "workspace_id": "ws_…",
  "crew_id": "crw_…",
  "agent_id": "agt_…",
  "agent_name": "Anna",
  "crew_name": "Ops",
  "agent_memory_dir": "/output/agt_…/.memory",
  "trigger": "run_failed",
  "tool_name": "shell_exec",
  "failure_snippet": "deploy.sh: missing DATABASE_URL",
  "prior_lesson": ""
}
```

| Field | Notes |
|---|---|
| `agent_memory_dir` | Container-side path where `lessons.md` lives; the consolidate writer mkdir-p's as needed. |
| `trigger` | One of the four kinds above. |
| `prior_lesson` | Optional dup-suppression: if non-empty, the evaluator gets it as "the agent already knows X" context and is less likely to ALLOW a near-duplicate. |

**Response:**

```json
{
  "request_id": "kpr_neg_d94f5a…",
  "decision": "ALLOW",
  "reason": "Recurring deploy-env mistake worth a permanent lesson",
  "risk_score": 4,
  "write_lesson": true,
  "lesson_id": "les_abc123…"
}
```

When `self_learning_enabled = 0` the response still says `write_lesson: true` (the evaluator's intent), but no lesson lands on disk — the operator must approve via inbox. Check `gdpr_actions`-style audit via `GET /api/v1/admin/keeper/requests?request_type=negative_learning`.

### Cross-tenant guard

<Accordion title="How the four evaluators enforce workspace isolation">
  All four endpoints assert `body.workspace_id == ctx.workspace_id` via `assertBodyWorkspaceMatchesCtx` before any evaluator runs. Asymmetric forgery (query=A, body=B) returns `400 Bad Request`. Empty ctx workspace also returns 400 — the gate refuses to operate without the middleware that's supposed to set it. Symmetric forgery (caller picks one workspace consistently) requires PR-F24 token-to-workspace binding to close fully. See [Internal IPC — Tenant isolation](/api-reference/internal#tenant-isolation-on-internal-auth-handlers).
</Accordion>

## System

Small cross-cutting endpoints that don't belong to any single domain handler. They surface install state, telemetry consent, the running binary's version, and dashboard time-series metrics.

<Note>
  `setup-status` and `telemetry` are intentionally **unauthenticated** because the login page needs to read them before any session exists; `version` and `metrics/timeseries` require an authenticated user (`metrics/timeseries` also needs workspace context).
</Note>

### GET /api/v1/system/setup-status

First-run gate. Returns whether the install needs to be bootstrapped (empty `users` table) and whether public signup is enabled. The login page calls this on every page paint -- when `needs_bootstrap` is `true`, the browser routes to `/bootstrap` instead of `/login`.

**Auth:** none -- the answer is what tells the browser which page to render.

**Request:** no body. **Response:** `{needs_bootstrap, allow_signup}`.

| Status | Condition |
|--------|-----------|
| `200` | Bootstrap state returned; database errors fail closed in the body. |

#### Response

```json
{
  "needs_bootstrap": false,
  "allow_signup": false
}
```

| Field | Type | Description |
|---|---|---|
| `needs_bootstrap` | boolean | `true` when `COUNT(*) FROM users = 0`. DB errors fail closed as `false` -- a transient blip won't ship the user into the bootstrap flow on a healthy install. |
| `allow_signup` | boolean | Mirrors the `CREWSHIP_ALLOW_SIGNUP` server flag. When `false`, the login page hides the "Sign up" link. |

### GET /api/v1/system/telemetry

Read-only consent gate for the frontend's Sentry client. The Next.js `sentry.client.config.ts` fetches this before calling `Sentry.init` and bails out if `enabled=false`. Consent is flipped via the CLI (`crewship telemetry on/off`), never over HTTP -- making this endpoint mutating would create a CSRF vector that flips the bit on every cross-site navigation.

**Auth:** none -- the login page must boot crash reporting before any session exists.

**Request:** no body. **Response:** `{enabled, install_id}`.

| Status | Condition |
|--------|-----------|
| `200` | Consent state returned; transient failures fall back to disabled. |

#### Response

```json
{
  "enabled": true,
  "install_id": "a3f9c2e1b8d74f5a"
}
```

| Field | Type | Description |
|---|---|---|
| `enabled` | boolean | `true` only when the operator has opted in, a DSN is wired, AND the backend Sentry init succeeded. |
| `install_id` | string | Anonymous identifier the backend already ships as Sentry's `ServerName`. Exposed so frontend events group with backend events for the same install. |

Errors fall back to `{enabled: false, install_id: ""}` rather than 5xx -- a transient DB blip defaults to the privacy-preserving outcome.

### GET /api/v1/system/version

Reports the running binary's **build identity** and (cache-permitting) the latest release from GitHub. The web UI uses `current`/`latest`/`newer`/`url` to render an "update available" banner; the build fields answer the separate question of *which build this server actually is*.

This is the only way to ask a running server what it is. `crewship version --remote` is the CLI for it.

**Auth:** required (any authenticated user, no workspace role needed).

**Request:** no body. **Response:** build identity and release metadata below.

| Status | Condition |
|--------|-----------|
| `200` | Version information returned. |
| `401` | Missing or invalid authentication. |

#### Response

```json
{
  "current": "0.4.1",
  "latest": "0.4.2",
  "newer": true,
  "url": "https://github.com/crewship-ai/crewship/releases/tag/v0.4.2",

  "commit": "496c8c1a84be761abdb5cbe323a1fd501b8b9ab7",
  "build_time": "2026-08-02T15:35:24Z",
  "dirty": false,
  "go_version": "go1.26.5",
  "os": "linux",
  "arch": "amd64",
  "schema_version": 20260801150210
}
```

| Field | Type | Description |
|---|---|---|
| `current` | string | The running binary's version (`SetBuild`-injected from `cmd_start`). `"dev"` for any build made without `-ldflags`. |
| `latest` | string? | Latest release tag from GitHub. `null` on a cold cache + GitHub timeout. |
| `newer` | boolean | `true` when `latest > current` by semver. |
| `url` | string? | Release page URL. `null` paired with `null` `latest`. |
| `commit` | string | Full git SHA of the build. Falls back to the binary's embedded VCS stamp when no `-ldflags` were passed, which is the only source an unstamped build has. `""` when neither is available (`go run`, `go install` from the module proxy). |
| `build_time` | string | RFC 3339. The `-ldflags` build date, else the commit time from the VCS stamp. `""` when unknown. |
| `dirty` | boolean? | Whether the working tree had uncommitted changes at build time. **`null` means unknown** -- a build with `-ldflags` but no VCS stamping (the Dockerfile path) genuinely does not know, and reporting that as `false` would be a confident wrong answer. |
| `go_version` | string | Go toolchain that compiled the server. |
| `os` / `arch` | string | `GOOS` / `GOARCH` of the server binary. |
| `schema_version` | integer | The highest migration this server binary can apply. For anything past the closed legacy sequential block this is a `YYYYMMDDHHMMSS` timestamp, so it also dates the newest schema change the build contains. A booted server has already migrated its database to this number. |

The handler imposes a 4 s upper bound on top of the update package's 5 s internal HTTP timeout -- a cold cache + slow network still returns "no info" rather than blocking the UI render. The build fields are computed in-process and are unaffected by it.

<Note>
  `current` alone cannot identify a build. Every binary an `-ldflags`-less `go build` has ever produced calls itself `dev` -- which is how a dev slot once sat a full day behind `main` with nothing able to say so. Compare `commit`.
</Note>

| Status | Condition |
|---|---|
| `400` | Unknown `metric` / `window` / `bucket` / `group_by`; bucket larger than window; combination produces &gt;200 buckets; `group_by=model` for a metric other than `cost_usd`; `group_by=crew` for a metric other than `issues_closed`/`runs_count`; `group_by=status` for a metric other than `issues_closed`/`active_missions`. |
| `401` | Workspace context missing from the request. |
| `500` | SQLite fill query failed. |

## License System

<Note>
**Roadmap (v0.2).** The license/edition system below is on the v0.2 roadmap. v0.1 ships as fully open-source Apache-2.0 with no edition gating.
</Note>

Crewship will use a three-tier licensing model that controls workspace limits and feature availability.

### Editions

| Edition | Description | Limits |
|---------|-------------|--------|
| **Community** | Free, default edition | 15 crews, 10 agents/crew, 5 members |
| **Team** | Paid team tier | Higher limits, additional features |
| **Enterprise** | Full enterprise tier | Unlimited, all features enabled |

### License Claims

Each license contains signed claims:

| Claim | Type | Description |
|-------|------|-------------|
| `license_id` | `string` | Unique license identifier |
| `licensee_name` | `string` | Licensed user name |
| `licensee_org` | `string` | Licensed organization |
| `edition` | `string` | `community`, `team`, or `enterprise` |
| `max_crews` | `integer` | Maximum number of crews |
| `max_agents_per_crew` | `integer` | Maximum agents per crew |
| `max_members` | `integer` | Maximum workspace members |
| `features` | `string[]` | Enabled feature flags |
| `issued_at` | `integer` | Unix timestamp of issuance |
| `expires_at` | `integer` | Unix timestamp of expiration |

### License Verification

Licenses are verified using Ed25519 digital signatures:

<Steps>
  <Step title="Signed format">
    A license file contains a JSON object with `payload` (the claims as a JSON string) and `signature` (base64-encoded Ed25519 signature).
  </Step>
  <Step title="Public key embedding">
    The Ed25519 public key is embedded into the binary at build time via `ldflags`. This prevents license tampering by tying verification to the specific build.
  </Step>
  <Step title="Signature verification">
    On startup, Crewship decodes the public key and signature from base64, then verifies the payload using `ed25519.Verify()`.
  </Step>
  <Step title="Expiration check">
    If the license has an `expires_at` timestamp and it is in the past, the license is rejected and community defaults apply.
  </Step>
  <Step title="Fallback">
    If no license file exists, verification fails, or the license is expired, Crewship runs with community edition defaults.
  </Step>
</Steps>

<Warning>
  The public key variable is set at build time. Without a valid public key embedded in the binary, license loading will fail with "no public key embedded in binary" and community defaults will apply.
</Warning>
