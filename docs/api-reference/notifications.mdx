Per-user activity feed. Other handlers create rows by calling the internal `CreateNotification` helper (`internal/api/notification_handler.go`); the user-facing endpoints below let the frontend list, count, mark read, and dismiss them. Every new row also fans out over WebSocket on the `user:{userID}` channel as `notification.created` so the dashboard updates without polling.

<Note>
  All endpoints below require an authenticated session **and** workspace context — the routes are wrapped in the `RequireWorkspace` middleware, so a `workspace_id` (query param, `{workspaceId}` path value, or `X-Workspace-ID` header) must be present and the caller must be a member, or the request fails at the middleware (`400` when absent, `403` when not a member). Data scoping is nonetheless strictly per-user: every query filters on `user_id = <session user>`, and a row belonging to another user is indistinguishable from one that doesn't exist (`404`).
</Note>

Every endpoint also returns `401 Unauthorized` when there is no authenticated
user. Successful responses are `200 OK` except delete, which is `204 No
Content`; database/query failures are `500`. These endpoints do not accept a
request body. The workspace middleware returns `400 Bad Request` when
`workspace_id` is missing and `403 Forbidden` when the authenticated user is
not a member; the notification handlers then scope every operation to the
authenticated user's ID.

## Endpoints

| Method | Endpoint | Purpose |
|---|---|---|
| GET | [`/api/v1/notifications`](#get-apiv1notifications) | List notifications, newest first |
| GET | [`/api/v1/notifications/count`](#get-apiv1notificationscount) | Unread count for the navbar badge |
| POST | [`/api/v1/notifications/{notificationId}/read`](#post-apiv1notificationsnotificationidread) | Mark one notification read |
| POST | [`/api/v1/notifications/read-all`](#post-apiv1notificationsread-all) | Mark all unread read |
| DELETE | [`/api/v1/notifications/{notificationId}`](#delete-apiv1notificationsnotificationid) | Delete one notification |

## Response shape

| Field | Type | Notes |
|---|---|---|
| `id` | string (CUID) | Notification id |
| `actor_type` | `"user"` \| `"agent"` | Who triggered the notification |
| `actor_id` | string | User or agent id |
| `actor_name` | string \| omitted | Joined from `users.full_name` or `agents.name`; the field is **omitted** (carries `omitempty`) when the actor row no longer exists |
| `action` | string | Free-form action verb (e.g. `mentioned`, `assigned`, `completed`) |
| `entity_type` | string | Entity kind the action targets (e.g. `mission`, `issue`, `chat`) |
| `entity_id` | string \| null | Entity id |
| `entity_title` | string \| null | Cached title; safe to display without joining |
| `read_at` | RFC3339 \| null | `null` = unread |
| `created_at` | RFC3339 | Always set |

## `GET /api/v1/notifications`

Paginated list, newest first.

**Request:** no body.

| Query param | Type | Default | Notes |
|---|---|---|---|
| `limit` | int | `50` | Capped at `100` server-side. |
| `offset` | int | `0` | Negative values become `0`. |
| `read` | `"true"` \| `"false"` | (unset = all) | Filter by read state. |

Returns `200` with a JSON array (possibly empty — never `null`).
Unparseable or non-positive `limit` values use the default; values above 100
are clamped to 100. Values other than `true` or `false` for `read` are
ignored and return both read states.
An omitted or unrecognised `read` value applies no read-state filter. The
`offset` is zero-based and negative pagination values are normalised by the
server.

**Statuses:** `200 OK`; `400`/`403` from workspace resolution; `401` without
authentication; `500` for a query or row-scan failure.

```bash
curl -H "Cookie: <session>" \
  "https://crewship.example.com/api/v1/notifications?read=false&limit=20"
```

```json
[
  {
    "id": "ntf_01HVZ...",
    "actor_type": "user",
    "actor_id": "u_01HVY...",
    "actor_name": "Petra Nováková",
    "action": "mentioned",
    "entity_type": "mission",
    "entity_id": "mis_01HVX...",
    "entity_title": "Q4 onboarding refresh",
    "read_at": null,
    "created_at": "2026-05-20T08:14:22Z"
  }
]
```

## `GET /api/v1/notifications/count`

Unread count, cheap. Used to drive the navbar badge.

**Request:** no body.

```json
{ "unread": 7 }
```
Returns `200 OK`; the count is scoped to the authenticated user.

The count is scoped to the authenticated user in the current workspace; it
does not include notifications belonging to other users.

**Statuses:** `200 OK`; `400`/`403` from workspace resolution; `401` without
authentication; `500` for a database failure.

## `POST /api/v1/notifications/{notificationId}/read`

Mark a single notification read. Idempotent — re-reading an already-read notification still returns `200`. Returns `404` only when the notification does not exist (or belongs to a different user, which is indistinguishable on purpose).

**Request:** no body.

```json
{ "status": "ok" }
```
Returns `200 OK` and is idempotent for an already-read notification.

The response is always the same for a notification that is already read. A
notification owned by another user is treated as not found.

**Statuses:** `200 OK`; `400`/`403` from workspace resolution; `401` without
authentication; `404` when the notification is absent or belongs to another
user; `500` for a database failure.

## `POST /api/v1/notifications/read-all`

Mark every currently-unread notification read for the calling user. Returns the row count.

**Request:** no body.

```json
{ "updated": 23 }
```
Returns `200 OK`; `updated` may be zero.

**Statuses:** `200 OK`; `400`/`403` from workspace resolution; `401` without
authentication; `500` for a database failure.

## `DELETE /api/v1/notifications/{notificationId}`

Hard delete. Returns `204 No Content` on success, `404` when the row doesn't exist or doesn't belong to the calling user.

**Request:** no body.

**Statuses:** `204 No Content`; `400`/`403` from workspace resolution; `401`
without authentication; `404` when the notification is absent or belongs to
another user; `500` for a database failure.

## WebSocket event

When any handler in the server calls `CreateNotification`, the new row is broadcast on the `user:{userID}` channel:

```json
{
  "type": "notification.created",
  "channel": "user:usr_01HVZ...",
  "payload": {
    "id": "ntf_01HVZ...",
    "action": "mentioned",
    "entity_type": "mission",
    "entity_id": "mis_01HVX...",
    "entity_title": "Q4 onboarding refresh"
  }
}
```

The frontend listens on its own user channel — see [WebSocket](/api-reference/websocket) for the connect + subscribe protocol.
