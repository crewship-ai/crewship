# crewship inbox

The inbox is the unified "things needing a human" feed — waitpoints awaiting approval, escalations from agents, failed runs, and direct messages. The CLI is the scriptable mirror of the `/inbox` web page; cron + jq + `inbox list` is the canonical "ping Slack when unread piles up" recipe. Defined in `cmd/crewship/cmd_inbox.go`.

```bash
crewship inbox <subcommand> [flags]
```

Auth: every subcommand requires `crewship login` plus an active workspace. The inbox is backed by the `inbox_items` table (migration v85), written-through by waitpoint creation, escalation creation, and run-failure handlers.

## Subcommands

| Command | Purpose |
| --- | --- |
| `inbox list` | List inbox items (default: unread only). |
| `inbox get <id>` | Show a single item with its full body + structured payload. |
| `inbox count` | Print the bell-badge unread count (cheaper than `list` for polling). |
| `inbox read <id>` | Mark an item as read **for you** — read state is per user, so another recipient of a role-targeted item still sees it unread. |
| `inbox unread <id>` | Flip an item back to unread for you (clears only your own read marker; restores an archived item for everyone). |
| `inbox resolve <id>` | Mark resolved, optionally recording the action taken. Resolved is workspace-shared. Refused (`409`) on a live waitpoint or escalation — see [`inbox resolve`](#inbox-resolve). |
| `inbox act <id> <action>` | Act on a `run_needs_human` card: `answer` delivers `--input` to the agent's session and resumes the run, `take_over` / `dismiss` settle the session. Writes a receipt, resolves the card in place. |
| `inbox archive <id>` | Resolve with `resolved_action=archived` (Gmail-style clear without a decision). |
| `inbox bulk read` | Bulk-mark items as read. |
| `inbox bulk resolve` | Bulk-mark items as resolved. |

## Flags

### `inbox list`

| Flag | Default | Effect |
| --- | --- | --- |
| `--state <enum>` | `unread` | Filter by state. One of `unread`, `read`, `resolved`, `all`. |
| `--kind <enum>` | (unset) | Filter by kind. One of `waitpoint`, `escalation`, `failed_run`, `message`, `memory_consolidation`, `schedule_missed`, `schedule_circuit_breaker_tripped`, `webhook_fire_failed`, `automation_enqueue_failed`, `run_needs_human` (a run's [outcome](/api-reference/issues#outcome) resolved to `NEEDS_HUMAN`, work package B6). |
| `--limit <n>` | `50` | Max rows. Server caps at 500. |
| `--offset <n>` | `0` | Skip this many rows (server-side offset pagination). |
| `--all` | `false` | Keep requesting pages until the server reports `has_more: false`. Exact only on a quiet workspace: a row that leaves the filter mid-walk shifts the window and is never returned. |

### `inbox resolve`

| Flag | Default | Effect |
| --- | --- | --- |
| `--action <enum>` | (unset) | Record what was done: `approved`, `denied`, `retried`, `cancelled`, `acknowledged`, `dismissed`. Stored in `resolved_action` for the audit trail. |

Which kinds it applies to:

- `message`, `failed_run` and the other inbox-owned kinds — always.
- `waitpoint`, `escalation` — **only when the backing record is already gone** (a token the sweep pruned, a staged hire already swept, a keeper-synthetic escalation that never had an `escalations` row). A **live** one is refused with `409`: this is the inbox-side resolve only, it does not call the source endpoint, and closing the row here would leave the run parked forever waiting for a decision that never reached it.

On the refusal the CLI exits non-zero and prints the command that decides it at the source, with the real token filled in:

```text
API error (409): use the source endpoint for this kind … — inbox PATCH only supports 'read' for source-managed items
This is a live waitpoint: the decision has to reach the run, so it is made at the source.
  approve: crewship routine waitpoints approve wp_tok_abc --comment "LGTM"
  reject:  crewship routine waitpoints reject wp_tok_abc
  mark it read here instead: crewship inbox read ibx_01HVZ...
```

An escalation gets the same shape with `crewship escalation resolve <id> --action approve|reject`. To know in advance which case a row is, read `source_missing` on [`inbox get`](#mark-an-item).

### `inbox act`

```bash
crewship inbox act <id> answer --input "Use the staging bucket, not prod."
crewship inbox act <id> take_over
crewship inbox act <id> dismiss
```

| Flag | Default | Effect |
| --- | --- | --- |
| `--input <text>` | (unset) | The answer to deliver to the agent. Required for `answer`, ignored for the other two. |

`answer` posts the text as your comment on the issue and delivers it to the same agent session that raised the card; the run resumes from its checkpoint with the answer as its next delivery (one delivery, one run — if the session is mid-run the delivery queues until that run ends). `take_over` and `dismiss` move the session from `awaiting_input` to `idle`. Every action leaves an `inbox_acted` receipt on the issue's event log (`crewship issue events <id>`) naming who acted, the action, the session's `agent_version` and, for an answer, the delivery and run it produced, and resolves the card in place with the same receipt under `payload.receipt`. Acting twice is refused (`409 already acted on`); waitpoints and escalations are decided through their own commands, not here.

### `inbox bulk read`

| Flag | Default | Effect |
| --- | --- | --- |
| `--ids <csv>` | (unset) | Comma-separated inbox item IDs. |
| `--all-unread` | `false` | Target every currently-unread item (server cap: 500 per call). |

### `inbox bulk resolve`

| Flag | Default | Effect |
| --- | --- | --- |
| `--ids <csv>` | (unset) | Comma-separated inbox item IDs. |
| `--all-unread` | `false` | Target every currently-unread item. |
| `--action <enum>` | (unset) | `approved|denied|retried|cancelled|acknowledged|dismissed`. |

`--ids` and `--all-unread` are mutually exclusive on both bulk subcommands.

## Examples

### Triage

```bash
crewship inbox list                       # unread only (default)
crewship inbox list --state all           # include read + resolved
crewship inbox list --kind waitpoint      # narrow by kind
crewship inbox list --limit 200
crewship inbox list --all          # the whole feed, not just the first page
crewship inbox list --format json | jq '.[] | {id, kind, title}'
```

Output is coloured by state (yellow=unread, cyan=read, green=resolved) and kind (yellow=waitpoint, red=escalation/failed_run, cyan=message), so a 50-row feed scans at a glance.

### Polling the badge

```bash
while true; do
  if [ "$(crewship inbox count)" -gt 0 ]; then
    notify-send "Crewship: inbox needs attention"
  fi
  sleep 60
done
```

`inbox count` hits `GET /api/v1/inbox/count` (the bell-badge endpoint) — much cheaper than `inbox list` when you only need the integer.

### Mark an item

```bash
crewship inbox get inbox_abc123           # full body + payload for one item
crewship inbox read inbox_abc123
crewship inbox unread inbox_abc123        # flip back (also restores an archived item)
crewship inbox resolve inbox_abc123 --action approved
crewship inbox resolve inbox_abc123 --action retried
crewship inbox resolve inbox_abc123       # generic, no action
crewship inbox archive inbox_abc123       # resolve with action=archived, no decision
```

`inbox get <id>` (backed by `GET /api/v1/inbox/{id}`) is the detail counterpart of `list` — it returns the markdown body and the structured `payload` that the list view omits. `inbox archive <id>` maps to a `resolved` PATCH with `resolved_action=archived`; only non-decision kinds (messages, failed-run notices, advisories) archive — the server `409`s an archive on a source-managed waitpoint/escalation whose source is still live.

`read` and `unread` are **per user**: the server computes `state` for the caller from `inbox_item_reads`, so marking a role-targeted item read clears it from your feed and nobody else's, and `unread` only drops your own marker. `resolve` and `archive` are workspace-shared — one decision closes the row for everyone. `inbox list` and `inbox get` print the state the server computed for you; the CLI never assumes it locally.

On a `waitpoint` or `escalation`, `inbox get` also reports whether the record that would decide it still exists — `source_missing` in `--format json`, and one line in the human view before the body:

```text
source live · decide it at the source (`crewship inbox resolve` answers 409 and prints the command)
source gone · nothing left to decide this — `crewship inbox resolve ibx_01HVZ...` dismisses it
```

`false` means a pending waitpoint token, a `PENDING_REVIEW` hire or a pending approval still backs the row, and `inbox resolve` will be refused; `true` means the source was pruned and the row may be dismissed from the inbox. The field is present only on `get` (never on `list`) and only for those two kinds; absent means the server did not probe, not that the source is live.

`--format json` on either `list` or `get` also carries the §12 attention contract where a producer has adopted it (work package B10): `thread_key` (the server-side merge key — two producers describing the same recurring condition collapse onto one row instead of the client stitching them together), `attention_class` (`decision` \| `input` \| `review` \| `repair`), and `actions` (`[{"id", "label", "effect", "irreversible"}, ...]`, unioned across every producer that merged into the row). All three are omitted for a kind that has not adopted the contract yet — script against `payload` for those, same as before.

On a `CREDENTIAL` escalation, `inbox get` also prints whether resolving it needs a **second approver**, and which of the two controls demands it:

```text
2nd approver required · workspace policy + L4 · critical credentials
whoever owns nela cannot resolve it — someone else has to
```

The same answer rides the JSON as `second_approver_required` / `second_approver_by_workspace` / `second_approver_by_tier` / `security_level_label`, the fields the crew escalations list carries. It is computed **when you read the row**, not when the escalation was raised: the workspace toggle and the credential's tier both change afterwards. Absent means the server said nothing, not that a single approver will do — see [Keeper → The switch is a floor, not a master switch](/guides/keeper#the-switch-is-a-floor-not-a-master-switch).

`resolve` is the inbox-side only — it does **not** call the source endpoint. To actually approve a waitpoint through to the executor, use `crewship routine waitpoints approve <token>` (`crewship approvals approve` is a different queue — approval requests, `apr_…` ids — and does not decide waitpoints). To resolve an escalation lifecycle, use `crewship escalation resolve <id>`. The inbox row tracks the decision; the source endpoint enacts it.

### Bulk operations

```bash
# Mark a known set
crewship inbox bulk read --ids inbox_abc,inbox_def,inbox_ghi

# Wipe the unread queue (capped at 500 per call)
crewship inbox bulk read --all-unread

# Bulk-resolve with an action tag
crewship inbox bulk resolve --ids inbox_abc,inbox_def --action acknowledged
```

Bulk operations submit the whole id set to the server-side [`POST /api/v1/inbox/bulk`](/api-reference/inbox#post-/api/v1/inbox/bulk) endpoint (one request flips many rows), chunked at 500 ids per call — the endpoint's id cap. On a `resolve` the server **skips** decision items (source-managed waitpoints/escalations and blocking rows) rather than closing them. The final line summarises the aggregated counts:

```
N updated · M skipped · K not found
```

A stale or already-resolved id lands in `not found` / `skipped`; it does not fail the command (the process exits `0`). Only a transport error or a non-2xx bulk response exits non-zero.

If `--all-unread` returns exactly the page cap (500), the CLI refuses to proceed and changes nothing, telling you to re-run after the batch or narrow with `--ids`, so the tail isn't lost.

## Sources

| Kind | Created by |
| --- | --- |
| `waitpoint` | Waitpoint creation (mission step paused for human input). |
| `escalation` | Agent escalation (agent asked for help). |
| `failed_run` | Run-failure handler when a run exits non-zero. |
| `message` | A routine's `notify` step, or an agent addressing a human directly (e.g. a hire request). |

The inbox is *human-attention-scoped*: it holds the things somebody has to look at, not every event that happened. Where those items are delivered outward — email, webhook, chat, push — is `crewship notifychannel`.

## Common errors

- **`either --ids <csv> or --all-unread is required`** — bulk command needs one of them.
- **`--ids and --all-unread are mutually exclusive`** — pick one.
- **`--ids parsed to empty list (got "")`** — comma-string was blank after trimming.
- **`hit the 500 unread-item page cap; no items were changed …  pass --ids to target a specific subset`** — `--all-unread` returned a full page and can't tell whether more remain, so it changes nothing. Re-run after clearing this batch, or target explicit `--ids`.
