# crewship audit

Surface the workspace audit log from the terminal. Filters mirror the `/api/v1/audit` query params 1:1 — the same expressiveness as the admin UI's filter chips. Names are kept identical to the UI fields so a user clicking through the dashboard can reproduce the same view from the CLI by reading the URL bar.

```bash
crewship audit [flags]
```

Requires an authenticated session (`requireAuth`) and a selected workspace (`requireWorkspace`).

`--action` values are intentionally not enumerated in the help text. The audit table stores domain verbs (`agent.run`, `workspace.create`, `credential.rotate`, `backup.export`, …) that grow over time; listing a stale "create/update/delete" trio in the help would misdirect users. Pointing at the server-side enum is more honest.

## Flags

| Flag | Default | Purpose |
| --- | --- | --- |
| `--source <trail>` | `workspace` | Which trail to read: `workspace` (settings, people, crews, credentials), `crews` (cross-crew dispatch and messages), `credentials` (secret use), `keeper` (gatekeeper decisions, append-only). The filters below apply to `workspace` only. |
| `--action <verb>` | `""` | Domain verb (`agent.run`, `workspace.create`, `credential.rotate`, …). |
| `--entity-type <kind>` | `""` | Entity kind (`AGENT`, `BACKUP`, `CREDENTIAL`, `CREW`, `USER`, …). |
| `--entity-id <id>` | `""` | Narrow to a specific entity row (e.g. an agent ID). |
| `--user <user-id>` | `""` | Filter by the user ID who performed the action. |
| `--since <when>` | `""` | Start of date range. RFC3339 (`2026-05-01T00:00:00Z`) or duration sugar (`1h`, `24h`, `7d`). |
| `--until <when>` | `""` | End of date range. Same syntax as `--since`. |
| `--search <text>` | `""` | Free-text search across `action`, `entity_type`, and the user's email/name. |
| `--page <n>` | `0` | 1-based page number for pagination. `0` means "no page param sent". |
| `--lines <n>` | `50` | Entries per page. Server caps at 100. |

The global `--format` flag (`table` / `json` / `yaml` / `ndjson` / `quiet`) is honoured by the underlying formatter.

## Output

Default table columns:

| TIME | ACTION | ENTITY | ENTITY_ID | USER |
| --- | --- | --- | --- | --- |
| `2026-05-19 14:02:11` | `agent.run` | `AGENT` | `a_abc123def4` | `petra@acme-engineering.com` |
| `2026-05-19 14:01:48` | `credential.rotate` | `CREDENTIAL` | `c_xyz789ghi0` | `pavel@acme-engineering.com` |

Entity IDs are truncated to 12 characters in the table view; switch to `--format json` to see the full ID and additional fields.

## Examples

### Latest 50 entries

```bash
crewship audit
```

### Find every agent run in the last day

```bash
crewship audit --action agent.run --since 24h --lines 100
```

### Credential changes only

```bash
crewship audit --entity-type CREDENTIAL --since 7d
```

### Who rotated which credential

```bash
crewship audit --search rotate --until 2026-05-01T00:00:00Z
```

`--search` matches across `action`, `entity_type`, and the user's email/name, so this catches both `credential.rotate` events and any `rotation`-tagged automation.

### Activity for one user

```bash
crewship audit --user u_abc123 --page 2 --lines 100
```

### One specific entity's full history

```bash
crewship audit --entity-type AGENT --entity-id a_xyz789ghi0 --since 30d
```

### Pipe to jq

```bash
crewship audit --action workspace.create --format json | jq '.[].user_email'
```

## `crewship audit head`

Inspect the current chain tail before deciding whether to start a new segment:

```bash
crewship audit head --scope workspace --format json
crewship audit head --scope instance --format json
```

`--scope` defaults to `workspace`. Workspace scope uses the selected workspace;
instance scope does not require one. The authenticated
`GET /api/v1/admin/audit/head` uses the same current OWNER and token-scope checks
as reseal. Request query parameters: `scope` is `workspace` or `instance`;
`workspace_id` is required for workspace scope and omitted for instance scope.
Response: `tail_seq` and `tail_hash`, or zero and an empty hash when
there are no chained rows. This is a read of stored state, not an integrity
verdict or approval of recovery. Inspect the alert and history separately.
Statuses: 200 for a successful read, 400 for invalid scope parameters, 401 for
missing authentication, 403 for insufficient OWNER authority, 404 for a
restricted account, and 500 for a database failure.

## `crewship audit reseal`

After investigating a missing audit key or an integrity alert, the current
OWNER can explicitly start a new audit segment. This preserves historical rows
and their MACs; it does not repair or authenticate unverifiable history.

```bash
crewship audit reseal --scope workspace --expected-tail-seq 42 --expected-tail-hash <reviewed-tail-hash> --reason "Approved recovery after loss of the historical signing key"
crewship audit reseal --scope instance --expected-tail-seq 42 --expected-tail-hash <reviewed-tail-hash> --reason "Approved instance recovery after historical key loss"
```

Use the independently inspected current tail from `audit head`, rather than
copying these example values. A scope with no chained rows uses sequence `0`
and an empty hash; legacy
unchained rows still remain unverified. The command never discovers and accepts
a newer tail automatically. A concurrent append returns 409 and requires a new
inspection.

| Flag | Default | Purpose |
| --- | --- | --- |
| `--scope` | `workspace` | `workspace` or `instance`; instance scope needs no selected workspace. |
| `--expected-tail-seq` | `-1` | Required, explicitly reviewed current chain sequence, at least zero. |
| `--expected-tail-hash` | `""` | Exact current tail hash; required for a positive sequence. |
| `--reason` | `""` | Required explanation, trimmed to 8–512 UTF-8 bytes. |

The authenticated `POST /api/v1/admin/audit/reseal` requires a current trusted
workspace OWNER and `workspace:admin`, or the configured instance OWNER and
`instance:admin`. Instance ADMIN alone is insufficient. Suspended accounts and
accounts restricted in any workspace cannot reseal. Authority and the reviewed
tail are checked again inside the write transaction. Invalid bodies return 400,
insufficient authority 403, and restricted accounts 404.

Request body: a JSON object containing `scope`, `expected_tail_seq`,
`expected_tail_hash` and `reason`, plus `workspace_id` only for workspace
scope. Both tail fields must be explicitly present, including sequence zero
and an empty hash for a scope with no chained rows. Unknown fields and JSON
null tail values are rejected; the body is limited to 4096 bytes.

The response identifies the committed checkpoint, its new tail and
`historical_status`. `continuation_verified` describes the new segment only.
Historical status remains `historical_unverified` or `historical_invalid` when
the old history cannot be verified; this is not a clean whole-history verdict.
The checkpoint and its exact old-tail acknowledgement commit together;
failure rolls both back. No key material is sent through this command.

## Common errors

- **`bad --since: …`** / **`bad --until: …`** — the value is neither RFC3339 nor a duration. Accept formats: `2026-05-01T00:00:00Z`, `1h`, `24h`, `7d`.
- HTTP `403 Forbidden` (surfaced as a generic CLI error) — audit reads are restricted to OWNER / ADMIN by default. Ask an owner to grant access or check your role with `crewship whoami`.
