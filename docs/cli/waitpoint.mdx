# crewship routine waitpoints

Waitpoints are HITL pauses created by a routine `wait` step of
`kind: approval`. A parked run resumes when a human approves or rejects the
waitpoint, or ends when its timeout elapses.

```bash
crewship routine waitpoints <subcommand> [flags]
```

The `pipeline` alias works in place of `routine`.

## Subcommands

| Command | API behavior |
|---|---|
| `list` | `GET /api/v1/workspaces/{workspace}/pipelines/waitpoints`; lists pending waitpoints. |
| `show <id>` | Reads the pending list and prints full prompt and metadata for the public waitpoint ID. |
| `approve <id>` | `POST /api/v1/workspaces/{workspace}/pipelines/waitpoints/{id}/approve` with `approved: true`. |
| `callback-url <id>` | Mint a new external completion URL for a pending waitpoint. |
| `reject <id>` | The same endpoint with `approved: false`. |

### `list`

```bash
crewship routine waitpoints list
crewship routine waitpoints list --format json
```

Human output columns are `TOKEN RUN ID STEP KIND CREATED TIMEOUT PROMPT`.
The TOKEN column shows a public `wp_` waitpoint ID. You can use it with
`show`, `approve` or `reject`. The human table shortens the run ID. An empty
pending list prints `No pending waitpoints.` or `[]` in JSON mode.
`--json` is a deprecated alias for `--format json`. YAML and NDJSON are also supported.

### `show <id>`

```bash
crewship routine waitpoints show wp_069f7add83c04c7bbc306f8c8bb85c10
```

Prints the public ID, run, step, kind, timestamps and full prompt. A missing,
expired or decided ID returns a not-found error. Typed decision forms and their
Inbox card IDs appear in JSON output. Make the decision through the authenticated
route or Inbox.

### `callback-url <id>`

A workspace manager can mint a callback URL on demand for an eligible pending
waitpoint. The CLI displays the secret once. Minting a replacement invalidates
the previous URL. Store the URL in your integration's secret store and keep
it out of logs and messages. Typed decision forms require an authenticated
decision.

When upgrading from a version that used the ID as a callback secret, stop the
old service before starting the new one. Start one new instance on the database
and let the ID migration finish before serving traffic. Existing pending
waitpoints retain their status, but all pre-upgrade callback URLs expire.
List pending waitpoints and mint and distribute new URLs for the integrations
that still need them.

### `approve` and `reject`

```bash
crewship routine waitpoints approve wp_069f7add83c04c7bbc306f8c8bb85c10 --comment "LGTM"
crewship routine waitpoints reject wp_069f7add83c04c7bbc306f8c8bb85c10 --comment "Needs revision"
```

Both commands accept `--comment` (default empty). The comment is forwarded to
the parked run as the wait step's output; rejection additionally carries the
rejection signal. Human output is `Approved waitpoint <short-token>.` or
`Rejected waitpoint <short-token>.` Decisions require authentication and a
workspace and return the server's Problem Details error for an invalid or
already-resolved token.

The decision is attributed to the person whose CLI token made it. An agent
cannot decide a waitpoint: a call made with an agent's internal token is
refused (`401` before the route; `403` with
`reason: waitpoint_decider_not_allowed` from the resolve door if it ever got
that far), the waitpoint stays pending, and the attempt is listed by
`crewship audit --action waitpoint.decision_refused`. Full rule:
[Waitpoints → Who may decide](/api-reference/waitpoints#who-may-decide).
