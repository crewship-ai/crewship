# crewship admin

`cmd/crewship/cmd_admin.go` exposes the **operator-on-the-host recovery surface**. The write subcommands under `admin` open the SQLite database file on this machine directly (no HTTP, no auth token) — the server doesn't even need to be running. Use these when a user is locked out of the UI.

The "credential" for those commands is **shell access to the host**. That matches what GitLab (`gitlab-rake gitlab:password:reset`), Gitea (`gitea admin user change-password`), Nextcloud (`occ user:resetpassword`), and Mattermost (`mmctl user change-password`) all do — if you can SSH to the box, you ARE the admin.

```bash
crewship admin <subcommand> [flags]
```

## Which database am I talking to?

`admin list-users` reads the **server** the CLI targets. Everything else in
the local-only group reads or writes the **database file on this host**.

Those are two different things, and until [#2086](https://github.com/crewship-ai/crewship/issues/2086)
the CLI conflated them: it resolved `~/.crewship/crewship.db` and ignored
`--server` / `CREWSHIP_SERVER` / `--profile` entirely, so pointing the CLI at
a populated server and running `admin list-users` printed

```
EMAIL  NAME  CREATED  LOCKED  FAILS  ROLES
(no users — run `crewship seed` or hit POST /api/v1/bootstrap)
```

and exited **0**.

The rule now:

- **`list-users` uses `GET /api/v1/admin/users`** on the targeted server:
  the current workspace's members, or every account for the instance owner. It needs a login — **always**, not only when
  something names a server. It is the one verb here that is not gated: it
  branches on `--local` alone, so on a host with no CLI config and no
  `CREWSHIP_SERVER` it still goes to the server and still fails with "not
  logged in", where the pre-#2086 build printed the table. Deliberate — a
  fallback to the local file on a failed login would answer the server's
  question from a file that may belong to another instance. `--local` is the
  old behaviour, asked for explicitly, and both failure paths say so.
- **Every other local-only subcommand refuses to run when a server is named**,
  unless you pass `--local`. The refusal names the server, names the file it
  would otherwise have touched, and names the flag. With nothing naming a
  server they run unchanged.
- **A server on `localhost` is not an exemption.** crewshipd routinely runs
  with its own `DATABASE_URL` — every dev clone uses `file:./crewship.db` —
  so "same host" tells you nothing about "same database".

```bash
# You mean the file on this host. Say so.
crewship admin reset-password --email admin@example.com --local

# Instance-wide user list with the lockout columns, read from the file.
crewship admin list-users --local
```

<Note>
  **The credential for the local-only commands is shell access to the host** —
  there is no `crewship login` token. Requirements:

  - Read+write access to the database file: `DATABASE_URL` when set, otherwise
    `<data dir>/crewship.db` (default `~/.crewship`).
  - The `crewship` binary must run on the **same host** as that file.
  - The host's filesystem permissions are the authentication.

  `--local` is what tells the CLI you mean that file rather than the server it
  is configured for. Every command prints the path it resolved.
</Note>

| Flag | Applies to | Description |
|---|---|---|
| `--local` | every `admin` subcommand (persistent) | Act on the database file on this host, not the server the CLI targets. |

## `crewship admin reencrypt`

Re-encrypt stored secret envelopes to the server's current master-key version.
This is the server-side step after configuring a new key version; the command
requires authentication, an active workspace, and a running server.

```bash
crewship admin reencrypt
crewship admin reencrypt --format json | jq .failed
```

The operation is idempotent: envelopes already at the current version are
skipped. Human output reports the target `key_version`, totals for
`Re-encrypted`, `Skipped`, and `Failed`, followed by per-table/per-column
counts when present. JSON output contains `key_version`, `reencrypted`,
`skipped`, `failed`, and `columns`. A non-zero exit means at least one value
could not be decrypted with the configured keys; do not retire the old key.

## `crewship admin reset-password`

Rotate a user's password.

<Warning>
  The hashed value is written into `users.hashed_password`, the brute-force
  lockout state is cleared (`failed_login_count=0`, `locked_until=NULL`), and
  every active session row for that user is revoked as a side effect (the audit
  trail records `revoked_reason='password_change'`).
</Warning>

```bash
# Interactive: stdin prompt with hidden input (no shell-history leak)
crewship admin reset-password --email admin@example.com --local

# Scripted: pipe the new password on stdin (CI-friendly)
echo 's3cret!' | crewship admin reset-password --email admin@example.com --password-stdin --local

# Argv (NOT recommended — visible in shell history and ps output)
crewship admin reset-password --email admin@example.com --password 's3cret!' --local
```

| Flag | Required | Description |
|---|---|---|
| `--email` | yes | Email of the user to reset. Normalised lowercase. |
| `--password` | no | New password as argv. Leaks to shell history; avoid in CI. |
| `--password-stdin` | no | Read the new password from stdin. Mutually exclusive with `--password`. |

<Tip>
  Omit both `--password` and `--password-stdin` to get an interactive prompt
  with hidden input — the right default for ad-hoc recovery from a host
  shell, and the only form that never leaks to shell history or `ps`.
</Tip>

## `crewship admin list-users`

Two different answers, deliberately:

**Default — the server.** `GET /api/v1/admin/users` on the server the CLI
targets (ADMIN+): the members of the current workspace, or — for an instance
administrator — every account on the instance. Columns: EMAIL, NAME, CREATED, ROLE
(`role@workspace-slug`, comma-joined), LAST ACTIVE, SESSIONS (signed-in
devices), LOCKED (`until …` while a lockout is in force). Requires a login.

**`--local` — the database file on this host.** Every row in `users` ordered
by `created_at ASC`, across every workspace. Columns: EMAIL, NAME, CREATED,
LOCKED (derived from `locked_until`), FAILS (`failed_login_count`), ROLES
(`role@workspace-slug`, comma-joined across workspaces). Needs no server —
the path for when the server or the login is what is broken.

```bash
crewship admin list-users                        # the server
crewship admin list-users --locked-only          # who is stuck?
crewship admin list-users --local                # this host's database file
```

| Flag | Default | Description |
|---|---|---|
| `--locked-only` | `false` | Keep only accounts under a sign-in lockout. Works over HTTP and with `--local`. Against a server too old to return lockout state the command exits 2 and says so, rather than printing "no locked-out users" for a workspace full of them. |
| `--local` | `false` | Read the database file on this host instead of the server. |

To lift a lock from the terminal: `crewship admin user unlock <email>` (over
HTTP), or `reset-password --local` on the database host.

Notes go to **stderr**: which people the list covers on the server path, and
the "which database" note on the `--local` path. Stdout carries the table and
nothing else, so `crewship admin list-users | awk 'NR>1 {print $1}'` yields
addresses.

That holds for an empty workspace too: stdout is the header row alone and
`(no users in this workspace)` is printed on stderr, so the same pipe yields
nothing rather than a line of prose. (The `--local` listing keeps its own
`(no users — run 'crewship seed' …)` on stdout — it is the example output
shown in the [admin CLI guide](/guides/admin-cli).)

## `crewship admin promote`

Grant a workspace role to an existing user. Roles ascend `VIEWER` < `MEMBER` < `MANAGER` < `ADMIN` < `OWNER`; the command updates the user's existing row in `workspace_members` (the user must already be a member — a non-member errors with `user is not a member of workspace`).

```bash
crewship admin promote --email admin@example.com --role OWNER --local
crewship admin promote --email lead@example.com --role ADMIN --workspace acme --local
```

This is not a duplicate of `crewship workspace member role`, which is the
server-side way to do the same thing. That path enforces the role ladder
against *your* role and needs a session — so it cannot mint the first OWNER,
and it is unavailable to the operator who is locked out. When the CLI names a
server, `admin promote` refuses and points at both options.

| Flag | Required | Description |
|---|---|---|
| `--email` | yes | Email of the user to promote. |
| `--role` | yes | Target role — exactly one of `OWNER`, `ADMIN`, `MANAGER`, `MEMBER`, `VIEWER` (case-insensitive). |
| `--workspace` | no | Workspace slug. Defaults to the user's only workspace **when they have exactly one** — when ambiguous the command errors and asks you to pick. |

This is the post-`init` step for bootstrapping a second admin: the first user from `crewship init` is `OWNER` automatically; everyone else starts as a regular member and needs `admin promote` to gain elevated access without going through the UI.

## `crewship admin invalidate-sessions`

Force-logout every active session for one user **without** changing their password. The user can still sign in normally afterwards — they just have to re-authenticate on every device they were already on.

```bash
crewship admin invalidate-sessions --email user@example.com --local
```

| Flag | Required | Description |
|---|---|---|
| `--email` | yes | Email of the user whose sessions to revoke. |

Each revoked row is stamped `revoked_reason='admin_invalidate'` so the audit trail distinguishes this from the side-effect revokes that fire during `reset-password` (those carry `revoked_reason='password_change'`).

<Accordion title="When to reach for this instead of reset-password">
  - Laptop stolen / recovered, the password is believed safe but a cached cookie might still be on the device.
  - Suspected token leak via Slack screenshot, browser history dump, etc.
  - Periodic compliance sweep — "log everyone out of yesterday's sessions".
</Accordion>

## `crewship admin sessions list`

Forensic read of `user_sessions` for one user — mirrors [`crewship session list`](/cli/session) but for **arbitrary** users (the user-side command is self-only). Admin-only via direct DB access.

```bash
crewship admin sessions list --email user@example.com --local
crewship admin sessions list --email user@example.com --active-only --local
crewship admin sessions list --email user@example.com --limit 200 --local
```

| Flag | Required | Default | Description |
|---|---|---|---|
| `--email` | yes | | Email of the user whose sessions to list. |
| `--active-only` | no | `false` | Filter to non-revoked, non-expired rows (matches what `crewship session list` shows the user themselves). |
| `--limit` | no | `50` | Row cap. Useful for users with hundreds of historic sessions. |
| `--local` | when a server is named | `false` | Read the database file on this host. There is no HTTP route for this: an endpoint that enumerates any user's session inventory would be a new surface on the exact table an attacker wants, and this command's audience already has shell access. |

Output columns: ID, STATUS (derived from `revoked_at` + `expires_at`; revoked rows show `revoked:<reason>`), CREATED, LAST USED (`last_used_at`), EXPIRES, IP, UA (`user_agent`). Sorted `created_at DESC`. A typo'd email reports `no user with email <addr>` rather than silently returning zero rows.

Pair with `admin invalidate-sessions` to act on what `sessions list` surfaces.

## `crewship admin prune-legacy`

Removes orphaned **pre-C1 (slug-only) crew docker resources** — volumes and
containers named `<prefix>-{home,tools,team}-<slug>` (e.g.
`crewship-3-tools-engineering`) left over from before the C1 naming change
(2026-06 audit, which re-keyed crew resources to include the crew id).

```bash
crewship admin prune-legacy
```

<Warning>
  **Unlike the rest of `crewship admin`, this command is HTTP-backed.** The
  docker daemon lives behind the running server, not the local SQLite DB, so
  this command needs a reachable server and an authenticated session
  (`crewship login`) — it is **not** a host-only recovery command. It is filed
  here because it is an operator/admin maintenance action.
</Warning>

### Why this exists

A legacy slug-only volume **survives `crewship seed --nuke`**: the nuke clears
the database, and crew teardown removes the *id-scoped* volumes — but never the
orphaned slug-only ones, because no crew row references them. While they exist,
the runtime's legacy-resource guard refuses to start the crew's container, and
the failure reaches users only as a generic **"failed to start agent
container"**. Every agent in the affected crew fails; a `seed --smoke-test`
reports `N/N agents failed`.

`crewship doctor` surfaces this proactively: the `legacy crew resources` check
calls the authenticated `GET /api/v1/admin/legacy-resources` endpoint and
**WARN**s with this command as the remediation when orphaned resources are
present. (Detection runs on this admin endpoint, not on the unauthenticated
`/healthz` hot path, so a slow docker daemon can never stall health probes.)

The prune is **instance-wide**: legacy docker names carry no workspace or crew
id, so detection (what `crewship doctor` surfaces) and prune enumerate the same
full crew set — otherwise the doctor could WARN on a slug the prune can never
reach. It removes **only** the orphaned legacy names; the id-scoped resources
the live runtime uses are excluded (slug/id-collision safe) and never touched.
It reports each resource removed:

```text
Removed 4 legacy resource(s):
  - crewship-3-tools-engineering
  - crewship-3-home-engineering
  - crewship-3-tools-quality
  - crewship-3-home-quality
```

Requires the `OWNER` or `ADMIN` role. Returns `503` when the server's container
provider is not docker (nothing to prune).

## `crewship admin reap-orphan-containers`

Finds — and, with `--apply`, reaps — **crew containers orphaned by an
internal-token master rotation**. When crewshipd restarts with a *different*
internal-token master while a per-crew agent container survives, that container
keeps the crew-bound token (`crwv1.<ws>.<crew>.<mac>`) it was minted with, and
the new process rejects it forever:

```text
WARN internal API auth failed: invalid crew-bound token  path=/api/v1/internal/credentials
```

The container's credential sync is silently and permanently broken while
`docker ps` still shows it "healthy", and it re-emits the warning every reap
interval (log-noise that drowns real signal). This command clears those
orphans.

```bash
crewship admin reap-orphan-containers            # dry-run: report only
crewship admin reap-orphan-containers --apply     # stop + remove the orphans
```

<Warning>
  **HTTP-backed**, like `prune-legacy`: the docker daemon lives behind the
  running server, so this needs a reachable server and an authenticated session
  (`crewship login`). **Dry-run by default** — nothing is removed unless you
  pass `--apply`.
</Warning>

### Reading the result: "none found" vs "could not tell"

The detector compares the token fingerprint a container's sidecar advertises on
`/health` against the one the server would mint for that crew today. It **fails
safe**: a container that advertises *no* fingerprint is never classified as an
orphan, so a reap only ever removes something positively proven stale.

That safety has a corollary — a sidecar too old to advertise `token_fp` at all
makes the detector **structurally unable to find anything**, while still
reporting zero orphans. So the sweep also reports its own coverage:

```console
# Detector worked, genuinely nothing stale
No orphaned crew containers found — 2 of 2 inspected container(s) reported a token fingerprint and matched.

# Detector could not look — "no orphans" here means "could not tell"
DETECTOR INERT — inspected 3 running crew container(s), but NONE advertised a token fingerprint.

# Nothing to look at — no crew container was running at all
No running crew containers to inspect — nothing to reap.
```

The third line is a **third state, not a variant of the first**. It is what you
get on a workspace whose crews are all idle (and on a CI runner that has a
docker daemon but never started a crew container): the sweep is clean in the
sense that nothing was reaped, but it says nothing about whether the classifier
would have got the answer right, because it never classified anything.

An inert detector is a **deploy defect, not a workspace condition**: the slot's
sidecar binary was never re-pointed to the freshly built artifact on reconcile
([#1390](https://github.com/crewship-ai/crewship/issues/1390)). Fix the slot's
sidecar, then re-run. Partial coverage (some sidecars silent) is reported as a
count rather than rounded away.

`--format json` carries `inspected`, `identified` and `detector_inert`. A server
predating these fields omits them, and the CLI then falls back to the older,
non-committal wording rather than inferring a coverage figure it wasn't given.

### One-time step after upgrading to the stable-master build

The [stable internal-token master](/api-reference/internal#authentication)
(#1385) stops *future* restarts from ever orphaning a container. But the
**deploy that first introduces it rotates the master once** — from the old
per-boot random to the value derived from `ENCRYPTION_KEY`. Any container that
outlived that one deploy is orphaned exactly once and does not self-heal.

After rolling out the new build, do **one** of:

- **Recreate the surviving containers** — a normal redeploy / crew re-dispatch
  starts a fresh container that re-mints a valid token; or
- **Run `crewship admin reap-orphan-containers --apply`** to stop+remove just
  the orphaned ones (the next dispatch to each crew recreates them fresh).

From then on the master is stable and no further action is needed unless you
deliberately rotate `CREWSHIP_INTERNAL_TOKEN` or the `ENCRYPTION_KEY` it derives
from.

### How detection stays safe

For each of the workspace's crews the command probes the running container's
sidecar `/health` for the token fingerprint it advertises (`token_fp`, #1385)
and compares it against the fingerprint of the token the server would mint
**today**. A container is listed **only** on a definite, non-empty mismatch —
an unreachable sidecar, a pre-#1385 sidecar that reports no fingerprint, or an
unconfigured master are all treated as *unknown* and are **never** reaped. A
healthy container is never touched. Any agent inside an orphaned container is
already broken (its credentials can't sync), so recreation restores it rather
than interrupting healthy work.

Dry-run prints the orphans it found; `--apply` reports what it reaped:

```text
Found 2 orphaned crew container(s):
  - crew engineering (c-eng) container 3f9a… — reaped
  - crew quality (c-qua) container 71b2… — reaped
```

Requires the `OWNER` or `ADMIN` role. Returns `503` when the server's container
provider is not docker.

## `crewship admin health`

```bash
crewship admin health
crewship admin health --format json | jq '.disk.used_pct'
```

```
CHECK           STATE
Uptime          23m
Database        connected
Disk            70% used · 62.1 GB free of 206.9 GB (/home/ubuntu/.crewship)
Log level       debug
Encryption key  external — injected by the operator's environment
```

**Disk** is the data directory's volume — the one that fills in practice, since
the database, agent outputs and logs all live under it. Where the platform
cannot measure it, the row says so rather than printing a zero.

**Encryption key** reports where `ENCRYPTION_KEY` came from. `generated` means
Crewship auto-created it into `<dataDir>/secrets.env`, next to the database it
protects — so a copied disk, a restored snapshot or a stray backup carries the
ciphertext *and* what opens it. `external` means the operator injected it.

**Log level** shows the live level, and says `(temporary)` when a timed
override is in effect — a level that reverts on its own is a different fact
from one someone set for good.

## `crewship admin workspaces`

```bash
crewship admin workspaces
crewship admin workspaces --format json | jq '.[0]._count_agents'
```

```
NAME    SLUG  MEMBERS  AGENTS  CREWS  RUNS 7D  SPEND 30D  LAST ACTIVITY         CREATED
Acme *  acme  3        8       2      41       $18.42     2026-09-29 08:12 UTC  2026-01-01T00:00:00Z
```

`GET /api/v1/admin/workspaces`. A workspace ADMIN or OWNER gets one row, the
workspace the CLI is authenticated against. An instance administrator (see
`crewship admin instance`) gets every workspace on the instance; `*` marks the current one. RUNS 7D counts runs started in the

LAST ACTIVITY is the newest audit-log entry. A server older than those fields
prints `-` for them.

Requires `OWNER` or `ADMIN` (`canRole "manage"`).

## `crewship admin user`

Per-person actions on the server the CLI targets. People are named by email;
the id is resolved through `GET /api/v1/admin/users`, so you can act on the
members of your current workspace, or on any account if you are an instance
administrator. An ADMIN cannot act on an OWNER.

```bash
crewship admin user sessions jana@example.com
crewship admin user revoke-session jana@example.com <session-id>
crewship admin user sign-out jana@example.com
crewship admin user unlock jana@example.com
```

| Command | Endpoint | What it does |
|---|---|---|
| `user sessions <email>` | `GET /api/v1/admin/users/{userId}/sessions` | Lists signed-in devices (device, IP, last use; `*` marks your own) and live CLI tokens (name, scopes, last use — never the secret). `--format json` returns the endpoint's body. |
| `user revoke-session <email> <session-id>` | `POST /api/v1/admin/users/{userId}/sessions/{sessionId}/revoke` | Signs the person out of one device. |
| `user sign-out <email>` | `POST /api/v1/admin/users/{userId}/sessions/revoke-all` | Signs the person out of every device. The password and CLI tokens are untouched. |
| `user unlock <email>` | `POST /api/v1/admin/users/{userId}/unlock` | Lifts a sign-in lockout and resets the failed-attempt counter. |

The host-side `invalidate-sessions` and `sessions list` stay for when the
server or the login is what is broken; these are the same actions over HTTP,
for an admin who is signed in. Every action writes an audit-log entry.

## `crewship admin instance`

What an instance administrator does across the whole server. People are named
by email and workspaces by slug. Only an **instance administrator** may run
these: `CREWSHIP_OWNER_EMAIL` on the server, or anyone named with `add-admin`.
An install that names nobody names the owners of its oldest workspace once,
the first time it is asked, and never again. Being ADMIN or OWNER of a
workspace is not enough. Every action is recorded in the instance audit. The
last active instance administrator cannot be removed or suspended. These

### backups run

`POST /api/v1/admin/instance/backups/run`. Starts a backup now in the
server's backup service (never through an agent). The server answers with the
run id at once and finishes the backup on its own, so the CLI's timeout
cannot cancel it; `--wait` follows every run it started to the end and prints
what each wrote (with `--format json`, a list of runs in the shape of
`backups runs`).

With `--plan` it runs that plan. Otherwise `--scope instance` writes one
instance bundle — the whole database, every file store and every crew
container, copied in one quiet window: running work is drained first, writes
are held for the copy only and released before packing — and
`--scope workspaces` writes one bundle per workspace, narrowed by
`--workspace`, with `--preset` and `--contents` choosing what goes in.

Every backup is encrypted: `--recipient` (repeatable) or `--passphrase-file`,
not both. Without either, the recipients come from the plan that covers the
same scope. The passphrase is held in the server's memory until the run
starts and is never stored.

```bash
crewship admin instance backups run --plan bp_… --note "before upgrade"
crewship admin instance backups run --scope instance --recipient age1q7x…m3k --wait
crewship admin instance backups run --scope workspaces --workspace lab --preset custom --contents memory
```

| Flag | Required | Description |
|---|---|---|
| `--plan` | no | Run this plan now. |
| `--scope` | no | `instance` or `workspaces`. |
| `--workspace` | no | With `--scope workspaces`: workspace slugs or ids. Every workspace by default. |
| `--preset` | no | `complete`, `workspace` or `custom`. |
| `--contents` | no | A custom run's categories. |
| `--env-mode` | no | `files` or `complete`. |
| `--recipient` | no | Encrypt to these age public keys (`age1…`) or recipient ids; repeatable. The covering plan's by default. |
| `--passphrase-file` | no | Encrypt with the passphrase in this file instead of recipients. |
| `--note` | no | A note shown with the run, such as "before upgrade". |
| `--wait` | no | Wait for the runs to finish and print what they wrote. Exits non-zero when one failed, was interrupted or was skipped. |
| `--timeout` | no | With `--wait`: how long to wait, 3h by default. |

## `crewship admin gdpr`

Answers the two requests a person can make about their own data.

```bash
# Right of access — everything this workspace holds about them
crewship admin gdpr export someone@example.com
crewship admin gdpr export someone@example.com --out subject-access.json

# Right to erasure — irreversible (`erase` is an alias of `delete`)
crewship admin gdpr delete someone@example.com --reason "SAR #1234" --yes
crewship admin gdpr erase  someone@example.com --reason "SAR #1234" --yes
```

Either a user id or an **email** is accepted; the email is resolved against the
workspace roster, because an operator holding a request from a person has their
address, not their cuid.

`--reason` is not paperwork. It is the audit trail, and it is what answers "why
was this person's data removed" a year later — so `delete` refuses without it,
and refuses again without `--yes`. Both commands write an append-only row and
return an **action id**: that id is the receipt for the request you were
answering, so record it against the request.

`export` writes to stdout by default (pipe it, redirect it); `--out` writes a
file with `0600`, since the file is every row about a person.

`delete` prints a per-table breakdown under the row total, and the labels carry
the **verb**, because the erasure does two different things:

```
✓ Erased 151 rows. Audit action: gdpr_act_…
  approvals_queue              2
  inbox_item_reads             9
  inbox_items                  4
  memory_versions              117
  page_grants_removed          3
  page_public_tokens_revoked   1
  page_versions_anonymised     12
  pages_transferred            1
  peer_cards                   23
  user_models                  1
```

*Anonymised* rows kept their content and lost the subject's name (a page version
is still there to roll back to); *removed* / *revoked* rows are gone, and any
capability they carried — a grant, a public `/p/{token}` link, an inbound webhook
token — stops working immediately. Only the second kind is counted in the row
total. `inbox_item_reads` is the subject's own read markers on this workspace's
inbox items — activity, not items about them. What the erasure promises, and the
accountability records it deliberately leaves behind, are in [GDPR](/security/gdpr).

An erasure that only partly happened — one table refused or a disk copy could
not be removed — comes back as `207 Multi-Status`. The receipt is still printed,
but the command **exits non-zero** with `erasure incomplete: <first error>` and
the audit action id, so a scripted SAR queue cannot record it as done; re-run
after fixing the cause (the cascade is idempotent, a second run reports zero for
what already went).

## `crewship admin security-posture`

Report how this instance is postured: encryption at rest, the private-egress ceiling, signup policy, rate limiting, and whether email/OAuth are configured.

```bash
crewship admin security-posture
crewship admin security-posture --format json | jq '.warnings[] | select(.severity=="high")'
```

**Read-only by design.** These are env-driven *deploy* decisions and are deliberately not settable from the app or from this command — the gap it closes is that their **state** was invisible without shell access to the box, which the person triaging an incident often doesn't have.

<Note>
No secret value is ever returned — only whether something is configured. That is the whole contract, and it's what lets this be a plain admin `GET` with nothing worth stealing in the response. A regression test asserts no secret-shaped env value reaches the wire, including via a warning message.
</Note>

### What it reports

| Setting | Source |
|---|---|
| Encryption key | `ENCRYPTION_KEY` present |
| Plaintext secrets | `CREWSHIP_ALLOW_PLAINTEXT_SECRETS` |
| Private-egress ceiling | `CREWSHIP_ALLOW_PRIVATE_ENDPOINTS` — the instance half of the two-key opt-in; the other half is per-crew `allow_private_endpoints` |
| Signup | `CREWSHIP_ALLOW_SIGNUP` |
| Rate limiter | `CREWSHIP_RATELIMIT_DISABLED` (and the legacy `CREWSHIP_DISABLE_RATELIMIT`) |
| Email / OAuth | `RESEND_API_KEY` + `RESEND_FROM` / Google client id + secret — presence only |

Each value is read through the **same accessor the runtime enforces with**, not re-parsed locally. A posture that parses a flag its own way eventually disagrees with the code that acts on it, and a security report that confidently states the wrong thing is worse than no report.

### Intent vs. effect

The rate limiter is reported twice on purpose. In production the limiter runs **regardless** of the disable flag (`MustNotDisableRateLimitInProd`), so:

```
Rate limiter    disable flag set, but IGNORED (production) — limiter running
```

Reporting that as "disabled" would send you chasing an exposure that doesn't exist; reporting it as plain "enabled" would hide that your config says otherwise and will bite the first time this config lands somewhere the guard doesn't apply.

### Warnings

Beyond the raw state, the report derives warnings that name the **consequence**:

- `plaintext_secrets_allowed` (**high**) — anyone with the database file can read every stored secret.
- `encryption_key_missing` (**medium**, **high** when combined with the above) — the combination means new credentials are being written in the clear.
- `rate_limit_disabled` (**medium**) — credential-stuffing and the `/credentials/test` oracle are unthrottled.
- `rate_limit_disabled_ignored_in_prod` (**info**) — a disable flag is set but the production guard keeps the limiter running. Not an exposure; it means your config and the running state disagree, which matters the first time that config lands somewhere the guard doesn't apply.
- `signup_open` (**medium**, **high** in production) — anyone who can reach the instance can create an account.
- `private_endpoints_ceiling_open` (**info**) — crews that also opt in can reach RFC1918/loopback. Link-local and cloud-metadata stay blocked regardless.

The keys above read the **environment**. The rest read what the instance has actually *become*, which is the half no config file can tell you:

- `encryption_key_generated` (**medium**) — Crewship bootstrapped the master key itself instead of an operator supplying one, so the key lives with the data it protects.
- `privileged_credentials_enabled` (**high**) — at least one workspace has `allow_privileged_credentials` on, which removes the fail-closed boundary between privileged crews and stored secrets.
- `private_endpoints_in_use` (**medium**) — crews have opted into private-endpoint egress *and* the instance ceiling is open, so the reach is live rather than merely permitted.
- `seed_account_default_password` (**high**) — the `crewship seed` demo account still authenticates with the password printed in these docs.
- `no_backup_recorded` (**medium**) — no `backup.*` action appears in the audit trail. Reported only when that query succeeds: a failed probe is unknown state, not a missing backup.

The same data backs the **Admin → Runtime → Security posture** card in the dashboard.

## `crewship admin memory-config`

Read or adjust `workspaces.memory_config` — currently the retention window for `memory_versions` rows, consumed by the per-workspace retention sweep.

The command also accepts the alias `crewship admin memcfg`.

```bash
crewship admin memory-config get
crewship admin memory-config get --format json
crewship admin memory-config set --retention-days 30
```

The endpoint (`GET/PATCH /api/v1/admin/memory/config`) exists so retention can be changed **without editing SQLite by hand**. Until this command there was no client for it, so the hand-edit stayed the only route — which is what the endpoint was built to avoid.

### `memory-config get`

Prints the **resolved** value and, importantly, whether it was chosen:

```console
SETTING                    VALUE     SOURCE
Memory versions retention  30 days   default (not set for this workspace)
```

`30 days` on its own doesn't tell you whether anyone picked it. That matters before changing it: overriding a built-in default is routine, overriding somebody's deliberate policy is not.

When the stored document carries keys this CLI version doesn't model, they are printed verbatim underneath rather than hidden — otherwise `get` would look authoritative when it isn't.

### `memory-config set --retention-days N`

| Flag | Required | Description |
|------|:---:|-------------|
| `--retention-days` | ✓ | Days to keep `memory_versions` rows. Server-validated to `1..3650` (10 years); longer windows require a deliberate SQL edit. |

Writes are **manage-tier** and emit `memory.config_updated` to the journal, so a compliance audit can trace when retention policy changed and who changed it.

<Warning>
Rows already older than the new window become **eligible for deletion** on the retention sweep's next pass. Shortening the window is not a preview — it schedules data loss.
</Warning>

Sent as a **partial `PATCH`** carrying only the key being changed. The server merges it into the stored document and preserves settings this CLI doesn't know about, so an older binary can't silently drop a newer knob by writing a whole document back.

The same data backs the **Admin → Runtime → Memory configuration** card in the dashboard.

## `crewship admin memory sync`

Run one of the two daily memory sweeps now instead of waiting for its
scheduled tick, and see the per-workspace summary the sweep otherwise only
logs. Two subcommands, one per sweep:

```bash
crewship admin memory sync user-model              # the operator-model sweep (05:00 UTC)
crewship admin memory sync user-model --dry-run    # report what it would do; write nothing
crewship admin memory sync user-model --all -f json
crewship admin memory sync peer-cards              # the peer-card sweep (04:00 UTC)
```

Before this command the sweeps could only be observed by being awake when
they fire. That is worse for the operator model than for most schedulers:
nothing is written when the model proposes nothing, when every candidate is
refused by the evidence gate, when the `curator` slot cannot be built, or
when the person is below the interaction threshold — and all four look the
same from outside. The summary tells them apart:

```console
✓ The operator-model sweep ran over 1 workspace(s) in 4.12s.
WORKSPACE   CANDIDATES  WRITES  BELOW THRESHOLD  EMPTY  OPTED OUT  PURGED  ERRORS  NOTE
ws_01HZ…    3           1       1                1      0          0       0
```

| Column | Meaning |
|---|---|
| `CANDIDATES` | Operators (or, for peer cards, agent–operator pairs) with a chat in the 14-day lookback window. |
| `WRITES` | Files written — or, with `--dry-run`, that would have been. |
| `BELOW THRESHOLD` | Skipped: not enough messages or session time yet. |
| `EMPTY` | Skipped: the extractor had nothing to write. With no model on the `curator` slot this is every candidate — check `crewship keeper aux`. |
| `OPTED OUT` / `PURGED` | The operator has opted out of peer memory; `PURGED` means an existing file was deleted (or would have been). |
| `ERRORS` | Candidates that failed inside the sweep; each has a `Warn` line in the server log. |
| `NOTE` | Set when the sweep for that workspace could not run at all. The other workspaces still ran. |

A `TOTAL` row is added when more than one workspace was swept.

Scope defaults to the current workspace (`-w` / config). `--all` runs every
active workspace on the instance — exactly what the scheduler does at its
tick. The sweeps are safe to re-run: the merge is idempotent and the write is
capped.

`--dry-run` runs everything up to the write — including the extractor, which
is the model-backed step worth observing — and reports what *would* have
happened. Nothing lands on disk, in the index tables, or in the audit log.
This is how a measurement like "how many facts does the extractor propose,
and how many does the gate refuse" becomes repeatable without planting data
in a live instance; the per-extraction counts are on the server log's
`user model extraction` lines.

The peer-card sweep has no extractor wired on the server today, so it
indexes and purges without writing new bodies — the same thing the 04:00
sweep does — and every threshold-crosser shows under `EMPTY`.

| Flag | Type | Default | Meaning |
|---|---|---|---|
| `--all` | bool | `false` | Sweep every active workspace on the instance, as the scheduled run does, instead of only the current one. |
| `--dry-run` | bool | `false` | Run the sweep up to the write and report what it would do; nothing is written. |
| `--timeout` | duration | `10m` | How long to wait for the sweep. The server runs one model call per candidate inside the request, so a big workspace can take minutes; the CLI's usual 30 s would cancel it — server side too. |

`--format json` prints the server's report verbatim (`sweep`, `dry_run`,
`workspaces[]`, `totals`, `duration_ms`).

Backed by `POST /api/v1/admin/memory/user-model-sync` and
`POST /api/v1/admin/memory/peer-card-sync`. Requires `OWNER` or `ADMIN`
(`canRole "manage"`).

## `crewship admin ratelimits`

Inspect and tune the instance's rate limiters at runtime — the same surface as the dashboard's **Infrastructure → Rate Limiters** tab. Every limiter that was once a hardcoded constant (the per-IP HTTP buckets, the login lockout, the notification anti-storm bucket, crew provisioning, agent webhooks) is listed and overridable without a redeploy.

Aliases: `crewship admin rate-limits` and `crewship admin ratelimit`.

```bash
crewship admin ratelimits list
crewship admin ratelimits list --format json
crewship admin ratelimits set http.auth_per_min 30
crewship admin ratelimits reset http.auth_per_min
```

`list` shows each limiter's group, key, current value, shipped default, unit, and whether the value is a default or an override:

```console
GROUP         KEY                                 VALUE  DEFAULT  UNIT        SOURCE
HTTP (per-IP) http.auth_per_min                   30     10       req/min     override
HTTP (per-IP) http.api_per_min                    120    120      req/min     default
Login         login.lockout_threshold             10     10       attempts    default
Notifications notify.burst                        5      5        tokens      default
Provisioning  provisioning.max_starts_per_min     20     20       starts/min  default
```

`set <key> <value>` overrides a limiter; `reset <key>` reverts it to the shipped default. Overrides persist in the instance-global `rate_limit_overrides` table and take effect **immediately** — the per-IP HTTP buckets are retuned on the live limiter, the rest read their value on next use.

| Key | Default | Unit | Limits |
|---|---|---|---|
| `http.auth_per_min` | 10 | req/min | Login / token-refresh / bootstrap, per IP (read-only session polls do **not** count). |
| `http.api_per_min` | 120 | req/min | Every other `/api/*` route, per IP. |
| `http.cred_test_per_min` | 60 | req/min | Credential-test endpoints (anti key-validation-oracle). |
| `login.lockout_threshold` | 10 | attempts | Consecutive failed sign-ins before an account locks. |
| `login.lockout_duration_sec` | 300 | seconds | How long a locked account stays frozen. |
| `notify.burst` | 5 | tokens | Notification burst per (recipient, channel, category). |
| `notify.refill_interval_sec` | 30 | seconds/token | Refill rate after a burst. |
| `provisioning.max_concurrent_per_ws` | 8 | jobs | Concurrent crew provisions per workspace. |
| `provisioning.max_starts_per_min` | 20 | starts/min | Crew provision starts per workspace per minute. |
| `webhook.agent_per_min` | 60 | req/min | Agent-webhook fires per agent. |

Writes are **manage-tier** (OWNER/ADMIN) and logged at WARN with the actor. A value outside a limiter's allowed range is rejected (`400`); an unknown key is `404`.

<Note>
Raising `http.auth_per_min` is the fix for an instance whose users get logged out under heavy refresh behind a shared NAT. On current builds the read-only session polls that caused that no longer touch this bucket, so most instances never need to.
</Note>

## `crewship admin seed-inbox`

Fill a workspace's inbox with one row of every kind — waitpoints, escalations, a failed run, messages, a memory proposal, schedule alerts — plus approval-queue rows both pending and decided. It exists because the inbox has no create endpoint: every row is written by a producer (a pipeline reaching a waitpoint, an agent escalating, the keeper sweeping), so a fresh workspace shows an empty inbox and there is no way to see how the views, facets and the reading pane behave against real variety.

Rows go in through the same writers the real producers use, so what lands is shaped exactly like production data rather than hand-built SQL that agrees with whatever the UI happens to expect.

```bash
# Seed a scratch workspace
crewship admin seed-inbox --local --workspace ws_abc123

# Remove only what this command wrote
crewship admin seed-inbox --local --workspace ws_abc123 --clear
```

| Flag | Purpose |
|---|---|
| `--workspace <id>` | **Required.** The workspace to seed. Give it a scratch workspace, not a real one. |
| `--clear` | Delete the rows this command wrote, and nothing else. Everything it writes carries a `seed_` source id (`[seed]` on approvals), which is what `--clear` matches; it never touches a row it did not create. |
| `--local` | Confirms you mean the database file on this host. Required when the CLI is pointed at a server — see [Which database am I talking to?](#which-database-am-i-talking-to) above. |

<Warning>
**Fixture, not a runtime test.** The run behind a seeded approval gate is a row, not an execution: no executor is parked on the waitpoint, so approving a seeded gate flips the token and cascades the inbox row and then *nothing resumes*.

Use it to remove "is it seeded?" preconditions from a test, and to prove a button reaches its endpoint — never as evidence that a decision took effect. That is the `approval-gate-demo` routine's job — `crewship routine run approval-gate-demo` parks a real run on a real gate, and approving it resumes the run.

Seed while the server is running, too: a restart sweeps gates whose pipeline run is missing or terminal (`CancelOrphanedWaitpoints`), which settles the seeded ones out from under you.
</Warning>

## crewship admin cleanup

Read container cleanup observations from the server selected by the CLI. This
HTTP read requires login. Instance admins can omit the workspace and read the
whole installation; workspace ADMIN/OWNER users must select a workspace and
see only its observations.
Unlike local recovery commands, it does not open a database file. It is backed
by `GET /api/v1/admin/resource-cleanup` and never triggers cleanup itself.

```bash
crewship admin cleanup --format json
```

The response includes `scope=containers`, controller state and per-crew `items`
for this installation (instance admins) or the selected workspace (workspace
admins), with observation time, completeness, remaining eligible containers (and
per-crew networks, when the crew had one), legacy unattributed count and fixed
error codes. `observed_clear` describes the last complete eligible-container and
crew-network scan, not volumes, host data or future creates.
Stale observations read as `unknown`.

If the crew's workspace is deleted or the server is unavailable, use
`crewship doctor cleanup --format json` on the host to read historical local
snapshots without workspace membership.
