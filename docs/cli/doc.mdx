# crewship doc

Work with a native document in the selected workspace. A document is saved on
an artifact, and the artifact's slug or `@<artifact-id>` addresses it. With the
Artifacts library enabled, documents are listed there as **Word**. The service
rechecks your current credential and document permissions before reading or
saving. Scoped credentials need `pages:read` for reads and both `pages:read` and
`pages:write` for editing; `pages:*` covers both. These scopes do not grant access
to somebody else's document.

```bash
crewship doc <subcommand> [<slug|@artifact-id>] [flags]
```

## Availability

| Switch | Kind | Default | Effect |
|---|---|---|---|
| `CREWSHIP_DOCUMENTS_ENABLED=true` | Server startup | Off | Turns on the document service. While it is off, `doc status` reports `enabled: false` and `read`, `outline`, `patch`, `initialize`, `checkpoints` and `checkpoint` return `503 Docs are not enabled on this server`. |
| `NEXT_PUBLIC_ARTIFACTS_LIBRARY=true` | Web build | Off | Lists saved documents in the Artifacts library. The CLI does not need it. |

`doc create`, `doc draft` and the chat **Create document** control also need
the workspace's agent artifact policy to allow the crew
(`crewship workspace artifact-policy show`).

| Commands | Credential | Scoped token |
|---|---|---|
| `status` | Any credential with access to the workspace | None |
| `read`, `outline`, `checkpoints`, `checkpoint`, `chat-results` | Human session or CLI token | `pages:read` |
| `initialize`, `patch`, `restore` | Human session or CLI token with edit access | `pages:read` and `pages:write` |
| `create`, `draft` | The admitted run's `CREWSHIP_AGENT_TOKEN` only | — |

A reader refuses unsupported saved document schemas, including initialization
retries, without returning their content. Use a compatible document service;
confirmed data stays retained rather than being silently replaced.

## `crewship doc create --file <request.json>`

Create a populated document during a run admitted for one human's creation
request. This command uses that run's credential and the local sidecar; it does
not fall back to a saved human profile. Document support and the workspace's
creation policy must allow the request.

Supply one JSON object of at most 1 MiB with `slug`, `name`, `mutation_id` and a
`blocks` array. Use `--file -` for stdin. For example:

```json
{"slug":"launch-plan","name":"Launch plan","mutation_id":"launch-one","blocks":[{"type":"heading","level":1,"text":"Launch plan"},{"type":"paragraph","text":"Start with one team and review feedback."}]}
```

The result identifies the saved document and its link. An ordinary card click
opens its current saved content beside the trusted conversation, after checking
your current read access. Closing the preview preserves your unsent chat message;
on a phone, use Back to chat. Modified clicks and native links open that saved
identity in your current workspace and native editor. An unavailable document never falls back to another page or the catalog.
If confirmation is lost,
retry the same input with the same mutation ID. Changing that input conflicts;
a retry never creates another document, including when the connection closes
after the document has been saved but before its response reaches the agent.
Retry from the same live run; do not generate a replacement mutation ID.
Creation keeps the requesting human as
owner. A one-shot admission grants no later access. If the original human request
explicitly includes drafting, the same live run may save further guarded drafts
of that one new document; it receives no access to another artifact.

An agent can also call `doc_create` in the Crewship routines MCP tools with the
same four fields. The tool uses the same run permission and saved result; an
exact retry can recover that result across the CLI and MCP interfaces.

An admitted run of an agent added to an already running crew can create and
draft its Document without restarting the shared crew container. The host still
checks the run capability, the requesting human's current access and the original
creation or drafting permission; startup roster labels do not grant access.

## `crewship doc draft`

Save progress while fulfilling an admitted creation request. The original human
request must include drafting permission. These commands use the current run's
credential and local sidecar, without a saved human profile or an artifact selector.
They apply only to the document created for that request and stop when the run
ends, its permission expires or is revoked, or a human changes the document.
A replacement run inherits no drafting permission.

1. Run `crewship doc draft view` to read a bounded view of confirmed headings and
   paragraphs, their block IDs and hashes, and the document's revision and epoch.
2. Run `crewship doc draft prepare --file <input.json>` with `view`, `target`,
   `text` and a stable `mutation_id` of at most 117 ASCII letters, digits, underscores
   or hyphens. It prepares an immutable edit and checkpoint
   packet locally; preparation does not save text.
3. Retain that output and run `crewship doc draft apply --file <packet.json>` to
   apply the guarded text replacement and checkpoint the confirmed revision.

Use `--file -` for stdin. Keep the original prepared packet after an uncertain
response. Applying that same packet again recovers its receipts without another
write. Changing an existing mutation's contents conflicts; rereading does not
rebase or authorize a replacement edit automatically.

Draft commands return JSON by default and honor `--format json`, `--format yaml`
and `--format ndjson`. Use JSON output for packets passed to another draft
command; input files remain JSON. Output formats preserve original integer
revisions and checkpoint identities.

If the text edit commits but the checkpoint confirmation fails, the edit remains
saved. The result reports `committed_checkpoint_pending`; retry only its original
checkpoint with `crewship doc draft checkpoint --file <packet.json>`. Do not
report committed content as lost or silently generate a new mutation.

The routines MCP tools `doc_draft_view`, `doc_draft_prepare`, `doc_draft_apply`
and `doc_draft_checkpoint` use the same permission and immutable requests. They
do not accept raw Yjs updates or whole-document replacement.

## `crewship doc status`

Read whether document support is configured on the selected instance. This
command takes no artifact argument. A disabled instance returns `enabled: false`.
`wordcraft_native` and `gridcraft_native` report whether the native Craft Word
and Sheet editors are configured.

```bash
crewship doc status -f json
```

```json
{"enabled":false,"gridcraft_native":false,"wordcraft_native":false}
```

## `crewship doc initialize <page-slug>`

Populate an empty artifact that you own personally with its first document.
The artifact must not be owned by a crew and must hold no other output. Create
one with [`crewship page create`](/cli/page) and `--allow-empty`. This command
needs a credential with the `workspace:admin` CLI scope. A minimal definition
is enough:

```yaml
apiVersion: crewship/v1
kind: Page
metadata:
  slug: launch-plan
  name: Launch plan
spec: {}
```

```bash
crewship page create --file page.yaml --allow-empty
```

This artifact is owned by you and shared with the workspace in the usual way;
document initialization does not require a private artifact. (Native Slides
does require one, so the same artifact is not a valid
[`slides initialize`](/cli/slides) target.)

Then supply a JSON request
containing an operation `id`, explicit `schema` (2 or 3), and a `body` document
tree. Schema 3 also requires the original `page_id`. Headings and paragraphs use
schema 2; initialization does not silently upgrade an existing document.

`--file` is required. Use `--file -` to read stdin. The file must contain one JSON
object of at most 2 MiB. Keep the same operation ID and contents when retrying
an operation whose confirmation was lost.

```bash
crewship doc initialize @<artifact-id> --file initialize.json
```

```json
{"id":"init-1","schema":2,"body":{"type":"doc","content":[{"type":"paragraph","attrs":{"id":"intro"},"content":[{"type":"text","text":"Original selected text"}]}]}}
```

The first response is the initial state, with `schema`, `rev: 0`, a numeric
`epoch`, `generation`, `blocks` (block `id` and `hash`) and the stored snapshot.
An exact retry returns the original receipt with `duplicate: true` instead:

```json
{"actor":"user:<user-id>","duplicate":true,"epoch":0,"found":true,"id":"init-1","kind":"init","rev":0}
```

The native editor's **History** button opens a separate read-only view of retained
checkpoints. Selecting an older checkpoint and closing history preserve your
current editor and unsaved draft. Browsing does not restore or overwrite content.

## `crewship doc checkpoints <page-slug>`

`crewship doc checkpoints <page-slug>` lists at most the latest 1,000 retained
checkpoint pins, ordered by revision and identity. Checkpoints are explicit saved
pins, not every editor keystroke. Older pins remain retained and can be read by ID.
Each entry in `checkpoints` has `id`, `rev`, `schema`, `actor` and `created_at`.
A document without retained history returns `404 document history unavailable`.

```bash
crewship doc checkpoints @<artifact-id> -f json
```

## `crewship doc checkpoint <page-slug> <checkpoint-id>`

Read that exact confirmed
body as `content`, with its `page_id`, checkpoint `id`, `rev` and `schema`. The
checkpoint ID must be 1 to 128 letters, digits, underscores or hyphens; anything
else stops locally with `bounded checkpoint identity required`. Both commands accept
`@<artifact-id>` and the standard JSON, YAML and NDJSON output formats.

These commands use current human read access, including the private audience;
an old run or checkpoint ID grants no access. Reads never restore content or
change a draft. The public response omits binary snapshots and writer fences.

## `crewship doc restore <page-slug> --file request.json`

Restore one retained checkpoint as a new confirmed revision. The original JSON
packet (at most 4 KiB) contains `page_id`, a unique operation `id`, the current `schema`, opaque
`epoch`, current `ifRev`, and the retained `checkpoint` ID. Read the current
Document first and confirm the intended checkpoint. Keep the exact same packet
for a retry after uncertain confirmation; never refresh its revision or epoch.
The server checks current human write access. A successful restore increments
the revision and generation and invalidates the previous writer epoch. The
receipt has `page_id`, `id`, `rev`, `epoch`, `kind` and `schema`.

```bash
crewship doc restore @<artifact-id> --file restore.json
```

The native History view requires explicit confirmation. Restore is unavailable
while a local draft is pending or requires recovery. An uncertain result keeps
the editor locked and offers the original retry, without claiming success.
Browsing history still preserves the live draft. Restore does not reactivate an
old agent run or its authority. Unsupported history content remains unavailable.

## `crewship doc read <page-slug>`

For a saved Document identity, `crewship doc read @<artifact-id>` keeps the original
object bound to the request. A deleted identity returns 404 even if another
document reuses its former slug. Current workspace and access checks still apply.

Read the currently confirmed document, content tree, block outline and revision.
Use the returned opaque `epoch`, `rev` and target block hash when preparing an
edit. Read after initialization to obtain the editing epoch.

```bash
crewship doc read @<artifact-id> -f json
```

The response also carries the stored editor state (`generation`,
`incarnation`, `snapshot`, `snapshotRev`, `updates` and `blocks`). This
abbreviated example leaves those values out:

```json
{
  "blocks": [ … ],
  "can_comment": false,
  "can_resolve": false,
  "can_write": true,
  "content": {"type": "doc", "content": [ … ]},
  "epoch": "<opaque-epoch>",
  "generation": 0,
  "incarnation": "…",
  "outline": [{"hash": "11afc865…", "id": "intro", "parent": null, "text": "Original selected text", "type": "paragraph"}],
  "page_id": "<artifact-id>",
  "rev": 0,
  "schema": 2,
  "snapshot": "…",
  "snapshotRev": 0,
  "updates": [ … ]
}
```

Each `outline` entry has the block `id`, its node `type`, the `parent` block ID
(`null` at the top level), its `hash` and its plain `text`.

An empty artifact with no document yet returns `404 document not found`. An
artifact that holds a different output, such as a typed version, Slides deck,
board, workbook, panels or a Project, returns `403 document access denied`.

## `crewship doc outline <page-slug>`

Print a JSON array of the current blocks, each with `id`, `type`, `parent`,
`hash` and `text`. This command
reads the same confirmed document as `read`; it does not mutate it. It always
prints JSON, whatever `--format` you pass.

```bash
crewship doc outline @<artifact-id>
```

```json
[{"hash":"11afc865…","id":"intro","parent":null,"text":"Original selected text","type":"paragraph"}]
```

## `crewship doc patch <page-slug>`

Save an explicitly guarded update. `--file` is required; `--file -` reads stdin.
Supply one JSON object of at most 2 MiB. A semantic text replacement contains
`id`, `schema`, the confirmed `epoch`, `target` block ID, replacement `text`,
`ifRev` and `ifHash`. Schema 3 also requires the original `page_id`. The editor's
binary update form uses `kind: "human"` and a base64 `update` instead.

A changed revision, target hash or epoch refuses the edit. Read the confirmed
state again and decide on a new edit; the command never rebases it automatically.
For a lost confirmation, resend the original request with its original ID.
The receipt identifies the durable revision; a successful exact retry does not
create another write. Revoked credentials cannot replay saved requests.

```bash
crewship doc patch @<artifact-id> --file patch.json
```

```json
{"id":"patch-1","schema":2,"epoch":"<opaque-epoch>","ifRev":0,"target":"intro","ifHash":"11afc865…","text":"Confirmed replacement"}
```

```json
{"actor":"user:<user-id>","epoch":"<opaque-epoch>","id":"patch-1","kind":"human","rev":1}
```

An exact retry returns the original receipt with `found: true` and
`duplicate: true`, plus the request's `schema` and the current `epoch`.

## Errors

With `-f json`, errors are printed as an `error` object with `message`,
`status`, `detail` and `exit_code`. See
[exit codes](/cli/overview#exit-codes-&-machine-readable-errors).

| Situation | Status | Message | Exit |
|---|---|---|---|
| Document service off | 503 | `Docs are not enabled on this server` | 7 |
| Empty artifact with no document yet | 404 | `document not found` | 3 |
| No such artifact (`read`, `outline`, `initialize`, `patch`, `checkpoints`, `checkpoint`, `restore`) | 404 | `document page not found` | 3 |
| Artifact holds another output, belongs to a crew (`initialize`), or you lack access | 403 | `document access denied` | 4 |
| No retained history | 404 | `document history unavailable` | 3 |
| Token without `pages:write` edits | 403 | `Forbidden` | 4 |
| Stale `epoch` | 409 | `old epoch; reload document` | 5 |
| Stale `ifRev` or `ifHash`, or unknown `target` | 409 | `semantic precondition conflict` | 5 |
| Another write committed at the same time | 409 | `document revision conflict` | 5 |
| Malformed restore packet | 400 | `original bounded Document restore packet required` | 2 |
| Unknown chat for `chat-results` | 404 | `chat not found` | 3 |
| Missing `--file`, file over the size limit, not one JSON object | — | Local message | 1 |
| `create` or `draft` without a run capability | — | `original CREWSHIP_AGENT_TOKEN run capability required; no human profile fallback` | 1 |

## Requesting a document in chat

With Document support and the workspace creation policy enabled, open a private
agent chat without selecting an existing artifact. Select **Create document** in the
composer, then describe what you want and send the message. For example, write
“Please draft a garden plan. Include three sections!” or “Napiš mi plán zahrady.”
The request can use Czech or English, punctuation, and multiple lines.

The selection applies to one sent message. It authorizes creating a new private
document and saving drafts of that document during the original live run.
Sending successfully clears the selection; changing users or conversations also
clears it. A failed local send preserves the selection for retry. The control
is unavailable while Document support is unconfirmed or an existing artifact is
selected. The server rechecks the original human and private-chat permissions.

The composer carries `document_creation_intent` metadata with a `submission_id`
and `drafting: true`; it leaves the message text unchanged. The older
`document_creation` metadata shape remains supported for existing clients.
Sending both shapes is rejected. Text returned by a model does not grant consent.

If a connection loses the reply, resending the same explicit submission key and
request is refused as already accepted, with the original human message ID.
Reload the conversation and inspect its saved result; the retry does not append
a second human turn, start another run, or renew drafting permission. Reusing the
key with different text or drafting permission is refused as a conflict. Current
human and chat authority are checked before either refusal. A message saved
before a consent-persistence failure remains visible, but its retry cannot mint
permission or start a run; report the unconfirmed request instead of silently
issuing a new key.


The narrow command `vytvoř dokument o plánu uvedení produktu` remains a fallback.
Its topic must be a single line containing letters, digits, spaces or hyphens;
quoted, negated or ambiguous text does not grant creation permission. Use the
composer control for other wording.

A Document created from a private chat has an explicit private audience: its
human owner and the workspace OWNER. Other roles, including ADMIN, cannot see
its title, catalog entry or content; direct reads return 404. Opening somebody
else's private document as OWNER requires a durable audit entry before access.
Crew membership, folder inheritance and ordinary sharing grants do not widen this
audience. Legacy public links cannot publish it. Storage limits continue
to count the whole workspace. If its owner leaves, removal returns 409 until
the workspace OWNER explicitly selects an active human successor.

The source conversation keeps that private audience from the original creation
consent, even if creation fails or the execution permission later expires.
Its stored tool results and live messages cannot expose the output to an ADMIN;
OWNER inspection is audited before delivery. Existing transcript-sharing links
cannot publish this protected conversation. Create new private documents from
your own private conversation; administrative chat access is not creation consent.
Deleting a protected source conversation currently returns 409: retained log
copies still depend on its privacy record. Ordinary chat deletion is unaffected.
Configured chat retention also keeps protected source conversations and excludes
them from its deletion preview while those copies depend on their privacy record.

The run creates a populated document and returns its saved link. Reopening a
result does not grant a later run permission to edit it. Repeating an uncertain
operation must reuse the original request, rather than issuing a new chat task.

## `crewship doc chat-results <chat-id>`

List saved documents linked to an accessible chat. This command requires your
current human credential, `pages:read` for scoped CLI tokens, access to the chat
and access to each document. Unavailable documents are omitted. Results contain
saved links and provenance, without document contents or transcript text. Each
entry in `results` has `page_id`, `type`, `page_slug`, `title`, `revision`,
`created_at`, `agent_id`, `agent_name`, `run_id` and `on_behalf_of_user_id`.

```bash
crewship doc chat-results <chat-id> -f json
```

A completed or recovered run does not erase its saved result. The command
rechecks your current access; the original run does not regain permission.

Agent-wide logs and diagnostics can contain copies from several conversations.
They are available only when the reader may inspect every protected conversation
represented by that agent; a document author does not gain access to another
author's private output. Foreign OWNER inspection is audited before copies are
returned. Unavailable required auditing prevents disclosure.
