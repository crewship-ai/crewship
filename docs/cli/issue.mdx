# crewship issue

Issue tracking wired directly into agent dispatch. Use these commands to create and triage issues, manage labels, comments, relations, and sub-issues, and hand work to an assigned agent (`start` / `stop` / `review`). Issues can also be bound to a routine so a fixed workflow runs whenever the issue is started.

```bash
crewship issue <subcommand> [flags]
```

**Alias:** `crewship issues`

## Subcommands

| Command | Description |
|---------|-------------|
| `list` | List issues in the workspace |
| `get` | Show issue details |
| `create` | Create a new issue |
| `update` | Update an issue |
| `delete` | Delete an issue |
| `comment` | Add a comment to an issue |
| `comments` | List comments on an issue |
| `labels` | List workspace labels |
| `start` | Start an issue (dispatch to assigned agent) |
| `stop` | Stop an issue (cancel running tasks) |
| `review` | Review an issue (approve or request changes) |
| `activity` | Show the activity timeline for an issue |
| `events` | Show the ordered, seq-cursored event log for an issue (for resync after a dropped realtime frame) |
| `runs` | List runs triggered by an issue |
| `sessions` | List an issue's agent sessions |
| `changes` | Show the git diff produced by work on an issue |
| `subtasks` | List sub-issues of an issue (aliases: `subissues`, `sub-issues`) |
| `relate` | Create a relation between two issues |
| `relations` | List relations for an issue (alias: `relates`) |
| `unrelate` | Remove a relation by relation ID |
| `links` | List the pull requests linked to an issue (aliases: `code-links`, `prs`) |
| `link` | Attach a pull request / merge request to an issue |
| `relink` | Re-read a linked pull request's state from its provider (alias: `refresh-link`) |
| `unlink` | Remove a pull-request link from an issue |
| `attachments` | List the files attached to an issue (alias: `files`) |

| `bulk update` | Apply the same patch to up to 100 issues in one round-trip |

## `crewship issue list`

List issues in the workspace with optional filters.

```bash
crewship issue list
crewship issue list --status IN_PROGRESS --crew backend-team
crewship issue list --priority high --label bug
crewship issue list --search "auth flow"
```

| Flag | Type | Default | Description |
|------|------|---------|-------------|
| `--status` | `string` | | Filter by status: `BACKLOG`, `TODO`, `IN_PROGRESS`, `REVIEW`, `DONE`, `FAILED`, `CANCELLED`, `DUPLICATE`. |
| `--priority` | `string` | | Filter by priority: `none`, `low`, `medium`, `high`, `urgent`. |
| `--crew` | `string` | | Filter by crew slug or ID. |
| `--assignee` | `string` | | Filter by assignee ID. |
| `--label` | `string` | | Filter by label name. |
| `--search` | `string` | | Search issues by title or identifier, on the server (sent as `q`). |
| `--limit` | `int` | `50` | Rows per page (the server caps it at 500). |
| `--offset` | `int` | `0` | Skip this many rows. Page with `--offset 50`, `--offset 100`, … |

**Output columns:** ID, TITLE, STATUS, PRIORITY, ASSIGNEE, CREATOR, CREW, LABELS, UPDATED

A human table ends with `showing 1–50 of 1 015 · next page: --offset 50`, read from the
`X-Total-Count` / `X-Limit` / `X-Offset` headers every paged list sends. Machine formats
(`json`, `yaml`, `ndjson`) stay a bare array, since scripts decode it directly; `quiet` stays one id per line.
The response also carries `X-Has-More` (#2286) for clients that only read that boolean.

## `crewship issue get`

Show issue details including comments.

```bash
crewship issue get <identifier>
crewship issue get BE-42
```

The identifier can be the issue identifier (e.g., `BE-42`) or the full ID.

**Output fields:** Identifier, Title, Status, Priority, Crew, Assignee, Assignee Type, Owner, Delegate, Description, Due Date, Mission Type, Labels, Comments count, Created By, Created, Updated, ID.

`Owner` and `Delegate` are the typed projection of the issue's human owner and agent delegate (`owner`/`delegate` in the API — #2297, independent of each other and of the legacy `Assignee`/`Assignee Type` pair above). Each shows the resolved name, or `-` when nobody occupies that slot. In `--format json` / `--format yaml`, the same data is `owner`/`delegate` objects (`{id, name}`), omitted entirely when unset.

Comments are displayed below the detail section.

### Who created an issue

Every issue records its creator. The `Created By` field (and the `CREATOR`
column in `issue list`) shows the resolved name, suffixed with `(agent)` when
the issue was created by an agent through a tool call rather than by a human:

```
Created By   Scout (agent)     # created by the "Scout" agent
Created By   Pavel Srba        # created by a human via the API/UI
Created By   -                 # legacy issue, predates creator attribution
```

In `--output json`, the same information is available as the `created_by`
object (`{type, id, name}`, where `type` is `user` or `agent`) plus
`authored_via` (`user_api` or `agent_tool_call`).

## `crewship issue comment`

Add a comment to an issue.

```bash
crewship issue comment <identifier> This is a comment
crewship issue comment BE-42 --body "Detailed comment here"
crewship issue comment BE-42 --mention riley "the CSV job is failing on empty rows"
crewship issue comment BE-42 --mention riley --mention casey "over to you both"
```

The comment body can be passed as positional arguments after the identifier, or via the `--body` flag (which takes precedence).

| Flag | Type | Default | Description |
|------|------|---------|-------------|
| `--body` | `string` | | Comment body (alternative to positional args). |
| `--mention` | `string` | | Mention an agent by slug. Repeatable. Resolved against the workspace agent roster (same lookup as `--assignee` elsewhere) and prepended to the body as the real `[@slug](crewship:agent/<id>)` link the server requires — one per mention, space-separated, before the rest of the text. Fails with a clear error naming the slug and the workspace's real agents if a slug does not resolve. `--mention` alone with no other text is a valid comment. |

<Warning>
A bare `@slug` typed into the body (positionally or via `--body`) is **not** a mention — it is plain text, and the mentioned agent is never notified or dispatched. The server only recognises the Markdown link form `[@slug](crewship:agent/<agentId>)` (`internal/mentions`, `docs/guides/issue-mentions.mdx`). Use `--mention` to write a real one.
</Warning>

## `crewship issue stop`

Stop an issue. Ships in two tiers, both fired by this one command:

- **Tier 1 (cooperative, always applied).** Marks pending/in-progress tasks `CANCELLED` and stamps `cancel_requested_at` on every live assignment; a run that hasn't started its exec yet never starts, and the runner polls the stamp at every step boundary. No further step is scheduled.
- **Tier 2 (hard, opt in with `--hard`).** After the Tier 1 stamp lands, ends each live run's own tmux session (`tmux kill-session -t agent-{slug}`, run as a brand-new exec into the run's *same* container), escalating to a direct `kill -KILL` on that session's own process group if it hasn't exited after a short grace period. Most agent runs own a tmux session named for their own agent slug -- a container-visible identity -- so this never runs a container-level kill and never signals by OS pid: the crew's container is shared by every agent on the crew, and a pid resolved from outside the container is not safe to signal from inside it ([#2365](https://github.com/crewship-ai/crewship/issues/2365) -- the pre-fix mechanism did exactly that and silently signalled nothing). Only the run's own session is ever touched; a sibling agent's session keeps running untouched. A run whose exec bypassed tmux entirely (an oversized prompt delivered via stdin, or a container without tmux installed) has no session to end -- confirmed first by listing its pane pids before touching anything, then reported `NOT_FOUND` immediately rather than sending a signal that reaches nothing. Bounded to a few seconds; what was signalled and the result (`TERMINATED_TERM`, `TERMINATED_KILL`, `ALREADY_EXITED`, `NOT_FOUND`, `UNSUPPORTED`, `ERROR`) is recorded on the run (also readable via `crewship issue runs -f json`'s `hard_stop_result`/`hard_stop_at`) and in the issue's journal. Without `--hard`, a step already mid-exec simply finishes that exec and is then recorded `CANCELLED` regardless of what it reports -- nothing mid-exec is interrupted.

Also reaches a run an `@mention` dispatched on an issue that was never started (`BACKLOG`/`TODO`): the assignment gets the same `cancel_requested_at` stamp (and, with `--hard`, the same signal if it's already RUNNING), and the issue's own status is left unchanged. `stop` still refuses when the issue is not `IN_PROGRESS`/`REVIEW` and has no live run to reach.

```bash
crewship issue stop <identifier>
crewship issue stop BE-42
crewship issue stop BE-42 --hard
```

| Flag | Type | Default | Description |
|------|------|---------|-------------|
| `--hard` | `bool` | `false` | Also terminate the running process (Tier 2). Cooperative stop alone only prevents further work from starting; a step already mid-exec is left to finish on its own. |

## `crewship issue activity`

## `crewship issue events`

The same `mission_activity` rows as `activity`, but ordered by `seq` (the B1 event log's monotonic per-issue cursor) instead of `created_at`, and NOT capped at 50 — this is the endpoint the board's client-side gap detector calls to resync after a WebSocket frame is dropped under load (F43, work package B11, #2368). Hits `GET /api/v1/crews/{crewId}/issues/{ident}/events?after_seq=`.

```bash
crewship issue events BE-42                    # full history, seq order
crewship issue events BE-42 --after-seq 42     # only what happened after seq 42
crewship issue events BE-42 --format json | jq '.latest_seq'
```

| Flag | Type | Default | Description |
|------|------|---------|-------------|
| `--after-seq` | `int` | `0` | Only return events with `seq` greater than this. `0` returns the full history. |

**Output columns:** SEQ, WHEN (relative time), ACTOR (`type/name`), ACTION, DETAILS (truncated to 60 chars). In `--format json`, the response is `{"events": [...], "after_seq": N, "latest_seq": N}` — `latest_seq` is the issue's current high-water mark, so a client with no new events can still tell "caught up at N" from "server has never heard of this issue".

## `crewship issue runs`

List every run attributed to an issue — mission tasks, mention-dispatched runs, and delegation-hop runs alike — the data the dashboard's issue "Runs" tab shows. Hits `GET /api/v1/crews/{crewId}/issues/{ident}/runs` after resolving `<identifier>` to its crew via `fetchIssue`.

```bash
crewship issue runs BE-42
crewship issue runs BE-42 --format json | jq '.[] | select(.source=="mention")'
crewship issue runs BE-42 --limit 20 --offset 20
```

| Flag | Type | Default | Description |
|------|------|---------|-------------|
| `--limit` | `int` | `100` | Runs per page (the server caps it at 500). |
| `--offset` | `int` | `0` | Skip this many runs; the footer names the next page. |

**Output columns:** RUN (the journal run id — what `crewship journal --run-id` and the Activity page take; `—` when the assignment never reached a run), AGENT (slug), TASK (truncated to 28), STATUS, OUTCOME, STARTED (relative time), DURATION, SOURCE, RESULT (error message or result summary; ANSI-sanitised, truncated to 50 chars).

SOURCE is why the run is attributed to the issue: `task` (the issue's own mission-task plan), `mention` (an `@mention` dispatch), or `delegation` (a sub-agent's own further `/assign` call mid-mission). In `--format json`, the same run also carries `mission_id` (the issue's mission ID; omitted on a legacy row that predates `assignments.mission_id`), `run_id` / `trace_id`, `agent_id` and `agent_slug`, and `hard_stop_result` / `hard_stop_at` (work package B7b, #2365) -- what a Tier 2 `issue stop --hard` did to this run and when, omitted on a run that was never hard-stopped. Not shown as a table column; read it with `--format json` so a live check can confirm a hard stop actually landed without reading the journal.

OUTCOME is the §9.6 routing decision (work package B6, #2349) — `NO_CHANGE`, `SUCCEEDED`, `WORK_CREATED`, `PARTIAL`, `NEEDS_HUMAN`, `FAILED`, or `CANCELLED`; `-` on a run that predates the `outcome` column. It answers a different question than STATUS: a `COMPLETED` run that never reported a recognised outcome shows `FAILED` here, with its error naming `"no outcome reported"` — an absent outcome is treated as a bug, not a silent success. `NEEDS_HUMAN` is the one outcome that raises an inbox item (`crewship inbox list --kind run_needs_human`). Full vocabulary and routing table: [API reference → Issues → Outcome](/api-reference/issues#outcome).

## `crewship issue sessions`

<Note>Session lifecycle: `issue_agent_sessions` is work package B1 of the Issues & Routines architecture (`docs/prd/PRD-ISSUES-AND-ROUTINES-2026.md`). A mention resolves or creates a session — mentioning the same agent on the same issue twice reuses it rather than creating a second. As of B4 (#2348) the session's `state` moves `pending` → `active` → `idle`/`error` with `active_run_id` set while a run is live; `awaiting_input` and the `idle` → `stale` sweep are not wired yet. As of B5 (#2345), every session-bearing dispatch also reads the session back into the agent's context — see `crewship issue checkpoints` below and `docs/guides/issue-mentions.mdx`.</Note>

List the durable, per-(issue, agent) sessions a mention has opened on an issue. Hits `GET /api/v1/crews/{crewId}/issues/{ident}/sessions` after resolving `<identifier>` to its crew via `fetchIssue`.

```bash
crewship issue sessions BE-42
crewship issue sessions BE-42 --format json
```

**Output columns:** AGENT, STATE, LAST SEQ (`last_consumed_seq`), VERSION (`agent_version`, `-` when the agent has no config history), UPDATED (relative time).

## `crewship issue checkpoints`

<Note>Work package B5 of the Issues & Routines architecture (`docs/prd/PRD-ISSUES-AND-ROUTINES-2026.md` §9.5, #2345). A checkpoint is the `done`/`plan`/`facts`/`blockers`/`next_step`/`confidence` block a session-bearing run reports when it finishes; the next run on the same session is handed the latest one as part of its §11.1 context pack, so it does not repeat completed work.</Note>

List a session's checkpoint history. Hits `GET /api/v1/crews/{crewId}/issues/{ident}/sessions/{sessionId}/checkpoints` after resolving `<identifier>` to its crew via `fetchIssue` and the session via `GET .../sessions`.

```bash
crewship issue checkpoints BE-42                    # only works when the issue has exactly one session
crewship issue checkpoints BE-42 --agent backend-dev
crewship issue checkpoints BE-42 --agent backend-dev --format json
```

| Flag | Type | Default | Description |
|------|------|---------|-------------|
| `--agent` | `string` | `""` | Agent slug or id whose session to read. Required when the issue has more than one session; a slug/id that resolves to an agent with no session on this issue errors by name. |

**Output columns:** RUN (the run that wrote it, `-` if none), SEQ (`seq_at_write`), DONE (truncated to 40), NEXT STEP (truncated to 40), CONFIDENCE, PARSED (`true`/`false` — `false` means the run ended without a valid `---CHECKPOINT---` block), CREATED (relative time).

## `crewship issue link`

Attach a GitHub pull request or GitLab merge request to an issue. Wraps
`POST /api/v1/crews/{crewId}/issues/{ident}/code-links`.

```bash
crewship issue link BE-42 https://github.com/acme/thing/pull/7
crewship issue link BE-42 https://gitlab.com/acme/thing/-/merge_requests/7
crewship issue link BE-42 https://ghe.acme.internal/platform/gw/pull/12
```

The provider is recognised from the URL's path (`/pull/` → GitHub,
`/-/merge_requests/` → GitLab), so **recognising** a self-hosted instance of
either needs no provider-specific configuration. Crewship then fetches the
request through that provider's API using a stored `GITHUB` / `GITLAB`
credential in the workspace.

Two things a self-hosted forge does still need: a credential labelled with its
host (below), and — if it lives on a private/intranet address — the operator
opt-in described in [Git links](/guides/git-links#self-hosted-forges-on-a-private-network).
Without the opt-in the fetch is refused with `blocked-host`.

For a self-hosted forge, set the credential's **account label** to the forge's
host so it is matched by host:

```bash
crewship credential create --name ghe-ro --type SECRET --provider GITHUB \
  --account-label ghe.acme.internal --value-stdin
```

Common failures (each a distinct RFC 7807 `code`): `no-credential` (412),
`blocked-host` (422 — the forge is on a private address; see
[Git links](/guides/git-links)), `credential-rejected` (502 — the token was
revoked), `rate-limited` (429), `already-linked` (409).

## `crewship issue attach`

Attach a local file to an issue. Wraps
`POST /api/v1/crews/{crewId}/issues/{ident}/attachments`.

```bash
crewship issue attach BE-42 ./crash.log
crewship issue attach BE-42 ~/Desktop/screenshot.png
```

The type is decided by the file's **extension**, against an allowlist — never by
what the client claims, because a server that trusted a client-supplied content
type would store and later serve markup from its own origin. Allowed: `.txt`
`.log` `.md` `.csv` `.tsv` `.json` `.yaml` `.yml` `.toml` `.xml` `.diff`
`.patch` `.png` `.jpg` `.jpeg` `.gif` `.webp` `.avif` `.pdf` `.zip` `.gz`
`.tgz`. Anything else is refused with a `415` that lists the set.

Maximum 25 MiB; a larger file is refused locally, naming its size, before
anything is uploaded. Attaching the same bytes twice is the same attachment, so
a retry is safe and does not add a second timeline entry.

The agent working the issue can read what you attach — see
[Issue attachments](/guides/issue-attachments).

## `crewship issue attachments`

List an issue's attached files. Alias: `files`.

```bash
crewship issue attachments BE-42
```

**Output columns:** ID, FILENAME, TYPE, SIZE, BY (`(agent)` when an agent
attached it), ADDED. Filenames are printed with control bytes stripped — they
are chosen by whoever uploaded the file.

## `crewship issue attachment`

Download one attachment by its **attachment ID** (the first column of `issue
attachments`). Alias: `download`.

```bash
crewship issue attachment BE-42 cmsf1a2b30001d5e6aa11 | less
crewship issue attachment BE-42 cmsf1a2b30001d5e6aa11 -o ./crash.log
```

| Flag | Short | Description |
|---|---|---|
| `--output-file` | `-o` | Write the file to this path instead of stdout |

Without `-o` the bytes go to stdout, so the command composes with a pager or a
pipeline. The server's stored filename is never used to choose a local
destination: it is a value someone else typed, and letting it name a path is how
a download writes somewhere you did not ask for.

## `crewship issue detach`

Remove an attachment by its attachment ID. Alias: `unattach`.

```bash
crewship issue detach BE-42 cmsf1a2b30001d5e6aa11
```

The stored bytes go too — but only if no other issue, comment or chat in the
workspace still references the same file. Attachments are stored by content, so
two issues carrying an identical file share one copy.

## `crewship issue bind-routine`

Bind a routine slug to an issue — the server stores the underlying `routine_id` (pipeline UUID) so subsequent routine renames don't break the link. Wraps `PATCH /api/v1/crews/{crewId}/issues/{ident}` with `{"routine_id": <id>}`.

```bash
crewship issue bind-routine BE-42 my-pr-review-routine
```

The slug is resolved client-side via the workspace's routine list before the PATCH, so a typo surfaces as `routine "xyz": <404>` instead of a silent no-op.

## `crewship issue unbind-routine`

Clear the routine binding (server normalises empty string to SQL `NULL`).

```bash
crewship issue unbind-routine BE-42
```

## `crewship issue bulk update`

Apply the same field updates to up to 100 issues in a single round-trip. Wraps `PATCH /api/v1/issues/bulk`. The 100-id cap is enforced both client-side (friendly error) and server-side (400).

```bash
crewship issue bulk update --ids ms_a,ms_b,ms_c --status DONE
crewship issue bulk update --ids ms_a,ms_b --priority high --assignee agent_xyz
crewship issue bulk update --ids ms_a,ms_b --labels lbl_bug,lbl_p0
```

| Flag | Type | Default | Description |
|---|---|---|---|
| `--ids` | string | _(required)_ | Comma-separated issue IDs (CUIDs, not identifiers). Empty entries are stripped; >100 entries reject locally. |
| `--status` | string | | New status for all listed issues. |
| `--priority` | string | | New priority. |
| `--assignee` | string | | Assignee ID (NOT a slug — bulk callers tend to script with IDs). Empty string clears the assignee. |
| `--assignee-type` | string | `agent` | Forwarded only when `--assignee` is non-empty. |
| `--project` | string | | Project ID. Empty string unlinks the issue from its project. |
| `--labels` | string | | Comma-separated label IDs. **REPLACES** the existing label set on each issue; empty string clears all labels. |

At least one of `--status` / `--priority` / `--assignee` / `--project` / `--labels` must be supplied. Response surfaces as `Bulk update applied to <updated>/<requested> issue(s).` — the two counts differ when some IDs were 404 or 403.
