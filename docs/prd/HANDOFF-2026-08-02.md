## 0. START HERE — where to pick up

### 0.1 In flight right now

**PR #1670 — host-aware admission control. MERGED 2026-08-02 as `e46ac44d`, and verified live on dev1 the same day.** All three load-bearing behaviours hold: a held start is visible on `crewship capacity` (header "Held container starts:") and `crewship now` ("Held for capacity:"); the gate stands down cleanly where the host memory signal is unreadable (macOS has no `/proc/meminfo` — it admits instantly, warns once, and the **concurrency** leg still binds); and the admit sits before `ContainerCreate` rather than before `EnsureCrewRuntime`, so warm reuse of a running container is not gated. That last one was proven by mutation — hoisting the admit above `reconcileExistingContainer` turns three tests red — and live, with a warm run answering immediately while a cold one was held in the same window.

**The unbounded hold is confirmed, and the reasoning that was written here to justify it was wrong.** `Admit` (`internal/admission/admission.go:204-238`) polls with the only exit being `<-ctx.Done()`; the deadlines are 30 min for a run and 45 for the scheduler. This section used to defend that by saying "the hold is fully surfaced instead". **It is not.** `ProvStepCapacityHold` is emitted by the Docker provider and rendered nowhere — the caller's stream shows `[status] Starting container...` for the entire wait, and the hold is visible only to somebody who independently runs an operator command they have no reason to run. Worse, when the hold does exhaust the budget the capacity reason is destroyed: the classifier at `internal/chatbridge/bridge.go:1117-1123` matches the substring `"container start"` and returns a generic `provision_failed`. There is also no queue, so a start held 29 minutes can lose repeatedly to fresh arrivals and then die.

All of that is **#1675**, which proposes fixing the labelling and the visibility BEFORE deciding anything about a cap — with those in place the argument for waiting the full 30 minutes is much more defensible, and the current design already produces a hard failure at 30 minutes, just a badly-labelled one.

## 1. What shipped

Seventeen PRs merged to `main` across two days. Grouped by what they fix, not by order.

**Container runtime.** `Init: true` unconditionally (PID 1 was `sleep infinity`; nothing reaped, and zombies count against `PidsLimit: 200` — a monotonic leak). `Ulimits` with `core: 0` (the exec CWD is `/output/<slug>`, a host-persistent bind, so a crashing agent wrote a core dump containing its whole credential environment to host disk). `GroupAdd` (agents had never had a supplementary group — the `User: "1001:1001"` colon form makes moby's `Sgids` branch unreachable). `MemorySwap == Memory`. `ShmSize` and `/tmp` derived from the memory limit. `RestartPolicy`, `Labels`, `StopTimeout`, `LANG`/`TZ`. Healthcheck replaced with `Test: ["NONE"]` — removing the field entirely made the daemon **inherit the image's**, which was a regression caught by review.

**Orchestration.** Preflight collapsed from **19 sequential container execs to 5**, and flat in the number of skills (was 64 at nine skills). Crew TTL now works — it was dead four ways, and no crew container was ever stopped. Host-aware admission control (#1670, may still be in flight — check).

**Memory.** Wake-time delivery: scan back to the last day with notes instead of only yesterday/today, plus a `[MEMORY GAP]` block stating today's date, the last active date and the elapsed days. `memory.search` wired to the FTS5 index (it was a line-by-line file scan). `conversation.search` removed from the prompt (it was named but never advertised or wired). The consolidator wrote pins to the **host filesystem root**, so `[PINS]` read a file nobody wrote.

**Credentials.** The agent token rode in curl's argv, where `/proc/<pid>/cmdline` (mode 0444) handed it to every sibling. An OAuth MCP binding poisoned the whole credential batch and aborted the run. A credential named `github-token` killed every run of its crew — five layers disagreed on what a legal name is.

**Providers.** Apple gained `/secrets`, the sidecar binary, an entrypoint, `--init` and rlimits — the three missing mounts had made the gap unclosable rather than merely unclosed. Capability reporting: the provider now says what it cannot honour, and four surfaces stopped reporting an egress fence that was not being enforced. `auto` was preferring the un-hardened provider while the docs promised the opposite.

## 2. How it was verified, and the standard that emerged

**Mutation testing is the standard in this repo now.** Every PR: write the test, confirm it fails for the right reason, implement, then **mutate the production code and confirm the test fails**, revert, and report the mutation. Do not skip this.

It exists because three "assert the shape, not the value" holes shipped in a single day:

- a test asserting a script *referenced* a size constant — so "no cap at all" passed
- a test counting flags across a whole prompt — so moving one from recipe A to recipe B passed
- a ulimits test asserting `positive && soft<=hard` — so `fsize: 4 KiB` (every write past 4 KiB dies) passed

**A count is almost never the property you want to assert.** Neither is presence. Assert the value, or assert the thing the value has to be *worth*.

**Two traps in running mutations yourself:**

1. A `sed`/`perl` mutation that does not match is indistinguishable from a mutation that was not caught. **Always print whether the patch applied** before believing a green test. This burned three times in one day.
2. `git checkout <path>` is **not** a revert for an untracked file. A mutation "reverted" that way stays live and contaminates the next one.

**Live verification on dev1** — the memory harness (`scripts/test-harness/test-memory.sh`) passed 4/4, and `memory.search` was proven end to end by asking an agent to find a nonce written a minute earlier. The `[MEMORY GAP]` block was proven by planting a daily note dated seven days back and reading the agent's own prompt.

## 3. Memory research — three passes, condensed

This is the part most worth not repeating. Everything below is source-verified unless marked.

### 3.1 The field verdict

**Files plus lexical search beats a vector DB for this use case, and the evidence is not close.** The four most-starred systems that ship memory — Hermes (223k★), AutoGPT, Claude Code, OpenHands — all use plain files with lexical search and **no embeddings**. Meanwhile Graphiti (29k★) has **no ANN index** (cosine computed inline over every matching edge); mem0 (62k★) **deleted** graph memory and its ADD/UPDATE/DELETE pipeline in v3, so the design everyone cites is retired code; Zep OSS is discontinued — the repo says so; crewAI deleted its four-tier memory model outright.

**Two of the most-cited systems in this space are routinely described from deleted code.** Verify against the tree before copying anything.

**Crewship's markdown-on-disk + per-tier SQLite FTS5 is the right substrate.** Do not "modernise" it into a vector store on the strength of a blog post.

### 3.2 Benchmarks are not trustworthy

No neutral, reproducible head-to-head exists. mem0's own paper has full-context baseline **72.9** beating Mem0 **66.88**. Zep criticises its own headline benchmark in §4.2. MIRIX scores 85.38 where full-context scores 87.52. Zep's LoCoMo number was published at 84%, disputed at 58.44%, conceded at **75.14%** — a spread larger than any improvement anyone claims, never third-party adjudicated. An independent audit found **6.4% of LoCoMo's answer key is wrong** and its LLM judge accepts **62.8% of intentionally wrong answers**.

`LongMemEval` is the one genuinely neutral judge-validated benchmark. **ConvoMem** (Salesforce, Apache-2.0) is the only major one from a lab with no memory product; it finds full-context wins below ~150 conversations.

**Do not manufacture a ranking from star counts.**

### 3.3 The long-gap finding — Crewship is ahead here

Surveyed Hermes, Letta, Zep/Graphiti, Cognee, LangMem, mem0, Google ADK, Claude Code, Cursor, crewAI. **Nothing tells an agent that time has passed.** Several compute the gap — for ranking (crewAI's `0.5^(age/30)`, mem0 Platform), for a human-facing UI (Claude Code shows it to the *user*, never the model) — and none says it in a sentence the model reads. Letta has `get_login_event(last_login=…)` with **no caller**. LongMemEval's median inter-session gap is **zero days**, so no benchmark would notice.

The `[MEMORY GAP]` block is genuinely novel. Its three-branch design (notes-below / out-of-window / withheld) exists so it never promises a log it could not deliver — do not collapse it back to two.

### 3.4 Extraction: what to copy, and from where

The user-model extractor is still a **no-op** in production (`NoopExtractor` / `NoopUserModelExtractor` in `cmd_start.go`). Design decided but unimplemented — see §4.

**CORRECTION 2026-08-02 (found while implementing #1669):** this section attributes three Graphiti rules to `extract_attributes`. **Only the value-origin whitelist is there.** The trend-vs-fact rule lives in `extract_summaries_batch` (~L575), and the anti-emotion exemplar list in `extract_message` (~L92) / `extract_text` (~L287). The quotes below are verbatim-correct; only the file locations were wrong. Recorded in `internal/usermodel/prompt.go`.

**Copy `extract_attributes`, not the summary prompt.** Graphiti's `graphiti_core/prompts/extract_nodes.py` has two candidates. The widely-quoted one at ~L542–595 is the entity-*summary* prompt (prose). The one you want is `extract_attributes` at **~L383–452**, which is a **whitelist of admissible value origins** rather than a blacklist of forbidden phrasings — checkable where the other is not:

> Each attribute value MUST be one of: (a) a clean value copied or directly normalized from text in MESSAGES, (b) the existing value already on the ENTITY (preserved unchanged), or (c) null / omitted.
> NEVER infer attribute values from the entity's name, from related entities, from generic world knowledge, or from prior summaries.

Also take the trend-vs-fact rule verbatim — it is the precise antidote to over-generalising:

> NEVER manufacture pattern language from a single occurrence. A single mention can support a fact, but not a trend, habit, or preference unless the text states that directly.

And their anti-emotion rule works because it **enumerates exemplars** rather than naming the category: *"Abstract concepts or feelings (joy, balance, growth, resilience, happiness, passion, motivation)"*.

**The prompt alone is measurably insufficient.** *Manufactured Confidence* (arXiv:2606.29279) measured Zep/Graphiti **with those prompts in place** still laundering attribution **12/12** and hearsay **11/12**. Every serious project moved the guarantee out of the prompt.

**Four formulations that complete it:**

- **Honcho** (`plastic-labs/honcho`) — closest to our design. Adds the **assent clause** (a third party's statement about the user counts only with the user's assent) and "no behavioral content — TRAIT and inferred PREFERENCE entries **will be rejected**". Backed structurally: `InductionSpecialist.can_update_peer_card = False`, so the pattern-inferring component is *incapable* of writing to the identity store.
- **memU v1.5.1** (cite the tag — deleted at HEAD) — two exclusions nobody else has: assistant-origin content, and *"content obtained only through the model's follow-up questions"*.
- **Veracium** — already ships our design: `SourceType = {STATED, OBSERVED, INFERRED}`, `EvidenceAuthor`, `Disclosure`, with `assertable` a computed property. Its one-line addition: **"Only extract what THIS event states. Empty lists are valid."** — telling the model that returning nothing is success.
- **OpenClaw** (`openclaw/openclaw`, ~385k★, Peter Steinberger) — **the strongest mechanism in the sweep, and it is not a prompt.** Consolidation enforces **byte equality**: the model picks *which span* and *which lifecycle action* and cannot author replacement prose. Pinned by a test literally named "rejects model-authored prose substituted for candidate evidence". Its pattern claims are arithmetic with a `minPatternStrength` gate, and that tier never writes durable memory.

**And the architecture is 24 years old.** **Personis** (Kay & Kummerfeld, Univ. Sydney, 2002, GPL-3) stores **evidence rows, never values**; resolves at read time via a named resolver; correction is **append**, never mutate; enforces an evidence type at construction (`explicit / implicit / inferred / stereotype`); two timestamps plus a `useby`. **Stated-only is then a write policy, not an architecture — relaxable later with no migration.** That directly serves the "switchable later" requirement.

### 3.5 Things to steal that are not about extraction

- **Declarative, not imperative** (Hermes): *"User prefers concise responses"* ✓, *"Always respond concisely"* ✗. Imperative phrasing is re-read as a directive in a later session and can override what the user is asking for now. **Our `[MEMORY INSTRUCTIONS]` are written imperatively and make this mistake today.**
- **"If a fact will be stale in a week, it does not belong in memory"** (Hermes).
- **Character budgets, not token budgets** (Hermes, OpenHands, Windsurf independently) — model-independent. Crewship already does this.
- **Show the model its budget** — Hermes renders `[63% — 1,386/2,200 chars]`, Letta renders `chars_current/chars_limit`. Ten lines, and the model self-manages instead of needing an eviction policy. **Not done in Crewship.**
- **Always pass the whole profile, never a retrieved subset.** LangMem reconciles against only the top-5 retrieved, so a contradicting fact outside that window is never seen. At our profile size this is free.
- **Never blob-rewrite.** Letta's `rethink` and MemoryOS's `merge=False` destroy the block; a correct fact vanishes untraceably.

### 3.6 Correction loops — an open opportunity

- **Perplexity Brain** is the reference: **per-entry provenance**, click through to the originating session, edit or delete, plus an explicit lifecycle and user corrections as a named input to the next run.
- **Hermes `write_approval: true`** is the best write-time gate: staged writes reviewed via `/memory pending | approve | reject`, auto-generated ones tagged `[auto]`. Docs name the exact problem: *"the answer to 'the agent saved a wrong assumption about me'"*.
- **ChatGPT** has the most developed management UI — searchable, per-item delete, salience up/down, version history with restore-by-date.
- **A messaging-native correction loop ("no, that's wrong, forget it") exists in NO system surveyed**, including OpenClaw despite being chat-driven — its builtin memory tools are read-only and correction means editing a file. **This is an opportunity, not prior art.**

Two documented traps: Copilot **restores** deleted memories if re-enabled within 30 days; new-experience Claude does **not** delete memory entries when their source conversation is deleted (legacy did).

### 3.7 Hermes specifically — correcting a plausible belief

Hermes is excellent on *how* memory is written and is the reason for several items in §3.5. But on stated-vs-inferred it has **no guardrail at all**, and its passive extractor `_MEMORY_REVIEW_PROMPT` (`agent/background_review.py`) **affirmatively solicits inference**:

> "Has the user revealed things about themselves — their **persona, desires**, preferences, or personal details worth remembering?"

Its `memory` tool says *"save when the user states a preference… **or you learn a stable fact**"* and its skill review treats *"Frustration signals"* as first-class. It answers the wrong-assumption problem **structurally, with the approval queue** — a legitimate alternative to forbidding inference.

Do not be fooled by its *"Provenance is declared, never inferred"* note — that is about **skill authorship**, not user facts.

## 4. The decision, and why

Recorded on issue **#1669**. The owner ruled:

1. **Stated only.** Never what the system inferred. An inference is often wrong, the person cannot rebut it because they do not know it was made, and once written it reads as fact — the prompt carries no notion of provenance.
2. **Technical, not emotionally coloured.** *"Like a CRM that creates value — more technical than emotionally coloured."* Role, ownership, declared working preferences, standing constraints. **Not** sentiment, mood, personality. *"User asked that commits carry no co-author trailer"* ✓. *"User seems frustrated with the review tooling"* ✗.
3. **Switchable later** — so the mode belongs in configuration (alongside `runtime.*` instance settings), not in a constant. And per LangMem/trustcall: **switch structurally, by not binding the tool, not by softening the prompt.** Prompt-only modes leak.
4. **Declarative, not imperative** — carried from §3.5, not in dispute.

**Still open:** whether the user can read and correct their own model. My recommendation is yes; a memory about someone they cannot see is a poor default. The schema's opt-out is "turn it all off", not "this one is wrong".

**Know before shipping: this design will score WORSE on public benchmarks.** PersonaMem-v2 and PrefEval explicitly **reward** inferring implicitly-revealed preferences. The empirical counter-argument is a peer-reviewed audit of **2,050 real ChatGPT memories** (arXiv:2602.01450, WebConf 2026): **96% created unilaterally, 52% containing psychological insight, ~16% not grounded in user context.**

## 5. ~~THE BIGGEST UNRESEARCHED GAP~~ — ANSWERED 2026-08-02

**Superseded by `docs/prd/memory-retrieval-layer.md`** (976 lines, measured against the production `memory.Engine` on three corpora, largest being this repo's real 7,788-chunk `docs/` tree). Read that instead of what follows; this section is kept for the questions it asked, not for its framing.

**The headline, and it was worse than "unresearched".** `search.go` joined quoted words with a space, which FTS5 reads as implicit AND, so a multi-word question needed every word inside one ~500-char chunk. **8 of 10 realistic questions returned zero rows** — including the `memory.search` the `[MEMORY GAP]` block tells a woken agent to run. Fixed in #1683 (zero-row 8/10 → 3/10; real-corpus top-3 5/10 → 7/10).

**Three things this section got wrong:**

- **The ordering.** Two of the seven unknowns are non-issues, one is provably inert, and the one that dominated everything was listed last.
- **Czech diacritics.** A non-issue on the markdown side — `unicode61` folds 15/15 as shipped. It is real on the *journal* path, where `ascii` indexes non-ASCII without folding, so `rozhodnuti` cannot find `rozhodnutí`.
- **RRF `k=60`.** Read from the primary source (Cormack/Clarke/Büttcher SIGIR'09: *"k = 60 was fixed during a pilot investigation and not altered"*). The value is fine; the problem is that `internal/memory/hybrid.go` fuses **disjoint** corpora, so nothing is ever cross-list and the fusion degenerates to fixed round-robin. Its own comment claiming otherwise is false at that call site (§7.8, unfixed).

**Measured and rejected, so nobody re-proposes them:** prefix indexes, the trigram tokenizer, pragma changes, `bm25()` column weights, chunk overlap, a vector database, and an aux-model query rewriter as a first stage.

**Still true, and still the honest caveat:** ten hand-written queries is a smoke test, not an eval. Enough to find an 80%-zero-result bug; **not** enough to separate the tokenizer options, which sit within one query of each other. §8 of that document specifies the read-side eval, and usefully the sidecar already journals real query text (`sidecar/memory.go:256`), so phrasing can be observed rather than invented.

### 5b. What the original section asked (kept for the record)


**Nothing in three research passes examined the retrieval and storage layer.** All of it was about *what to remember* and *how to decide*. None was about *how to store and find it well*.

Specifically unknown, and all of it decides whether `memory.search` returns the right thing — the function that the entire `[MEMORY GAP]` recovery path depends on:

- **FTS5 tokenizer choice** — `unicode61` vs `trigram` vs `porter`, and what that means for Czech content
- **BM25 column weighting** and whether `rank` should be customised
- **Prefix indexes** — worth it at our corpus size?
- **RRF `k=60`** — inherited or chosen? `episodic/hybrid.go` uses it parameter-free
- **Chunking strategy for markdown** — plausibly the dominant factor in result quality and never examined
- **SQLite pragmas** — WAL, page size, mmap, `optimize` cadence, and the cost of index maintenance on every write (`memory.write` now reindexes incrementally, added this session)
- **Query rewriting** — Hermes ships `plugins/memory/query_rewrite.py`, an aux-model pass turning the user's message into a retrieval question with injection guards. We have nothing; substring-shaped user text will miss a lot.

**Do this before implementing the user model.** Writing facts into a store whose retrieval quality is unmeasured is the wrong order.

**And there is no eval.** Nobody has published a precision-oriented benchmark for user modelling because it makes memory systems look bad. If you want a number, build it: label `(conversation, candidate fact) → {stated, inferable-but-not-stated, over-generalised, fabricated}` and score refusal-to-store on the last three, with a no-memory arm to separate model confabulation from store confabulation. ~100 transcripts, LongMemEval-sized, two people for a couple of weeks. `HaluMem` (arXiv:2511.03506) scores hallucination at the *write* stage and is the closest thing to build on.

## 5c. Runtime and use-case validation, 2026-08-02 evening — READ THIS BEFORE TRUSTING ANY "IT WORKS"

Seven runtimes were conformance-tested and then, separately, the **product's use cases** were run against real runtimes on real instances. The two are not the same claim, and conflating them is how the gaps below survived.

**Conformance (does the runtime honour our HostConfig):** docker 27/27 · podman 6.0.2 27/27 · Apple 20/20 · Colima, OrbStack, Rancher-dockerd **29/29 each** · containerd/nerdctl **impossible** (gRPC vs REST, #1687, candidate removed) · Rancher-in-containerd cannot run.

**Use cases (does the product actually work there):** three features are broken in ways no unit test could see.

| Verdict | What |
|---|---|
| **#1713 — P0** | **Backup never captures memory.** `collector.go:56` sets `ContainerMemoryPath = "/output"`; memory lives at `/crew/shared/.memory` and `/crew/agents/<slug>/.memory`, and the string `"/crew` does not appear anywhere in `internal/backup`. Proven: 34 seeded memory files, backup, delete, restore — workspace came back, memory did not. The manifest still reports `"memory_included": true`. |
| **#1708 — P1** | **Sidecars start on one code path out of thirteen.** Only `chatbridge/bridge.go` calls `EnsureCrewServices`; the other twelve `EnsureCrewRuntime` call sites — `issue start`, scheduler, webhook, pipeline runners, terminal, preflight — start the crew with no services. A crew with Redis in its manifest works in chat and runs silently database-less everywhere else. |
| **#1714/#1715/#1716 — P1** | Restore lands files `root:root` so the agent loses write access to its own data; hard-fails 500 non-atomically whenever the target volumes are not already agent-owned (the default for any fresh crew); and the documented `--as-crew` DR flow is rejected 403 on its own prescribed second step. |
| **#1706** | **Crews cannot start on Colima at all** on a default Homebrew install: the mandatory sidecar/entrypoint binds resolve to `/opt/homebrew/…` (`sidecarBinaryCandidates`), Colima mounts only `$HOME`. Conformance passed there because the harness staged its artefacts into a shareable temp dir — a true result that was misleading. |
| **#1705** | The devcontainer build shells out to the **`docker` CLI and its own `docker context`**, while the provider dials a socket. `docker context` splits them — which is exactly what `colima start` and Rancher do by default. `DOCKER_HOST` does *not*, because the CLI inherits it. The split's error is `pull access denied … may require 'docker login'`, sending the operator after a registry auth problem that does not exist. |
| **#1704** | A runtime switch leaves the old daemon's crew container **running**, under the same name, still writing to live crew memory. Two containers, one memory tree, product aware of one. |
| **#1717** | The web terminal starts the crew from the bare default image rather than its provisioned one — three call sites omit `CachedImage`. |

Also filed: #1697, #1707, #1709, #1710, #1711, #1712.

**What survives a runtime switch, measured:** `/crew`, `/workspace`, `/output` yes — but they are NOT plain binds, they are `TypeVolume` with `local` driver and `device=<hostpath>,o=bind` (`noexecBindMount`, docker.go:1134), so `docker inspect` hides the host path **and** they only survive if the new runtime's VM shares that path. `/home/agent` and `/opt/crew-tools` are named volumes and do not survive. Nothing records which runtime made a container.

**The lesson worth carrying:** every one of these passed its unit tests. Three passed a conformance suite. They were found by running the product against a real runtime and reading the result from inside the container.

## 8. Process notes worth keeping

**CodeRabbit produced no review on any PR in this batch across two days** — rate-limited throughout, while its commit status stayed green. Per CONTRIBUTING that green means "not read". Every PR in this session carries a **review record comment** stating what was and was not machine-reviewed and what was verified by hand. Keep doing that; the honest record is worth more than the implied one.

**Agents corrected the issue they were given, repeatedly, and were right to.** Roughly a third of the issues written this session contained an error that the implementing agent found by reading the code — a wrong file:line, a miscounted field, a "blocker" that was already resolved, a fix described as two lines that would have panicked. **Write issues so the implementer is expected to disagree, and read their disagreement.**

**A rebase is exactly when a guard quietly stops running.** Re-run the mutation set after every rebase.

**Read `docs/prd/` before designing anything.** This session spent a full day re-deriving an analysis that already existed in `agent-identity-signing.md`, including its locked decisions. The directory is untracked, so it never shows in a diff.
