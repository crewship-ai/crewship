# Persistent service quota contract

This opt-in backend complements Docker CPU, RAM, PID, swap, log and temporary-filesystem limits with physically preallocated ext4 volumes. Existing service declarations retain their trusted writable root and ordinary Docker volumes. No legacy contents are imported automatically.

A service requests `quota_enforced: true`. Every persistent volume specifies `quota_bytes` (32 MiB through 64 GiB, in MiB multiples); `generation` defaults to 1. Changing capacity requires a new generation and deliberate data migration. Quota services use a read-only image root, bounded `/tmp` and `/run`, and reject image-declared anonymous volumes. Docker restart policy is disabled; the durable service controller owns recovery and stopped intent.

The provider requires an explicitly configured `quota.ReferenceCatalog`. Missing or inaccessible helpers deny quota services before Docker creation. The Linux helper accepts stable crew/service/volume/generation identifiers, never caller filesystem paths. An administrator chooses its private root, socket, aggregate capacity, host free-space floor and server UID at installation. The default server UID is 1000; agent 1001 and credential broker 1002 are forbidden. Unix peer credentials authenticate both parties.

The root helper owns a locked catalog, fully allocated images and private mounts. It verifies ext4 loop devices, exact backing files, physical allocation and mount flags. Aggregate reservations include orphan images and survive process restart. Immutable capacity, root ownership and symlink checks fail closed. Durable protection references bridge helper verification and Docker volume attachment. Remove refuses protected references and active physical filesystem aliases in process mount namespaces; it never lazily unmounts an active volume.

Cleanup removes the Docker volume before releasing its protection reference and removing the helper image. If host namespace aliases prevent removal, the image remains reserved and requires an administrator to remove the alias and retry explicit cleanup. A helper restart recovers catalog mounts without changing capacity or copying data. Installation must order helper recovery before service reconciliation.

Verification includes synthetic 64 MiB physical overflow, fixed capacity and aggregate admission, helper restart with a durable canary, authenticated server access and agent/broker denial. Dedicated guest tests avoid real crew data and shared daemon changes. Helper process recovery is distinct from host reboot acceptance. Production installation, backup/restore integration for quota contents and dedicated guest reboot acceptance remain release gates; declaring this typed option alone does not satisfy them.
