# Persistent service quota contract

This opt-in backend complements Docker CPU, RAM, PID, swap, log and temporary-filesystem limits with physically preallocated ext4 volumes. Existing service declarations retain their trusted writable root and ordinary Docker volumes. No legacy contents are imported automatically.

A service requests `quota_enforced: true`. Every persistent volume specifies `quota_bytes` (32 MiB through 64 GiB, in MiB multiples); `generation` defaults to 1. Changing capacity requires a new generation and deliberate data migration. Quota services use a read-only image root, bounded `/tmp` and `/run`, and reject image-declared anonymous volumes. Docker restart policy is disabled; the durable service controller owns recovery and stopped intent.

The provider requires an explicitly configured `quota.ReferenceCatalog`. Production config supplies both `container.quota_helper_socket` and `container.quota_helper_namespace` (environment `CREWSHIP_QUOTA_HELPER_SOCKET` and `CREWSHIP_QUOTA_HELPER_NAMESPACE`). Each database has a distinct immutable namespace, private catalog and socket; restored crew IDs cannot identify a host-wide tenant. Every socket request and response validates namespace identity, and opening a catalog with another namespace fails. Missing or inaccessible helpers deny quota services before Docker creation. The Linux helper accepts stable crew/service/volume/generation identifiers, never caller filesystem paths. An administrator chooses its private root, socket, aggregate capacity, host free-space floor and server UID at installation. The default server UID is 1000; agent 1001 and credential broker 1002 are forbidden. Unix peer credentials authenticate both parties.

The root helper owns a locked catalog, fully allocated images and private mounts. It verifies ext4 loop devices, exact backing files, physical allocation and mount flags. Aggregate reservations include orphan images and survive process restart. Separate helpers serialize host free-space checks and complete preallocation through a fixed root-owned host reservation lock. Immutable capacity, root ownership and symlink checks fail closed. Durable protection references bridge helper verification and Docker volume attachment. Remove refuses protected references and active physical filesystem aliases in process mount namespaces; it never lazily unmounts an active volume.

Cleanup removes the Docker volume before releasing its protection reference and removing the helper image. If host namespace aliases prevent removal, the image remains reserved and requires an administrator to remove the alias and retry explicit cleanup. A helper restart recovers catalog mounts without changing capacity or copying data. The installer creates a per-instance root-owned catalog/socket and sets the Docker container prefix to the instance identity. Its `Type=notify` helper publishes readiness only after recovery and authenticated socket creation; the server drop-in requires and orders after that readiness. The helper uses the host mount namespace so Docker sees physical mounts. It must not acquire a private mount namespace through systemd sandbox directives.

Verification includes synthetic 64 MiB physical overflow, fixed capacity and aggregate admission, helper restart with a durable canary, authenticated server access and agent/broker denial. Dedicated guest tests avoid real crew data and shared daemon changes. Helper process recovery is distinct from host reboot acceptance. An owned dedicated guest verifies the production installer/unit and authenticated UID1000 client across Docker restart and host reboot, including physical limits and stopped policy before reconciliation. The application service-controller acceptance is separate. Service quota contents are not included in Crewship application backups; that is a documented limitation, not an additional requirement attributed to the original service PRD. No shared-host installation occurs during verification.
