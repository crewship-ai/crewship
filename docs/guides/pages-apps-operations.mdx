Pages applications are optional. Ordinary panel Pages do not need a build image or
application runtime. The supported application browser is desktop Chrome or Edge;
other browsers can use the Page panels.

## Enable Pages applications

**Prerequisite:** page project storage is configured and the server runs with
it. Set `CREWSHIP_PAGE_PROJECTS_PATH` (or `storage.page_projects_path`) to an
absolute directory outside the storage base path and restart the server once
(see [Host requirements](#host-requirements)). There is no default location yet,
and `crewship page enable` refuses to run without one; a default and enabling
Pages applications on a fresh installation without any configuration are
planned as a follow-up to #3108.

Then, on the server host, with the Crewship binary of the release you run:

```bash
crewship page enable
```

The binary carries the compiler's build context. `enable` builds the Pages tools
image from it, tags it `crewship-pages-build:<fingerprint prefix>`, labels it
`ai.crewship.pages.image=<build context fingerprint>` and **records its exact image
ID** in `<CREWSHIP_PAGE_PROJECTS_PATH>/pages-build-image.json` (mode `0600`). Run
it as the account the server runs as (with `sudo` the record is given to the
storage directory's owner) and with the server's configuration (`--config`). It
needs Docker access, and network access only during this step (base image and
compiler dependencies). It prints only the immutable `sha256:…` image ID on stdout;
progress and hints go to stderr. Running it again with the same release does
nothing, and it exits nonzero when Docker is unavailable or project storage is
not configured.

A server already running with that storage reads the record and notices it
within seconds, so no further restart or configuration edit is needed. It uses an image only when its ID equals the
recorded ID **and** it carries the exact tag and its release's label; the label
alone is never trusted, because images built `FROM` a labelled base — such as a
crew's runtime or cache image, which workspace managers choose — inherit it.
Without a verified record Pages applications are disabled: the server starts no
Pages container and the build, review and publish endpoints answer `503` with
`code: page_apps_not_enabled`. `crewship doctor` reports the state, including a
record that no longer verifies.

The compiler never pulls an image or installs project dependencies during a Page
build (`--pull=never`, `--network=none`) and always runs from the immutable image
ID. After each build the server verifies that the image's SDK/compiler/dependency
fingerprint matches its own; a mismatch is an installation error that asks you to
run `crewship page enable`.

To turn Pages applications off again, remove this version from the record and
delete the image it names (`--all` also removes the recorded images of other
versions; an image that only carries the label is never removed):

```bash
crewship page disable
```

### Pin an image explicitly

`CREWSHIP_PAGE_BUILD_IMAGE` overrides the record. When it is set, the server uses
exactly that image and never reads the record. It must be an immutable
`sha256:…` ID or digest, never a mutable tag, and the image must be built for this
release (the post-build fingerprint check still applies). Use it to pin one
specific image or when change control requires the ID in configuration:

```bash
CREWSHIP_PAGE_BUILD_IMAGE="$(crewship page enable --image-only)"
```

### Hosts without internet access

Run `crewship page enable` on a connected machine with the **same Crewship
version**, then move the image:

```bash
image="$(crewship page enable --image-only)"
docker save "$image" -o crewship-pages-build.tar
# on the target host:
docker load -i crewship-pages-build.tar
```

Then pin it on the target with `CREWSHIP_PAGE_BUILD_IMAGE=<that sha256 ID>` and
restart the server. A loaded image is not recorded: the record is written only by
a build on the server's own host.

### Docker Compose

The production Compose stack (`docker/docker-compose.prod.yml`) reaches Docker
through a socket proxy with `BUILD=0`, so `crewship page enable` cannot build from
inside the Crewship container, and the container does not read the host's files.
Run `crewship page enable --image-only` on the Docker host with a `crewship` binary
of the same version and set `CREWSHIP_PAGE_BUILD_IMAGE` to the printed ID in the
stack's environment; the server container runs that image on the shared daemon.
Do not grant the proxy `BUILD` only for this step. (Mounting the record into the
container is possible — `pages-build-image.json` in the container's
`CREWSHIP_PAGE_PROJECTS_PATH` — but the record also needs `docker image inspect`
through the proxy; the explicit image is the documented route.)

### Host requirements

The Go service needs `git` in PATH, access to Docker, and a protected absolute
`CREWSHIP_PAGE_PROJECTS_PATH` outside agent/crew mounts. The service account must
own the directory; source files must not be served as a public filesystem tree.
The build container uses UID 1001 and receives no crew mounts or credentials.

## Configure the browser-facing origins

A local installation whose Studio is `http://localhost:<port>` and whose server
listens on loopback or all interfaces needs no origin setting: when
`CREWSHIP_PAGE_RUNTIME_ORIGIN` is unset, the server derives
`http://127.0.0.1:<server port>`. A literal loopback IP is a different browser site
from `localhost`, so this is real site isolation, not the development same-origin
exception. The derived origin applies only to browsers that reach the server on
a loopback host (`localhost`, `127.0.0.1`, `::1`) directly. A request carrying a
proxy header (`Forwarded`, any `X-Forwarded-*`, `X-Real-IP`) counts as remote even
when the proxy rewrote `Host` to localhost. Studio reached on any other host or
through a proxy does not frame it and publication answers as if no runtime origin were
configured, and the same-host workbook editor is never served on it.

Every other installation (remote viewers, HTTPS, a custom domain) sets the runtime
origin; without it publication answers `503` with
`code: page_runtime_origin_missing`. Example configuration for an existing Go
service (the projects path must lie outside the storage base path, which defaults
to `/var/lib/crewship`):

```bash
CREWSHIP_PAGE_PROJECTS_PATH=/var/lib/crewship-page-projects
CREWSHIP_PAGE_STUDIO_ORIGIN=https://studio.example.com
CREWSHIP_PAGE_RUNTIME_ORIGIN=https://apps.example.net
```

Replace the example origins with domains you control. They must have different
registrable site names: `studio.example.com` and `apps.example.com` are insufficient.
Both origins need DNS and certificates trusted by the viewer's browser. Internal
DNS/CA are acceptable when clients are configured to trust and reach them.

Point the runtime reverse proxy at the same Crewship Go listener, preserving its
runtime Host header. Route only `/api/v1/pages/runtime/bootstrap` on that host and
return 404 for other paths. Do not strip or weaken Crewship's CSP/frame headers.
The browser origin (`CREWSHIP_PAGE_STUDIO_ORIGIN`) uses the existing
authenticated application proxy configuration.

A hosts-file entry on the server is not browser DNS. Verify from a viewer machine:

```bash
curl --fail --head https://apps.example.net/api/v1/pages/runtime/bootstrap
```

Then open a published Page in supported Chromium and verify the iframe renders,
its requests are confined, and the Stop control remains usable with a broken
preview. A 200 on `/pages/{slug}` alone only proves the static shell is served.

`CREWSHIP_PAGE_RUNTIME_DEVELOPMENT_SAME_ORIGIN=true` is a deliberate development
exception, off by default. It must use exactly the browser origin and shows an
isolation warning. It is not a production substitute for the second site.

## Verify a clean installation

Start with a fresh Crewship data directory and the normal administrator setup.
Using an authorized owner/crew, create a Page with an existing local producer and
a declared harmless routine. Then initialize the shipped starter, pack/save it,
build it and explicitly review/publish it with the CLI or the page editor's
review (**Edit → Content**). Commands and
expected-revision flags are documented in [Page CLI](/cli/page).

Run these checks before accepting the installation:

```bash
crewship page project fsck <slug>
crewship page project history <slug>
crewship page project publications <slug>
```

Check the application as a separate reader. Withdraw it or revoke the reader's
access and verify that cached executable content disappears. Restart the service
and confirm the draft/publication/receipt identities survive. Repeat with a fresh
restore target using the existing Crewship workspace backup/restore workflow;
source SQL without the Page project archive is intentionally rejected as incomplete.

For repository verification, `bash scripts/test-pages-apps.sh` rebuilds the tools
image from `tools/pages-build` and pins it with `CREWSHIP_PAGE_BUILD_IMAGE`, runs real Docker/API/MCP/seed checks and exercises the Go bootstrap in
Chromium. It fails when required tests are skipped. It does not replace a real
chat-agent authoring test or your deployment's DNS/TLS verification.

## Storage and recovery

Storage quotas apply across a workspace. Retention keeps required draft, live and
running-build roots plus bounded optional history; optional history can be reclaimed
before saves/builds when storage is under pressure. Older Git ancestry is truncated
at retained checkpoint boundaries without changing the retained commit hashes.
Backups carry those boundaries and complete retained source trees.

Administrators can reclaim eligible storage without removing active roots:

```bash
crewship page project compact
```

If optional history must be discarded immediately across this workspace:

```bash
crewship page project compact --discard-history --yes
```

The second command intentionally removes optional restoration history. Back up
first if it must be retained externally. It preserves current drafts, live pointer
receipts and running builds. If those active roots themselves fill the quota,
reduce unneeded active Pages/content; repeating compaction cannot remove active data.
Do not manually delete Git objects, source snapshots, artifacts or SQL pointers.

`crewship page project fsck <slug>` compares referenced source/artifact digests and
checkpoint definitions with SQL. It prints diagnostics and exits nonzero on failed
integrity checks; it does not silently repair data. Restore a verified backup or
investigate the named root. Temporary build persistence failure is reported as
`interrupted`; compiler diagnostics remain `failed` with their original error.

## Upgrade and rollback

Before upgrade, take a complete workspace backup and preserve the current server
binary/version. After installing the new binary, run `crewship page enable` again:
a release with a changed compiler profile ignores the previous image, and until the
new one exists Pages builds answer `page_apps_not_enabled` and `crewship doctor`
reports the image as outdated. Existing published artifacts continue to run;
upgrade does not automatically rebuild or republish customer applications.

Use an unpublished draft for a rebuild with the new profile. Compare the preview,
SDK interactions and action declarations, then explicitly publish. If compilation
fails, the previous publication stays live. Image fingerprint mismatch requires a
matching image; do not disable the check or change the lockfile to work around it.

`enable` keeps older Pages images, so rolling back to the previous binary finds its
own image again without a rebuild. Remove images you no longer need with
`docker rmi`, or all of them with `crewship page disable --all`, which also turns Pages
applications off until the next `enable`. If you pin `CREWSHIP_PAGE_BUILD_IMAGE`,
update it together with the binary.

V1 profile/SDK maintenance must keep existing source contracts compatible; a breaking
change requires a new explicit profile and migration instructions. A portable source
file does not promise byte-identical output on a different release. Keep old images
for rollback, subject to your installation's security update policy.

Publishing a Page freezes its UI and declared action binding, not a routine's code.
The confirmation dialog and receipt expose definition drift. The routine runner
continues to use the routine's current definition and scripts, so sensitive operation
approval must also follow that routine's own governance.

What a publication *is* fenced on is the routine definitions the reviewer was
shown: the review snapshot lists a digest for every routine a `call` action
would run, the publication sends them back as `expected_routine_digests`, and
the server recomputes and compares them inside the publishing transaction. A
routine that changed between the review and the click — an upgrade that
rewrote its script, a maintainer editing it — refuses the publication with
`409` and `conflict: "routines"`, naming the routines that moved. So when you
upgrade or edit routines that Pages call, expect in-flight reviews to be
refused and re-reviewed; that is the fence working, not a failure to work
around. `crewship page project review <slug>` shows each routine's current
state (`unchanged`, `changed`, `unknown`) before anyone publishes.
