`@opencode/cli` (v2.3.0, selected stable release as of 2026-11-16).
Upstream is `github.com/anomalyco/opencode`. The old `opencode-ai` package
tracks the 1.x line and does not select OpenCode 2.

## Install

```bash
pnpm add -g @opencode/cli@2.3.0
```

New provisioning resolves an unpinned or `latest` OpenCode tool to this exact
release before computing build inputs. Explicit V2 pins and locked tool selections are preserved. V1 pins or locks
are refused with an upgrade message. Existing images using an older installer policy are reprovisioned through
the normal crew build path when next needed. The build rejects OpenCode 1.x
binaries before publishing a ready image. The build toolchain inventory records the observed version.

Each run uses `--standalone` so a background OpenCode server cannot supply
configuration or credentials from another invocation.

Crewship generates native V2 `providers.<id>.settings` overrides and uses
`@opencode/ai/providers/openai-compatible` for custom compatible endpoints.
Go, Zen and Z.AI Coding Plan retain their native provider packages. MCP files
currently use OpenCode 2's supported legacy-config normalization.

## Auth (BYOK across providers)

OpenCode reads provider credentials from env vars based on which `provider/model` you pick. Crewship's `apiKeyEnvVarsForAdapter("OPENCODE")` accepts:

| Env var | Provider |
|---|---|
| `ANTHROPIC_API_KEY` | Anthropic |
| `OPENAI_API_KEY` | OpenAI |
| `GOOGLE_API_KEY` / `GEMINI_API_KEY` | Google |
| `OPENROUTER_API_KEY` | OpenRouter |
| `XAI_API_KEY` | xAI / Grok |
| `GROQ_API_KEY` | Groq |
| `DEEPSEEK_API_KEY` | DeepSeek |

Add any of the above as a `SECRET`-type credential and assign to your OpenCode agent.

## Command shape

```bash
opencode run --standalone --format json --model <provider/model> -- <user message>
```

`--format json` (NOT `--output-format`) emits JSONL events.

## MCP

Configured at `/output/<slug>/opencode.json`:

```json
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "fs": {
      "type": "local",
      "command": ["npx", "-y", "@modelcontextprotocol/server-filesystem", "/work"],
      "environment": {"FOO": "{env:FOO}"},
      "enabled": true
    },
    "linear": {
      "type": "remote",
      "url": "https://mcp.linear.app/sse",
      "headers": {"Authorization": "Bearer {env:LINEAR_TOKEN}"},
      "enabled": true
    }
  }
}
```

OpenCode-specific:
- Top key is `mcp` (NOT `mcpServers`)
- `type: local` (stdio) or `remote` (HTTP/SSE)
- `command` is an ARRAY (binary + args together)
- env field is `environment` (NOT `env`)
- Each entry carries `"enabled": true`
- Env-var syntax is `{env:VAR}` (NOT `${VAR}`) — Crewship translates standard `${VAR}` form on write

<Note>
Crewship auto-injects two sidecar-hosted servers under `mcp` (`injectMemoryMCP` + `injectRoutinesMCP`): `crewship-memory` and `crewship-routines`, both `type: remote` pointing at `http://127.0.0.1:9119/mcp/memory/<slug>` and `.../mcp/routines`. A user-declared server of the same name wins.
</Note>

## Memory

`AGENTS.md` is OpenCode's auto-discovered system instructions file. Crewship writes it as part of the canonical memory set. For turn-1 parity (OpenCode discovers `AGENTS.md` on the second invocation, not the first), the orchestrator also prepends the preamble inline with `[SYSTEM]/[USER]` delimiters on the first turn — turn-2+ uses the file.

## Output stream

Flat JSONL per V2 `packages/cli/src/run/noninteractive.ts`. Text and reasoning
are already deltas and must not be deduplicated as accumulated snapshots:

```
{type: "text", sessionID: "...", part: {id, text}}
{type: "reasoning", part: {text}}
{type: "tool_use", part: {id, tool, state: {status, input, output}}}
{type: "step_start", part: {}}
{type: "step_finish", part: {tokens, cost, reason}}
{type: "error", error: {type, message}}
```

V1 recordings may also carry `providerID` and `modelID`; those fields remain
accepted, but the V2 CLI does not promise to emit them.

Note `type` IS the part type at top level — NOT a nested `message.part.updated` envelope. `step_finish` (snake_case, NOT hyphen).

## Troubleshooting

**Bare model rejected** — use `provider/model` form (`anthropic/claude-sonnet-4-6` not `claude-sonnet-4-6`).

**MCP server uses literal `${VAR}` token** — Cursor/Claude `${VAR}` syntax incompatible; ensure Crewship's writer translated to `{env:VAR}`. Check by `cat /output/<slug>/opencode.json`.

## OpenCode Go and Zen

In **Credentials → Add provider**, choose **OpenCode Go** or **OpenCode Zen**,
follow the console link and paste an API key. Name the account and assign it to
the crew or agent that will use it. Then select the matching model provider in
the agent's model settings; the runner is **OpenCode**.

- Go models use `opencode-go/<model>` and the Go subscription endpoint.
- Zen models use `opencode/<model>` and the metered Zen endpoint.

These are separate accounts in Crewship even if you reuse the same upstream
key. The selected key stays in the sidecar; OpenCode receives dummy auth and
keeps its native per-model protocol. Crewship's credential slots are
`OPENCODE_API_KEY` for Zen (mapped to `opencode` in OpenCode's auth file) and
`OPENCODE_GO_API_KEY` for Go (mapped to `opencode-go`) — upstream
environment-variable conventions these are not.

Go connects using an API key, but has subscription usage limits. Its optional
**Use balance** setting can consume Zen credit after those limits; manage it
in the [OpenCode console](https://opencode.ai/auth). Crewship does not infer
remaining subscription quota or balance-overage charges from token counts.
Zen usage estimates use Zen's model prices. The console is authoritative for
both products' actual billing, limits and model access.

Model suggestions are a curated subset; use a custom native model ID for
other models your OpenCode version supports. Transport verified with OpenCode
1.18.31; update older crew installations if the provider or model is unknown.
See the official [Go](https://opencode.ai/docs/go/) and
[Zen](https://opencode.ai/docs/zen/) documentation.

## Z.AI GLM Coding Plan

In **Credentials → Add provider**, choose **Z.AI Coding Plan**, subscribe to
the [GLM Coding Plan](https://docs.z.ai/devpack/tool/opencode) at Z.AI, create
an API key and paste it below. Name the account and assign it to the crew or
agent that will use it. The runner is **OpenCode** and models use the
`zai-coding-plan/` prefix (for example `zai-coding-plan/glm-5.3`).

This is a **subscription product, not metered Z.AI API credit**: a different
endpoint (`api.z.ai/api/coding/paas/v4`), a different key and its own usage
limits. The two are separate accounts in Crewship even if the same vendor
issued both keys, and one is never used as a fallback payer for the other. A
metered Z.AI key stored under **Z.AI** does not authenticate Coding Plan
models — the run fails closed instead of switching products.

The selected key stays in the sidecar; OpenCode receives dummy auth and keeps
its native openai-compatible protocol. Crewship's credential slot is
`ZAI_CODING_PLAN_API_KEY`, mapped to `zai-coding-plan` in OpenCode's auth
file; upstream itself reads `ZHIPU_API_KEY` for every z.ai/zhipu product, so
that shared name is not used as an account identity here. Crewship does not
infer remaining plan quota or overage pricing from token counts; the Z.AI
console is authoritative for limits and billing.

Model suggestions are the catalog entries of the deployed OpenCode version
(verified against 1.18.31); use a custom native model ID for others your plan
supports. Zhipu/BigModel regional variants are separate products and are not
configured by this connection.

## Amazon Bedrock

Choose **Vault → AI providers → Add AI provider → Amazon Bedrock**. Enter a
Bedrock API key and its expiration, pick its AWS region from the list and tick
the inference profiles this account may use. A profile that is not listed can be
added by its ID. **EU profiles only** keeps the region in the EU and offers only
`eu.` profiles. These settings and the key are encrypted together. Pasted keys
require manual renewal; AWS role authentication is not offered by this method.
See [AWS Bedrock API keys](https://docs.aws.amazon.com/bedrock/latest/userguide/api-keys.html).

**Test** sends a minimal, billable Converse request to each permitted model.
Saving alone does not verify access. The result distinguishes authentication,
model-access/permissions, unavailable models and quota failures. Successful
verification describes access at that moment, not a guarantee of future quota.

In **Pays for**, choose agents or current crew members and a permitted model.
Crewship atomically assigns the account, sets the OpenCode runner and stores the
full model ID, for example `amazon-bedrock/eu.anthropic.claude-opus-5-5`.
The devcontainer's normal preparation installs the managed OpenCode version on
its next run. Later assignments are available in the saved account's **Pays for**
tab, which can also move every agent it already pays for to another permitted
model.

In **New agent → Model** (and **Edit agent → Model**), choosing **Amazon
Bedrock** asks for the account first and then offers that account's permitted
models by name. The runner is shown as OpenCode and cannot be changed; the
account, model and runner are assigned together when the agent is saved.
**Pays with** offers only logins of the agent's model provider, and a Bedrock
account only for a Bedrock agent. Crew assignment expands to explicit bindings for the current members;
new crew members must be assigned separately. A missing, expired, revoked or
withheld account stops the run, without trying another payer.

The real key remains in the credential-injecting sidecar. The agent gets dummy
authentication, a specific account routing identifier and the native Bedrock
provider configuration. Sidecar-off execution is refused. Images with an
`/etc/opencode` configuration are refused for Bedrock because managed settings
can override the runtime's privacy-critical configuration. Project configuration
and model-catalog downloads are disabled for these runs.

The EU profile restriction requires an EU region and exact `eu.` model IDs;
`global.` and bare model IDs are refused. OpenCode title/compaction configuration
uses the selected model, other providers are denied, and the sidecar independently
checks every Converse model path against the account's permitted IDs. This is a
restriction on OpenCode model inference, not a claim of whole-workspace residency:
server-side evaluators, external tools and integrations have their own destinations.

Token usage is observed incrementally from AWS EventStream responses, with a
64 KiB frame bound, and attributed to the selected account, agent and native model
under `amazon-bedrock`. Crewship's catalog prices or provider fallback are estimates;
AWS billing and quotas remain authoritative.

For the CLI, create a `PROVIDER_LOGIN` with provider `AWS_BEDROCK` using an
account JSON document through stdin or a protected file, never a secret argument:
`auth_method` is `bedrock_api_key`; `api_key`, `region`, `models`, `expires_at`
(RFC3339), and `eu_only` carry the same fields as the form. Then use:

```sh
crewship credential bedrock-assign bedrock-eu --agent worker --model eu.anthropic.claude-opus-5-5
crewship credential test-stored bedrock-eu
```

A manifest may refer to the saved credential by its stable name/ID and explicitly
grant its `AWS_BEARER_TOKEN_BEDROCK` slot to an agent using the OpenCode runner and
an allowed `amazon-bedrock/…` model. This slot identifies the account grant; the
secret is still not exported as an agent environment variable. Workspace defaults
and account pools are not fallback payers for Bedrock.
