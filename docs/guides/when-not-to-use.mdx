# When not to use Crewship

Crewship is an orchestration and governance layer for bounded agent work. It is a poor fit when the orchestration cost or uncertainty is greater than the task.

- **A latency-critical request path:** use a normal service for synchronous requests with strict tail-latency SLOs. Crewship runs are asynchronous and model latency is variable.
- **A large deterministic batch:** use a data pipeline when the transformation is known, repeatable, and cheaper to express as code. An agent adds cost and variance without adding judgment.
- **An irreversible production action without review:** use a deployment system with its own approvals and rollback. Crewship can request approval, but it does not make a risky change safe by itself.
- **A task with no usable context:** if the repository, issue, acceptance test, or required skill is unavailable, improve the inputs first. A longer prompt cannot invent missing authority.
- **A secret or regulated dataset you cannot place inside the instance boundary:** keep it out. Credentials are injected under policy, but Crewship is not a substitute for your organisation's data-classification decision.
- **A task that needs an always-on autonomous loop:** use a scheduler or event system with explicit triggers. Crewship routines are queue-and-trigger based and pause at durable waitpoints.

Use Crewship when an agent can make progress in a bounded workspace, the outcome can be checked, and a human or policy can own the decision when the work crosses a trust boundary. Start with [First projects](/guides/first-projects) and stop after the rung that proves your use case.
