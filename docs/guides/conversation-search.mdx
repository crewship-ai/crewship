# Conversation Search

## Overview

**Conversation search** lets you (or an agent) find earlier chat turns by
keyword. Every message in a chat session is persisted twice: as the durable
JSONL session log on disk, and as a searchable row in a full-text index. The
search runs over that index and returns the matching messages ranked by
relevance, each with its source session id and timestamp.

It answers the question *"what did we discuss — or decide — before?"* without
you having to remember which session, or even which agent, it happened in.

This is distinct from the [Crew Journal](/guides/crew-journal) `recall`
surface, which searches the workspace-wide *event* memory (runs, peer
conversations, escalations). Conversation search reads the chat transcripts
themselves.

## Scope and isolation

A search runs in one of two scopes, and both are decided by the server:

- **Agent scope** — you name an agent. The query is filtered to that agent's
  `agent_id`, and the API verifies the agent belongs to your workspace first.
  This is the only scope an agent-initiated search can ever have: the agent
  identity comes from the runtime, so one agent can never read another's
  chats through this surface.
- **Workspace scope** — you name none. The API reads the agents in *your*
  workspace — from your session, never from the request body — and runs one
  ranked query across them. This is what ⌘K in the dashboard sends, and what
  the CLI does by default. It spans at most 400 agents (the most recently
  created ones).

In both scopes the search backend only filters; the API decides which agent
ids it may ever see, and drops any hit outside that set.

Two limits apply to both scopes:

- **Search-from-now-on.** Only conversations recorded after this feature
  shipped are indexed. There is no backfill of older history — the index
  fills as new turns land.
- **Keyword (BM25) only.** This first release ranks by BM25 full-text
  relevance. There is no semantic / embedding re-rank yet.

## CLI

Use `crewship conversation search` (alias: `crewship conv search`):

```bash
# Search every agent in the workspace
crewship conversation search "deploy pipeline"

# Narrow to one agent (slug or id); cap the number of hits
crewship conversation search "rate limit" --agent backend-bot --limit 50

# Machine-readable output for piping to jq
crewship conversation search "auth" --format json | jq '.hits[].session_id'
```

`--format yaml` and `--format ndjson` are honoured too, like every other read command —
see [Output Formats](/cli/overview#output-formats).

Arguments and flags:

| Argument / flag | Meaning |
|-----------------|---------|
| `<query>` | The search text. Remaining args are joined with spaces. FTS5 operators (`OR`, `NEAR`, `*`) are treated as literal words, not query syntax. |
| `--agent <slug-or-id>` | Narrow to one agent. A slug is resolved to its id. Omit it to search every agent in the workspace. |
| `--limit <n>` | Maximum number of hits (1–100). Defaults to 20; out-of-range values (`≤0` or `>100`) fall back to the default of 20. |
| `--format json\|yaml` | Emit the raw result envelope instead of the table view. |

Each hit shows its timestamp, the message role (`user` / `assistant`), the
agent that said it, the source `session_id`, and a snippet of the matched
content.

The agent-first positional form this command shipped with
(`crewship conversation search backend-bot "deploy pipeline"`) still works:
with no `--agent` and several arguments, the first is read as an agent.

## Dashboard (⌘K)

The command palette carries a **Conversations** group. Unlike the entity
groups, which are fetched once when the palette opens and filtered in the
browser, this one asks the server as you type (debounced, and each keystroke
cancels the request before it), because messages are the largest thing in a
workspace and a match is a phrase rather than a name.

A row shows the matched snippet, the agent that said it and how long ago;
selecting it opens that thread at `/chat/<agent-slug>?session=<chat-id>` — the
same deep link a chat notification uses.

Two keystrokes are the minimum before anything is sent. If the endpoint is
not configured on the deployment, or the search fails, the group simply does
not appear: nobody explicitly ran this search, so it never raises an error.

## API

`POST /api/v1/conversations/search`

Request body:

```json
{
  "agent_id": "agent_123",
  "query": "deploy pipeline",
  "limit": 20
}
```

| Field | Required | Notes |
|-------|----------|-------|
| `agent_id` | no | Omit it to search every agent in the caller's workspace. When given, it must belong to that workspace. |
| `query` | yes | Free text. Operators are neutralised to literal words. |
| `limit` | no | 1–100; defaults to 20. Out-of-range values (`≤0` or `>100`) fall back to the default of 20. |

Response:

```json
{
  "count": 1,
  "query": "deploy pipeline",
  "scope": "workspace",
  "hits": [
    {
      "id": "msg_abc",
      "session_id": "sess-42",
      "agent_id": "agent_123",
      "agent_slug": "backend-bot",
      "agent_name": "Backend Bot",
      "role": "user",
      "content": "please deploy the staging pipeline tonight",
      "ts": "2026-06-01T10:00:00Z"
    }
  ]
}
```

Status codes:

| Code | When |
|------|------|
| `200` | Search ran; `hits` may be empty. |
| `400` | Missing `query`, or a malformed query. |
| `401` | No workspace in the request context. |
| `404` | The agent does not exist in your workspace. |
| `503` | The search mirror is not configured on this deployment, or (workspace scope only) the configured backend cannot span agents. |

## Agent tool

<Warning>
  `conversation.search` is **not advertised to agents today**. The memory MCP
  server's `tools/list` publishes `memory.read`, `memory.write`,
  `memory.search` and `memory.append_daily` only, so a model never sees the
  tool — and its backend is the host database, which the in-container
  dispatcher cannot reach. Search conversations from the HTTP API or the CLI
  above.
</Warning>

The tool's schema and handler ship, ready for a transport that can reach the
mirror from a sandbox. It is agent-scoped by construction — the agent identity
comes from the runtime, never from the model, so an agent could only ever
search its own history — and where the mirror is not reachable it returns a
recoverable "not available" result rather than failing the run.

## How it works

When a chat turn is persisted, the conversation store writes the JSONL line
(the durable source of truth) and, when a database mirror is configured,
dual-writes a row into a `conversation_messages` table backed by an
SQLite FTS5 external-content index. Search joins the index, filters by the
agent set the API resolved, and orders by BM25. The JSONL files remain authoritative; the
index is a rebuildable mirror, so a transient write failure costs at most the
searchability of a single turn, never the turn itself.

## Searching from the chat sidebar

The chat sidebar has a search button, and **Ctrl/Cmd+Shift+F** opens the same dialog. The shortcut
is on for everyone (it is not behind a flag): it works only outside text fields, never while Alt is held, and
it never fires inside the message box, so it does not take over typing. If your browser or operating system
already uses that combination, use the button instead. Ctrl/Cmd+K stays the global palette. The dialog has three tabs:

- **This chat** — matches inside the open agent session.
- **All chats** — every agent conversation you can see.
- **Files** — not available yet; the tab says so rather than showing zero results. (Developers can enable sample data with `NEXT_PUBLIC_CHAT_SEARCH_FILES_FIXTURES=true`; the tab is then labelled "Sample data — file search is not available yet" and its rows are disabled, not links. It is not real file search.)

Type free text plus optional filters: `from:agent` (any agent's replies), `from:ada` (that agent's own replies),
`in:ada` (one agent), `has:link`, `has:code`, `has:tool`, `after:2026-10-01`,
`before:2026-10-31`. An unknown filter is reported, not ignored. Use the arrow
keys to move through results (Left/Right switches tabs) and Enter to open the exact message; Escape closes.

`from:` matches a hit only when it is an agent reply, so `from:ada` never returns your own messages in Ada's chat. `from:me` (also `user` and `you`) is not supported yet: group agent chats are searched too and a hit does not say which person wrote it, so the dialog says it needs the message author from the server instead of guessing. An agent's name or slug wins over all the keywords (`agent`, `assistant`, `user`, `you`, `me`), so an agent called Agent or User can be selected.

Only `in:` is applied by the server. `from:`, `has:`, the date filters and
**This chat** are applied to the server's 50 best matches, so when that page
was full the dialog says the result is **partial** instead of claiming nothing
matched. A full page of 50 (the requested limit; the response has no has-more flag) with nothing filtered out is shown as **First 50 results, more may exist**, because search has no next page yet. An unsupported `from:` value is reported, not ignored. Rooms and direct messages with people are not covered by this search
yet.

`after:` is inclusive and `before:` is exclusive, both at 00:00 UTC of the given date, while result dates are shown in your local time. `in:` cannot be combined with **This chat**. If the matched message is not shown as its own entry in the open conversation (for example it was merged into an earlier reply), the dialog says it could not locate it rather than saying it is gone.
