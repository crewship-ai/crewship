# Your First Crew

A **crew** is a team of AI agents that work together on tasks. Each crew runs inside a shared Docker container, and agents communicate through the sidecar proxy.

## Core Concepts

<CardGroup cols={3}>
  <Card title="Crew" icon="ship">
    A named team with a shared container, identity, and purpose. One container per crew (not per agent).
  </Card>
  <Card title="Agent" icon="robot">
    An AI-powered worker with a persona, role, and tool profile. Runs as `Exec` inside the crew container.
  </Card>
  <Card title="Mission" icon="flag">
    A multi-task objective orchestrated by a Lead agent. Tasks can have dependencies and retry logic.
  </Card>
</CardGroup>

## Agent Roles

Every agent has one of two roles that determines their capabilities:

| Role | Purpose | Capabilities |
|------|---------|-------------|
| **AGENT** | Individual contributor | Executes assigned tasks, writes code, runs tools |
| **LEAD** | Team orchestrator | Assigns tasks to agents, creates missions, monitors progress |

<Note>
  Roles are functional, not hierarchical. A Lead is an equal colleague with orchestration responsibility -- not a boss. This is a core Crewship philosophy (the "Crewship Adventure" ethos).
</Note>

## Creating a Crew

<Steps>
  <Step title="Navigate to the Crews page">
    Open the Crewship dashboard and click **Crews** in the sidebar.
  </Step>

  <Step title="Create a new crew">
    Click **New › New crew** (or press **C**) and fill in the details — name,
    slug, icon and colour, what the crew should do — then choose how it starts:
    **Suggest a team** (the lead proposes agents from your description; you can
    rename or remove any before anything is created), **From a template**,
    **Import crewship.yaml** or **Empty crew**. The fields map to the API:
    - **Name:** A human-readable name (e.g., "Engineering")
    - **Slug:** URL-friendly identifier (e.g., `engineering`)
    - **Icon:** A lucide icon name (`terminal`, `rocket`, `clipboard`, etc.) -- not emoji
    - **Color:** A palette ID (`blue`, `emerald`, `violet`, `amber`, `rose`, `cyan`, `lime`, `fuchsia`) -- not hex
  </Step>

  <Step title="Add agents to the crew">
    In the app, **New ▾ › New agent** (or **A**) opens a four-step wizard:
    **Who** (start from a blank agent, a template or a copy of an existing
    agent; name, title, description, crew and role), **Model** (provider,
    runner, model, tool access, longest run), **Access** (the provider account
    it pays with and its skills — assigned right after the agent is created;
    a refused assignment is named and the agent stays) and **Instructions**
    (its own instructions, chat suggestions, memory, and a summary of what
    Create agent will do). Each agent needs:
    - **Name and slug:** Identity (e.g., "Viktor" / `viktor`)
    - **Role title:** Human-readable role (e.g., "Backend Engineer")
    - **Agent role:** `AGENT` or `LEAD`
    - **Crew:** Optional for an `AGENT` — leave it empty for a **workspace-wide agent** (no crew; you can assign one later). A `LEAD` must belong to a crew.
    - **CLI adapter:** Which coding CLI to use (`CLAUDE_CODE`, `CODEX_CLI`, `GEMINI_CLI`, `OPENCODE`, `CURSOR_CLI`, `FACTORY_DROID`)
    - **Tool profile:** Controls available tools:
      - `MINIMAL` -- Read-only: Read, Glob, Grep (plus MCP discovery)
      - `CODING` -- Full coding tools
      - `FULL` -- All tools available
    - **System prompt:** The agent's persona and instructions
    - **Memory enabled:** Toggle persistent memory across sessions
  </Step>

  <Step title="Assign credentials">
    Add API keys for the LLM provider your agents will use. Credentials are encrypted with AES-256-GCM and injected via the sidecar proxy -- never as environment variables.

    ```
    Settings -> Credentials -> Add Credential
    ```

    Agents created from templates or through the internal API have credentials auto-assigned (`autoAssignCredentials` matches on provider). Agents created via the CLI or UI assign credentials manually -- creation does not prompt for one. An agent that ends up with none, and no crew credential to inherit, is flagged on its overview canvas: the Credentials cell warns "No credential assigned" instead of staying quiet.
  </Step>
</Steps>

## The Crews screen

`/crews` is the fleet: crews in the side panel, the open crew or agent beside
it. On a desktop it opens straight on a crew (the last one you looked at, or
the first in the panel); on a phone it opens the list.

- **The panel** starts with **Views** — *All crews*, *Needs you*, *Working*,
  *Idle* and *Temporary hires* (keys 1–5) — then the crews, grouped by status
  (*Needs you*, *Working*, *Idle*) or **A–Z**. A crew row shows how many things
  wait for a person, or a live dot while it works. The open crew's agents are
  listed under it: the lead with a star, a temporary hire with its time left
  (or *hire* while it waits for approval, *expired* after). Agents without a
  crew are listed at the end. The view and the grouping are kept in the URL
  (`?status=`, `?group=`), and `/` jumps to the search.
- **The top bar** names where you are (`Crews › Research`) and carries
  **Activity** (the crew's activity), **Terminal** (opens the dock),
  **Chat with** the lead, the crew menu (*Restart agents*, *Copy CLI command*,
  *Copy link*, *Delete crew…*) and **New** (*New crew*, *Crew from a
  template*, *Import crewship.yaml*, and for the open crew *New agent* and
  *Hire a temporary agent*). **C** opens New crew and **A** New agent.
- **A crew page** has one head — status, lead, number of agents, autonomy,
  image and container — and six tabs: **Overview** (what needs you, each row
  with its verb: *Build now*, *Install gh*, *Connect*, *Inspect*, *Review*;
  what the crew is doing, Health, the Team and what it works on), **Team** (the
  agents, temporary hires with *Approve*, the time left or *Rehire*, and how the
  team works), **Tools and access** (which agent has which skill and
  credential), **Environment**, **Memory** and **Settings** (profile,
  escalations, autonomy, people, the command line and, for admins, the
  danger zone).
- **Environment** is a set of cards, filtered by a segment (*All*,
  *Container and image*, *Tools*, *Network*, *Services*, *Advanced*):
  **Container** (state, size, the containers with their load; *Start* / *Stop
  container*, *Restart agents*, *Open terminal*), **Image** (*Change*, whether
  a newer image exists, *Rebuild…* with a cached or a clean build, build
  history), **Tools and versions** and **Features** (*Add a tool*, *Add a
  feature*, remove one, or edit the tool versions as text), **Network** (with
  *Private network* for admins and whether the host enforces it),
  **Resources**, **Services next to the agents**, **Preview links**
  (*Revoke*), **Environment variables**, **Security** and **Folders in the
  container**. Typed values save through the page's one save bar, and saving
  network, resources or tools restarts the container; switches and actions
  apply at once.
- **Memory** on a crew shows CREW.md (who wrote it last, version history) and
  every agent's AGENT.md; on an agent, *Remember between runs*, what the agent
  knows about you (*Forget* asks first) and its AGENT.md with *History*,
  *Export* and all notes.
- **An agent page** links back to its crew and has the tabs **Overview**,
  **Instructions**, **Model and limits**, **Tools and access**, **Memory** and
  **Settings**. Edits save through the same save bar. **Instructions** also
  says where the agent's instructions come from, lists their history, offers
  *Reset to crew default…* (it asks first) and shows the crew default with an
  editor; **Overview** includes *Messages from teammates*. Switching tabs
  with unsaved edits asks first: *Stay*, *Discard* or *Save and leave*.
- The tab is part of the link (`?tab=`); older links such as `?tab=work`,
  `?tab=skills` or `?tab=credentials` land on the tab that holds that content.
  See [Agent memory](/guides/agent-memory) for the Memory tab.

Lists are windowed at 500 rows; when a fleet is larger the panel says how
many rows are not loaded and loads them on ask.

## Running Your First Mission

<Steps>
  <Step title="Send a message to a Lead agent">
    Navigate to the crew chat and send a task to the Lead:
    ```
    "Analyze the current directory structure and create a summary report"
    ```
  </Step>

  <Step title="Lead orchestrates the work">
    The Lead agent can:
    - Execute the task directly
    - Assign subtasks to other agents via `/assign`
    - Create a multi-task mission via `/mission/create`
  </Step>

  <Step title="Monitor progress">
    Watch real-time progress in the chat panel. Assignments appear with status indicators:
    - **PENDING** -- Waiting to start
    - **RUNNING** -- Agent is working
    - **COMPLETED** -- Task finished successfully
    - **FAILED** -- Task encountered an error
  </Step>
</Steps>

## Crew Container Architecture

When a crew starts, Crewship creates a shared container with this filesystem layout:

```
/crew/
  agents/
    {agent-slug}/           # Each agent's home directory
      .memory/              # Persistent memory (AGENT.md, daily/*.md)
      .mcp.json             # MCP server configuration
  shared/                   # All crew members can read/write
/output/
  {agent-slug}/             # Output files visible in Files panel
/secrets/
  {agent-slug}/             # Read-only credential files
    .env                    # Maps env var names to file paths
    GH_TOKEN                # One file per credential
/workspace/                 # Temporary scratch space
```

<Tip>
  Files agents create in `/output/{slug}/` are immediately visible in the Files panel of the UI. Use the shared crew space at `/crew/shared/` for cross-agent collaboration.
</Tip>

<Note>
  **Agents in a crew trust each other.** All agent processes in the container run as one Unix user (UID 1001), so the per-agent directories above are an organizational convention, not a security boundary — any agent can read a sibling's home, output, and `/secrets/{slug}/` files. The enforced isolation boundary is the crew container itself. Agents that must not see each other's credentials belong in separate crews; see [Credentials > The trust boundary is the crew](/guides/credentials#the-trust-boundary-is-the-crew-not-the-agent).
</Note>

## System Prompt Assembly Order

For the full 2-stage breakdown, see [Architecture > System Prompt Assembly](/architecture#system-prompt-assembly-order). When an agent starts, its system prompt is assembled in this order:

```
1. Crewship system preamble (filesystem layout, credentials docs)
2. [CREWSHIP ETHOS] block (role-specific adventure context)
3. [AGENT IDENTITY] (name, role, crew)
4. User-defined system prompt (persona)
5. [SKILLS AVAILABLE] (injected skill playbooks)
6. [CREW CONTEXT] (Lead only: crew member list + API docs)
7. [PEER CONTEXT] (non-Lead agents: peer communication)
8. [CONVERSATION HISTORY] (recent messages, 60% of remaining token budget)
9. [AGENT MEMORY] (persistent memory, 40% of remaining token budget)
10. [MEMORY INSTRUCTIONS] (how to write/read memory files)
```

The token budget is managed with a 60/40 split: 60% for conversation history, 40% for memory context. The maximum system prompt token budget is defined in `internal/tokenutil/`.
