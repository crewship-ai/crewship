# Activity

## Overview

**Activity** lives at `/activity`, under the **Run** group of the sidebar. It answers the question people arrive with — *what is happening, and where do I look* — as a stream: a left rail listing what has been **active in the loaded window**, and a main column that changes with whatever the reader picked.

The page is built from three independent reads:

- **The workflow index** — `GET /api/v1/chains` (`hooks/use-chains.ts`), one row per chain. A *chain* is every run sharing one `chain_origin`: the rule or person that started it, the routine runs it caused, and the agent work those dispatched. It is fetched on demand, not streamed.
- **The routine runs** — `GET /api/v1/workspaces/{ws}/pipeline-runs?since=` and the run's own records, which feed the [home](#the-home) and the [run page](#a-run-page).
- **The journal** — `GET /api/v1/journal`, which feeds the filtered event list and the opened-event detail. It streams over SSE and falls back to polling.

The two are deliberately separate: the rail must still answer "where can I go" when the current filters answer nothing.

<Note>
`/activity` used to be a single-canvas run **trace**: a rail of runs, one run's execution chain on a ReactFlow canvas, a step side panel. That page is gone — with its saved views, heatmap toolbar, step selection and inline waitpoint buttons. A run's execution was not lost; see [Where the run trace went](#where-the-run-trace-went).
</Note>

## When to use it

- **Something ran and you want to know how it went.** A row opens [the run](#a-run-page) — its status, why it failed or what it waits for, its steps with every attempt, what it caused further down the chain, what it is linked to and changed, and its routine's previous runs.
- **You open the page to see the day.** The [home](#the-home) says in one sentence how many runs there were, what is live, what needs you and what could not finish, and draws every run on its routine's lane.
- **You want a routine's runs, not its definition.** **Group by → Routine** opens a routine's runs grouped by the hour, with each run's own result on the row instead of its id. The definition stays on [Routines](/guides/routines).
- **You want to know what your agents did.** **Group by → Agent** lists agents that took work in the window, how much, and in which workflows.
- **An issue moved and you want to know what moved it.** **Group by → Issue** lists issues touched in the window with the routine and agent that reached each one.
- **You are chasing a failure.** The **Could not finish** status row narrows both the rail and the feed.
- **You want accepted work or received webhooks.** The **Ledger** rows at the bottom of the rail open the [work queue and webhook deliveries](#ledgers).

To *author* a routine, go to [Routines](/guides/routines). A plain approval can be decided from the home's **Needs you** card or on the run page — it is the same item as in [Inbox](/guides/inbox), and an approval with a decision form opens on the run, where the form is. To read the raw event log, use `/journal` (workspace OWNER and ADMIN only, see [Crew Journal](/guides/crew-journal)).

## Key concepts

| Term | What it means here |
|------|--------------------|
| **Chain** | Every run sharing one `chain_origin`. The unit the index groups by, and a valid anchor for `GET /api/v1/chains/{anchor}`. |
| **Run row** | One chain in the rail. Every chain of the window is listed — a plain run of a routine as much as one that composed something. |
| **Group by** | Which catalogue the rail lists: Time (the default), Issue, Agent, Routine — the `?lens=` value. All four are derived from the same loaded chain list, so no two can disagree about what happened. |
| **Row title** | The routine's name, as on the Routines rail. The second line says what started it in short words — `schedule`, `by hand`, `webhook · contact-form`, `rule · on issue closed`, `from OPS-1` (`startedByWord`) — then the duration and what it touched. The right edge says when. |
| **Sentence** | The row's tooltip — the whole *shape*: `file a follow-up when an issue closes → Follow up on close → riley → ENG-7`. |
| **Handle** | The last 8 characters of the chain origin, in the row's tooltip. Derived, never generated. |
| **Status row** | All · Waiting for you · Running · Completed · Could not finish — the Routines rail's words and order. One choice. Counts **chains**, which is what the list under it holds. |
| **Stop / trail** | Where the reader is standing. Every pick is one stop on a path; the back-bar above the column is the walk — **‹ Back to activity** returns to the overview (as **‹ Back to issues** does), and each crumb after it jumps to that stop; `Esc` steps one stop up. Styled and animated like the Issues and Routines back-bars. Capped at 6 stops (`ACTIVITY_MAX_DEPTH`), and the trail says when earlier stops fell off. |
| **Drill-down** | What a row leads to: a run's steps, an issue's "what reached it", an agent's work, a routine's runs. |

## The rail

One column, and it is navigation, built from the same sidebar kit as [Issues](/guides/issue-detail) and [Routines](/guides/routines): a search box, a filter popover, a **Group by** button, then a collapsible **Status** section, the list, and the **Ledger** rows. Every *narrowing* lives in the popover; every *place you can go* is a row. There is no tab strip above the page and no second row of tabs in the rail.

### Group by

The View button (the rows icon beside Filter) groups the list. Each grouping lists only the members that were **active in the loaded window**. An issue nobody touched today is in [Issues](/guides/issue-detail), not here.

| Group by | A row is | Sorted by |
|------|----------|-----------|
| **Time** (default) | One chain: a run of a routine and everything it caused | Time bucket, then newest first |
| **Issue** | An issue something touched in this window — not the backlog | Busiest first (chains touching it) |
| **Agent** | An agent that took work in this window | Busiest first (assignments) |
| **Routine** | A routine that **ran** in this window — not the catalogue | Busiest first (runs, not chains) |

Under **Time**, every chain of the window is listed and grouped into **Active now**, **Today** and **Earlier**. "Active now" is a *state*, not a time: a chain parked on a human approval since Tuesday is the most urgent row on the page and must not sort to the bottom by its timestamp.

Each row wears its routine's own icon and colour (the same derivation the Routines rail uses), a status dot notched into the corner, a halo while something is live, the routine's name, `could not finish / waiting for you · what started it · duration · what it touched`, and how long ago it was active.

### Status

A collapsible section with one row per bucket, in the Routines rail's order and words: **All**, **Waiting for you**, **Running**, **Completed**, **Could not finish**. Every row is always there — a bucket holding nothing dims rather than disappearing, so no row moves because its neighbour emptied. The count pill and the selected row are the Routines rail's, to the class (`railStatusRows` in `lib/activity-rail.ts`).

The counts are taken over the window **with the search applied but not the status**, so a number survives its own selection: counting after the pick would render "Could not finish 3 · Waiting 0 · Running 0" — what is left rather than what there is to pick.

The same choice narrows the journal query server-side (`active`/`waiting` become an `entry_type` filter, `failed` becomes `severity=error`); `done` is the one bucket with no server-side expression, so it is filtered client-side.

**Waiting** is narrowed twice, and the second pass is the one that matters. The journal is an *event log*, so the `entry_type` query returns ask-shaped **rows** — including an `approval.requested` whose approval was granted an hour ago, and a `peer.escalation` that is the *end* of one (ask and answer share that one entry type, separated only by `payload.state`: `pending` is the ask, and `resolved`, `expired` and `cancelled` are the three ways it ends). A row is only still waiting on somebody while its ask is **open**, so each ask is joined to its answer on kind + id over the loaded window, and the answered ones fall into **Completed**.

The join needs both halves in the window, so the `waiting` query asks for the **answers** as well as the asks — `approval.granted` / `denied` / `cancelled` / `timeout` and `keeper.decision`, which are filed under the Security facet and would otherwise be excluded server-side. They never reach the feed: the same narrowing that retires their asks files them under **Completed**.

That costs window. The journal pages by a fixed **row** count from the newest end, so answer rows occupy slots that asks used to have, and an open ask pushed past the last row would drop out of Waiting altogether — the opposite of the bias below. Only this scope therefore pages to the API's ceiling (500 rows rather than 300), which holds comfortably more asks than the ask-only query did. Beyond that ceiling the boundary is the usual one, with **Load older** under the list.

An ask whose answer lies outside the window, or that carries no id to join on, stays under Waiting: over-reporting one row is a smaller failure than hiding something a person is blocking on. An escalation in a state this classifier has never seen is treated the same way — unrecognised is not the same as answered.

One function (`scopeOf` in `lib/activity-stream.ts`) does this for the feed list, every row's status dot and the Overview's **Waiting on you** card, so those three cannot disagree. The rail's **status rows** are the exception, and deliberately so: they count *chains* (`chainScopeCounts` over the `ChainSummary` index, ultimately the server's `status` column) rather than journal rows, because the chain index is fetched independently of the scope facet and so can still answer for the buckets the journal query did not fetch. A status row counts chains; the feed beside it counts entries.

### Search and filters

The search box narrows two things at once: the rail's workflow list (client-side, over the loaded index page — matching the routine's name and slug, what started the chain, the handle, and the identifiers, titles and agent names it touched) and the journal query (server-side, as `q`).

The **Filter** trigger carries a count of active narrowings and opens a popover holding:

| Facet | Notes |
|-------|-------|
| **Crew** | Dropping a crew drops its agents with it. Rendered only when the workspace has crews. |
| **Agent** | Narrowed to the selected crews when any are picked. |
| **Issue** | An issue focus goes to the server as `mission_id`. |
| **Routine** | A routine focus cannot go to the server — the slug lives inside the payload — so it narrows the **loaded window** only, and the chip says so. |
| **Time range** | Past hour / Past 24 hours / Past 7 days / Past 30 days. 24h is the default, and selecting it is not counted as a filter. |
| **Source** | Runs, Routines, Issues, Security, Cost, Memory, Comms, System. |
| **Severity** | Warning, Notice, Info. |
| **Noise** | *Show system telemetry* — puts back `container.metrics`, `file.written`, `network.egress`, `exec.output_chunk` and friends, which are excluded by default because they were 86% of the feed. |

<Note>
`error` is deliberately absent from Severity and `human` from Source: they **are** the Could-not-finish and Waiting-for-you status rows, and one filter reachable from two controls is how the two quietly contradict each other. See `lib/activity-rail.ts`.
</Note>

A filter combination that matches nothing says so — "the loaded window holds N events, and none of them satisfies all M filters at once. This is an empty question, not a quiet system." — with one button that clears everything. An empty grouping gets one of five distinct sentences depending on *which* emptiness it is (`emptyLensCopy`), because they want different actions from the reader.

## The main column

One selection, one column — never a stack.

| What is selected | What the column draws |
|------------------|-----------------------|
| Nothing, grouped by Time, status **All**, no filter | [The home](#the-home) |
| Nothing, grouped by Issue / Agent / Routine | That grouping's own dashboard |
| A status row, a search, a crew/agent/issue filter, a pinned crumb, or a node walked into from a graph | The feed as a list, with **Load older** |
| A run row whose chain starts at a routine run | That [run's page](#a-run-page) |
| A run row rooted in agent work | The [workflow page](#a-workflow-page) |
| An issue / agent / run / routine row | Its [drill-down](#where-a-row-leads) |
| A feed row | That [event, opened](#opening-one-event) |

### The home

The time view's home is built from **runs**, not journal events, and answers in the order a person asks on arrival (`components/features/activity-stream/activity-home.tsx`, rules in `lib/activity-home.ts`):

| Part | What it says |
|------|--------------|
| **Header** | One sentence — `14 runs · 2 running · 1 needs you · 3 could not finish · $0.42` — with a **24 h / 7 d** switch. A zero is left out, except "nothing needs you". |
| **Needs you** | The approvals waiting (`GET …/pipelines/waitpoints`), the same items as Inbox. A MANAGER or above can **Approve** or **Reject** a plain approval here; one with a decision form, and everyone else, gets **Open run**. |
| **Right now** | Runs that are running or waiting, and **Up next** — the next planned runs from the routines calendar. |
| **What ran** | One lane per routine across the window, every run a bar coloured by outcome; click a bar to open the run. Live and failing lanes come first; the quiet tail folds into a count. Drawn from the newest 200 runs of the last 7 days, and it says so when that cap cuts the window. |
| **Problems** | Failures grouped by cause (`GET …/pipelines/runs/errors`), but only causes that failed in the last 7 days — the server's groups cover all time. Opens the latest failure. |
| **What changed** | The issues the window's runs created and touched, from the chain index. Page writes are not listed yet: the API has no "pages written by this run" read. |
| **Outcomes** | Seven days by outcome, with the share that finished. |
| **Latest runs** | One line per run — what it came to (`HTTP 502 Bad Gateway`, `Finished in 4.7s`, `Waiting for a decision`) and what started it. Admins get a **Raw events in Journal** link. |

The home covers the whole workspace, so it shows only while nothing narrows the page. A crew, an agent, a search or a pinned crumb asks a narrower question, and the filtered event list answers it.

### Issues, Agents, Routines

Each grouping owns the column, so picking one changes what is *shown* and not only what is selected.

- **Issues** — Touched / Created by agents / Changed / Agents involved, then one line per issue carrying the issue's real status and priority glyph, with an indented `↳ routine → agent` line that opens the workflow behind it.
- **Agents** — Agents at work (of N hired) / Assignments / In workflows / Busiest, then one line per agent with a proportion bar and what it worked on. "In workflows" is the wall clock of the chains the agent worked in, **not** billed agent time — the index does not carry that.
- **Routines** — Routines that ran (of N in the catalogue) / Runs / Success / Failing, one line per routine with a success-rate bar, plus a **Firing next** card listing the schedules due next with their cron and a countdown.

## A run page

A rail row whose chain starts at a routine run opens **that run** (`activity-run-page.tsx`), and so does every other way to a run on this page — a sub-run, a dot in Previous runs, a bar on the home, `?run=` from Inbox or the bell. It is built from the parts [Routines](/guides/routines) uses, so a run reads the same on both pages:

| Part | What it says |
|------|--------------|
| **Header** | The routine's name, the status in the rail's words (with a ping while running), what started it, when, and the run id. **Retry** / **Run again** replays the run with its original inputs (`POST …/pipelines/runs/{id}/replay`, MANAGER+); **Stop** cancels a live run (`POST …/pipelines/runs/{id}/cancel`, OWNER/ADMIN); **Open routine**. The buttons follow the API's own role gates. |
| **Banner** | The approval it waits on, decidable here, or **Why it failed** — the step it stopped at, the failure, what was kept and what never ran (`routineRunBanner`, the same sentence as on Routines). |
| **Facts** | Started · Duration · Cost · Steps (finished of the recipe's) · Trigger. |
| **Steps** | The routine step spine — attempts, for-each items and agent work inside a step, each with its recorded output. |
| **Caused by this run** | The work further down the chain, nested: the runs of the routines it called, agent assignments, inbox asks. Each opens. |
| **Result** | The run's output, once it has finished. |
| **Linked to** | Its routine (to the routine's history), the issues in its chain, and the agents. |
| **What it changed** | The issues its chain created or touched — only when the chain starts at this run. |
| **Previous runs** | The routine's newest runs as a strip, oldest left, this one ringed; each opens. |
| **Raw events** | `N raw events · Journal` (`GET /api/v1/journal/count?run_id=`), for OWNER and ADMIN only. |

A run id that is not a routine run — agent work — falls back to the typed run detail.

## A workflow page

A chain rooted in agent work has no run to open, so its row opens the chain as a page, answering five questions in order:

1. **What was this?** — the sentence as the heading, who started it, the raw `triggered_via`, when (absolute and relative), and the chain origin. Then a strip: Duration, Runs, Failed, Depth, Issues, Agents.
2. **Which runs?** — the **Runs** card, derived from the chain walk and filtered to *this* chain's origin. Each row opens that run.
3. **How did it happen?** — the **topology** card: the causal graph from `GET /api/v1/chains/{anchor}`, drawn left to right. Nodes are clickable and walk one level down.
4. **What happened, then?** — **What happened, in sequence**, beside the graph: the same nodes as dated rows, indented by cause, time in a fixed left gutter and duration in a fixed right one.
5. **What did it touch?** — the issues and agents, clickable.

<Warning>
Both halves of the picture declare what they cannot show. The topology card lists the links the schema cannot carry (`inbox_items` has no issue pointer; `escalations` has neither a run nor a mission column) and says when the walk was truncated. The sequence says when rows are undated: the server dates events — runs, agent work, inbox items — and not the routines, rules and agents behind them, so an undated level keeps the walk's order rather than being placed by a time nobody recorded.
</Warning>

## Where a row leads

Each kind gets the surface that kind already has elsewhere, not a fifth rendering of the feed.

| Row | Opens |
|-----|-------|
| **Run** | [The run page](#a-run-page). A run that is not a routine run (agent work) gets the typed detail from the run API (`GET /api/v1/runs/{id}`): status, result, the run-activity rail, and a **Run evidence** card. A run with no execution record says so — and says that a missing record does not prove the agent never started. |
| **Issue** | What Activity knows that `/issues` does not: which workflows reached this issue, whether it was **created here** or merely changed, which agents did the reaching. An **Open issue ↗** link appears only when the workspace uses issue identifiers — `/issues/[identifier]` resolves nothing else, and a button that 404s is worse than an absent one. |
| **Agent** | Workflows, assignments, issues reached, and the wall clock of the chains it worked in, with a link to the agent's own page. Its sessions and messages stay there. |
| **Routine** | That routine's runs, grouped by the reader's local hour. |

### A routine's runs

Thirty runs of a one-minute routine are thirty rows that read the same, so this page makes three deliberate choices (all pure functions in `lib/run-digest.ts`):

- **Absolute time, to the second** — the reader already knows it was recent and is asking *which one*.
- **The run's own result instead of its id** — the first line of its output ("3 tickets classified"), or the error for a failure, or a `slow — 4.2s` note when the run is past 1.4× its peers' median. An empty output renders as a dash rather than a stock phrase repeated on every row.
- **An hour header that summarises** — "12 runs · all ok" is skippable; "3 runs · 1 failed" is where you stop. The header carries its date only when the page holds more than one day.

The strip reports Runs, Pass rate (over runs that reached a verdict), Typical duration (median, not mean), Slowest, Newest and Failed.

<Note>
This page's "failed" folds in `cancelled` and `interrupted`, while a chain row's `failed_runs` does not. That is not a bug to align: a chain row answers *did this workflow fail*, where a process killed by a deploy is the operator's problem; this page answers *which of these thirty runs did not produce the thing I came for*, and a run killed mid-flight produced it exactly as little as one that threw.
</Note>

## Opening one event

A row in the feed opens as a full-width page, not a side panel — an activity has a shape, and a 340px column is where that shape goes to die. It carries: four KPIs (this event, chain duration, chain cost, errors in chain), an **Execution graph** for the run behind the event, a **topology** card, the **Chain** (every journal entry under the same trace, oldest first), and the raw **Record**.

<Note>
The execution graph here is the same `TraceCanvas` component the old trace page drew — but inline waitpoint decisions and heatmap shading are **not** wired to it. Decide waitpoints in [Inbox](/guides/inbox).
</Note>

## Where the run trace went

This is the question every reader of the old page arrives with. The trace canvas as a *page* — pick a run from a rail, read its steps in a side panel — no longer exists. What it showed is in three places:

| You want | Go to |
|----------|-------|
| A run's steps, duration, cost and journal | The **run drill-down** — open a run from a workflow's Runs card, from a routine's runs, or with `/activity?run=<id>` |
| The causal graph — what called what | The **topology** card on the workflow page (and on an opened event) |
| One run's execution graph as a picture | Open any event of that run from the feed |
| Approving a paused waitpoint | [Inbox](/guides/inbox), or the **Waiting on you** card on the [Routines](/guides/routines) overview |

There is no step object on this page: a run's steps **are** its drill-down. Saved views, the heatmap toolbar, group-by axes and keyboard step selection went with the canvas and have no replacement.

## The URL is the state

Whatever you are looking at on `/activity` is in the address bar, and a change of position is a history entry: **Back** closes the drill-down you just opened, a reload resumes the walk, and the page can be sent to someone.

| Parameter | Carries |
|-----------|---------|
| `?run=`, `?pipeline=`, `?mission=` | A single run, routine or issue — and the routine→run pair — in the same spelling the inbound links below use |
| `?walk=kind:id/kind:id` | Any deeper walk (a workflow, an agent, a crew, two runs) |
| `?lens=issues\|agents\|routines` | The rail's grouping; absent for Time |
| `?status=` | The status row |
| `?entry=` | The opened journal record, once the window holding it has loaded |

Position (the walk, the opened record) is pushed; grouping and status are replaced, so Back does not step through every choice you tried. Ids read from a URL show as ids until the entities they name load, then the trail re-labels them.

A bare `?run=` with no routine used to render "This run's record is not loaded", because the record lives in the routine's run list and the link carried no routine. The run page now asks the run API for the record and resolves the routine (or agent) behind it from there. Under the run's heading a **Related** row links its routine, its issue, its agent, its crew and its own journal trace — the second leg of the one timeline (issue → run → journal → issue).

## Deep links

Fourteen places across the product link into `/activity` with a query string the trace canvas defined. Those links still work — the parameters are translated rather than dropped (`lib/activity-deeplink.ts`) and written back in the same spelling.

| Parameter | Lands on | Emitted by |
|-----------|----------|------------|
| `?run=<id>` | That run's drill-down | The Activity Bar, an inbox waitpoint, a routine's run rows |
| `?pipeline=<slug>` | The overview narrowed to that routine, over the loaded window | A routine's "view runs" |
| `?mission=<id>` | That issue's drill-down | An issue card's "activity" |
| `?status=active\|waiting\|failed\|done` | Selects that status row — a narrowing, not a destination | The Activity Bar's "view all" |
| `?step=<id>` | **Ignored** | The old canvas's own URL bar |

Two rules are worth knowing:

- **Order is by specificity, not by the URL.** `?mission=` then `?pipeline=` then `?run=` are pushed as stops in that order, so `?pipeline=<slug>&run=<id>` — the link routine cards build — lands on the run with the routine *behind* it, and **Back** returns to the routine rather than to the overview.
- **A status this page has no row for is ignored rather than obeyed.** A link written against some other vocabulary lands on everything, because a page that renders empty because it did not recognise a word is indistinguishable from a page with no data.

<Warning>
`?step=` is accepted and does nothing. The canvas focused one step in a side panel; the stream has no step object. Pasting an old `/activity?run=<id>&step=<id>` URL lands you on the run — the half of it that still means something — and silently drops the rest.
</Warning>

## What the numbers can and cannot say

Every count on this page is a claim about a window, and the page says so where the numbers are. Repeated here so nothing is implied by omission:

- **One page of the index.** The Group by totals, the status rows and every KPI on every grouping's dashboard are derived from the loaded chain index page — the newest 25 rows in the dashboard. When the workspace holds more, the rail prints *"Newest N workflows. Every count on this page describes these, not the whole workspace."* (`has_more` from the API; the client treats a missing field as "there are more"). The API itself defaults to 50 rows and caps at 200.
- **Group by → Agent sees only routine-dispatched work.** The index groups `pipeline_runs`, so an agent whose work no routine dispatched has no chain to belong to and is not indexed. That is a hole in the index, not in the grouping — and the empty state says it rather than reading as "nobody worked".
- **Group by → Issue is issues touched in the window**, not the backlog. An issue with no activity has no row here at all.
- **Issue writes an agent makes from inside its own assignment do not attach to the chain.** Those journal entries carry the assignment's own journal run id as their trace, and that id is not recorded on the assignments row, so nothing joins them back. The issues a chain's **routine runs** touched are complete; the ones its **agents** touched are not reachable. Stated as a KNOWN GAP on `chainIssuesQuery` in `internal/api/chains_list.go`.
- **Chains whose runs predate `chain_origin` are not in the index at all.** The link was never written and cannot be reconstructed, so listing them would mean claiming each run was its own chain root. Their existence is reported instead — the rail prints *"Older runs are not indexed here — the link that would group them was never written."*
- **A row's issue and agent lists are capped at 5 each**, with the exact totals alongside, so a cut list reads as cut ("+N more, not carried on this row").
- **A routine, run or step crumb narrows the loaded window only** — those ids live inside the journal payload, which the API cannot filter on. The chip says `(loaded window)` rather than implying a full-table match.
- **A workflow chip narrows nothing.** The journal has no `chain_origin` column, so a chain is not expressible as a filter over journal rows; picking one re-points the column. It is therefore not counted by the "none satisfies all N filters" banner.
- **The index is fetched, not streamed.** A row can be picked and then swept from the list — the page says "This workflow is no longer in the index" rather than drawing a graph-shaped hole.

### Every run is listed

The Time grouping used to list only chains that **composed** something and sent a plain run of a known routine to the Routines lens, with a sentence in its place. On a quiet workspace that left the rail empty while a run had happened. The rail is where a run is *found*, so every chain of the window is a row now; whether it composed anything is what its sentence and its page show.

## Keyboard

- `j` / `k` — step to the next or previous event in the feed, opening it. From nothing open, `j` opens the newest.
- `Esc` — close an opened event; with nothing open it steps one stop back up the trail, rather than doing nothing once you are already at the top.

Both are ignored while the focus is in a text field.

## Realtime

The journal feed subscribes to the workspace stream and prepends live entries; the badge next to the event count reads **live** (SSE), **polling** (the stream is unavailable, falling back to a 5s poll) or **connecting**. There is no Pause and no Refresh: the surface is always live, so a Refresh button would only advertise a staleness that is not there and a Pause is a way to be shown old numbers by accident.

The chain index is **not** streamed. The rail is a place you return to between actions, not a tape you watch — one query per look, rather than one per event, and no re-sorting under the cursor.

## API and CLI

Activity is a shell over existing endpoints; each has a CLI command with the same shape.

|----------|-----|------------|

The legacy `/orchestration` route still redirects to `/activity` so old bookmarks keep working — and so does the retired Work page: `/work` (with its `?section=work|deliveries` view) opens the corresponding ledger.

## Ledgers

Two lists sit under **Ledger** at the bottom of the rail:

- **Work queue** (`?section=work`) — the durable work ledger: every piece of accepted work (a webhook, a chat turn, a schedule, an assignment), its attempts and its result, filterable by state.
- **Webhook deliveries** (`?section=deliveries`) — every received webhook, including the ones the filter ignored; an accepted delivery opens its work.

They used to be tabs above the page header. Each now opens the way an issue does: the **Activity** header first, then a back-bar — **‹ Back to activity › Work queue · Webhook deliveries** — with the two ledgers side by side, because a delivery opens its work and the reader needs the way back. Only the open ledger is mounted, so opening one does not start the journal stream.

## Activity Bar (toolbar)

The `/activity` page answers "what happened" in depth; the **Activity Bar** answers "what is running right now" at a glance, from anywhere in the app. It is the Activity icon in the top toolbar next to the Inbox bell, with a badge counting live runs — amber the moment anything waits on a human approval, blue while routines run.

The dropdown holds **LIVE** (up to six active routine runs with their current step, elapsed time and cost, each with Review / Trace / Cancel, plus any in-flight agent runs) and **RECENT** (the last few terminal routine runs, so "did my run just finish?" costs no page hop). The footer opens `/activity?status=active` while anything is live, and `/activity` otherwise.

The server is the source of truth: `GET /api/v1/runs?status=RUNNING` for agent runs and `GET /api/v1/workspaces/{ws}/pipelines/runs/active` for routine runs, re-fetched on a short poll and immediately on `assignment.updated`, `run.*`, `mission.updated`, `pipeline.run.*` and `pipeline.step.started` — so a dropped frame cannot leave the badge stale. Nothing in flight, and the badge disappears.

## Run activity rail

Individual issue and routine pages carry an inline **Run activity** rail — the readable, human-first timeline of what an agent actually *did* during a run, built from the journal. Each step is one line: a toned icon, the time, a plain-language title ("Ran command", "Wrote file"), an optional detail line (the path, command or url) and right-aligned metadata (`exit 0 · 1.2s`, `412 B`, `$0.0021`). Machine noise — output chunks, container metrics — is dropped so the rail stays the highlights reel.

- **On an issue** (`/issues/<id>`): once the issue is started, a "Run activity" section appears below the description, scoped to that issue's runs via the journal's `mission_id` filter and narrowed to work entry types (`run.*`, `assignment.*`, `exec.command`, `file.written`, `network.egress`, `llm.call`, `keeper.*`, `summary.generated`). It is distinct from the issue's lifecycle Activity feed below it, and hidden while the issue is still in Backlog or Todo.
- **On a routine** (`/routines`): right after you click **Run** or **Test run**, the rail shows the just-started run inline so status is visible immediately.
- **On a run drill-down here**: the same component renders the **Steps** card, so a run reads the same wherever it is opened.

## Common pitfalls

- **"Agents 4" is a fact about the window, not the workspace.** Read the line at the bottom of the rail before quoting a number from this page.
- **An empty Agent grouping does not mean nobody worked.** Work no routine dispatched is not in the chain index at all.
- **A short "what it touched" list is a cut list.** The row carries at most five issues and five agents; the exact totals are on the workflow page's strip.
- **`?pipeline=<slug>` narrows, it does not open the routine.** To get a routine's runs, set **Group by → Routine** and pick it there.
- **Two crumbs can intersect to the empty set.** A run pinned from an event's spine plus an issue focused in the rail is one click away; the page says the question is empty rather than reporting a quiet system.
- **The workflow you picked can vanish.** The index is fetched once per look, so a row can be swept between the click and the render. The runs it held are still in the feed.
- **A server that records runs in the journal only has no per-run list.** The routine runs page says so instead of rendering an empty table.
