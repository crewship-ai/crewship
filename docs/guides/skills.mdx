# Skills

Skills are **system prompt extensions** that get injected into an agent's prompt during task execution. They teach agents specialized behaviors, guardrails, and output formats.

## How Skills Work

When an agent has skills assigned, their content is injected as `<skill>` blocks in the system prompt. The agent's LLM reads these instructions and follows them during execution.

```
[SKILLS AVAILABLE]
You have access to the following skill playbooks. Activate them when the user's
request matches each skill's "When to Activate" criteria.

<skill name="Network Probe" category="DEVOPS">
  # Network Probe
  ## When to use this skill
  - Task involves ping, HTTP checks, DNS resolution...
  ## Instructions
  1. Always use -c flag with ping...
  ## Guardrails
  - Never ping more than 10 times per host...
</skill>
[END SKILLS AVAILABLE]
```

## Skill Structure

Every skill has three key sections:

### When to use this skill
Describes the conditions under which the agent should apply this skill. Uses keyword matching against the task description.

### Instructions
Step-by-step guidance for how to perform the skill. These are concrete, actionable instructions the LLM follows.

### Guardrails
Safety constraints and limits. For example:
- "Never ping more than 10 times per host"
- "Only fetch from public, well-known URLs"
- "Write only to /tmp/"

## SKILL.md Format

Skills use a YAML frontmatter + markdown content format:

```markdown
---
name: "my-skill"
display_name: "My Custom Skill"
version: "1.0.0"
description: "What this skill does"
category: "CODING"
icon: "terminal"
---

# My Custom Skill

## When to use this skill
- Task involves...

## Instructions
1. First step...
2. Second step...

## Output Format
- Save results to...

## Guardrails
- Never do...
```

<Note>
Import via the API endpoint `POST /api/v1/workspaces/{id}/skills/import` with the SKILL.md content as the body.

Import requires the workspace creation role or an explicit `skill.create` capability, matching skill generation. A trusted MEMBER or VIEWER can import when granted that capability; revoking it removes that authority on the next request. Guest restrictions and scoped CLI `skills:write` requirements still apply. URL validation, content scanning and license checks remain required.
</Note>

## Skill Assignment

Skills are assigned to specific agents. The seed data maps agents to skills based on their role.

### On the Skills page

The left panel of **Skills** works like the one on Routines and Issues:

- **Views** (keys 1–6) — **Library**, **On agents**, **Not on any agent**, **Needs attention** (flagged by the scan, never scanned while an agent has it, or an agent missing a credential it needs — each with one action), **Proposed by agents** (owners and admins, who can approve) and **Archived** (unused for 90 days; agents that still have one keep it).
- **Filter** — **Source** (the repository a skill was imported from, Crewship built-in, or Made in this workspace; the five largest, then *All sources…*), **Domain**, **Trust** (Verified, Not reviewed, Flagged), **Status** (Unused 30 days, Made here) and **Used by crew**. Each picks one value. A link from an agent (`/skills?agent=<id>`) shows as a removable *Agent* chip above the views.

The library is one table: source, name and description, domain, trust, who has it and uses in the last 7 days. Sort by **Most used**, **Recently updated** or **Name**, group by **Source** or **Domain**; 50 rows show and the next 50 load as you scroll. Managers and above can tick several skills and **Give to crew**. On a phone the library is a list of rows. View, filters, sort, group, the open skill and its tab are in the URL, so a reload or a shared link keeps them.

A skill's page shows where it comes from, its trust, domain, licence and whether it runs scripts, then:

- **Overview** — when an agent uses it (the `description`, which should read "Use when…"), the last 7 days, where each runner finds it (`.claude/skills/<slug>/SKILL.md`, `.agents/skills/…`, `.opencode/skills/…`, `.factory/skills/…`, `.cursor/rules/<slug>.mdc`; Gemini CLI only through the prompt) and the credentials it needs.
- **SKILL.md** — Preview or Source, Copy, Download and, for skills not built in, Edit.
- **Used by N** — one card per crew with a switch per agent (it applies at once, from the agent's next run), **Give to the whole crew**, a warning where an agent lacks a credential, and **Recent uses** from the journal. The **Activity** button in the top bar jumps here.
- **Security** — the licence, the import scan, the curator's review and whether it runs code. A flagged skill offers **Take it from all agents**.
- **Version** — the source, the version and when it was last updated.

**Give to agents** opens one picker for crews and agents; it applies only what you changed and keeps the failed agents in view with **Retry** if a part fails. The ⋯ menu has **Edit**, **Copy into this workspace**, **Download SKILL.md**, **Open source** and, for owners and admins, **Remove from library…**.

**Add skill** has three steps: **Source** — `owner/repo`, a GitHub or GitLab URL or another https repository URL, with an optional ref; **Skills** — what the repository holds, with skills whose licence is not on the allow list shown but not selectable (you can allow them, which is recorded in the journal) and a note where a skill with the same slug would be replaced; **Who gets it** — crews whose agents all get the new skills, or none, with the matching `crewship skill import` command. Instead of a repository you can **Paste SKILL.md**, **Describe it** (Claude writes the SKILL.md from your description with the workspace's Anthropic key) or **Write it** (fill in when agents should use it, the instructions and the credentials it needs, and see the SKILL.md it becomes). The terminal button lists the same actions as `crewship skill` commands.

Edit changes an imported or generated skill: its name, icon, domain, description, instructions and credentials. Every save runs the import scan again. **Copy into this workspace** copies any skill, built-ins included, under a new name; built-in skills themselves cannot be edited or removed.

<Note>
The icon and domain are the `icon` and `category` keys of the SKILL.md frontmatter. The Skills page saves them through the import endpoint, which upserts by slug — so `crewship skill import` with the same `name` updates a skill the same way.
</Note>

## Creating Custom Skills

<Steps>
  <Step title="Write the SKILL.md file">
    Create a markdown file with YAML frontmatter defining the skill metadata and content body with activation conditions, instructions, and guardrails.
  </Step>

  <Step title="Import the skill">
    Use the API or UI to import the skill into your workspace.
  </Step>

  <Step title="Assign to agents">
    Assign the skill to the agents that should use it. An agent can have multiple skills assigned.
  </Step>
</Steps>

## Verification Status

Marketplace skills go through a verification pipeline:

| Status | Meaning |
|--------|---------|
| `UNVERIFIED` | Not yet reviewed |
| `PENDING_REVIEW` | Submitted for review |
| `VERIFIED` | Approved and safe to use |
| `REJECTED` | Failed review |
| `DEPRECATED` | No longer maintained |

<Tip>
  Skills are injected into the system prompt, so they consume token budget. Keep skills focused and concise -- a skill with 500 words of instructions is more effective than one with 2000 words of edge cases.
</Tip>

## Invocation telemetry

Every time an agent actually *uses* one of its assigned skills, Crewship records it. This is what lets the skill-review sweep distinguish a skill that is genuinely in use from one that is just assigned and forgotten.

The orchestrator watches the agent's tool-call stream. When a tool call maps to one of the agent's enabled skills -- either a `Skill` tool call whose input names the skill's slug, or a tool whose name *is* an assigned slug -- the platform, in a single transaction:

- inserts one row into `skill_invocations` (an append-only audit log: which skill, which agent, which workspace, when, and the exit code);
- bumps the skill's denormalised counters: `usage_count`, `last_used_at`, and -- when the call reported a non-zero exit code -- `error_count`;
- emits a `skill.invoked` entry to the Crew Journal (payload carries `skill_id`, `skill_slug`, `agent_id`, `tool_name`, `exit_code`, and the post-increment `usage_count`).

Recording is **best-effort and off the hot path** -- it runs in a bounded background worker, so a busy agent is never slowed by telemetry, and a tool call that does not correspond to an assigned skill is silently ignored. A non-skill tool (e.g. `Read`, `Bash`) never produces an invocation row.

The skill-review routine reads the `skill_invocations` aggregate (count + error count over a lookback window) to decide whether an assigned skill is still earning its place in the system prompt. Filter the journal Timeline on `skill.invoked` to see, per agent, exactly which skills are pulling their weight. The Skills page shows the same numbers for your workspace: uses in the last 7 days in the library, and a skill's history under Used by › Recent uses.
