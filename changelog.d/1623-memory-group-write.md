- **Crew memory writes no longer lock the other writer out until the next container start, and lost mission-outcome lessons are now visible.** The agent (uid 1001), the sidecar (uid 1002) and crewshipd share each crew's `.memory` tree through group 1002, but the writers created lockfiles `0600`, rewrote files `0644` and made new subdirectories `0755`; with the services' `0022` umask nothing restored group write until the container-start reconcile, so the second writer got `permission denied`. Inside a setgid memory tree, locks are now `0660`. Files that already have group read also get group write, and directories the writer creates keep setgid and get group write the same way (`2775` under the usual `0022` umask). The mode is set through the writer's own descriptor and never adds read access the umask removed (#4777). A mission-outcome lesson that crewshipd cannot write is now logged at ERROR as `mission_outcome_lesson_write_failed`, counted in `crewshipd_mission_outcome_lesson_write_failed_total`, and on a permission failure names the missing memory-group membership (#1623). Hosts whose crewshipd user lacks gid 1002 still need that supplementary group.
