- **Waitpoint callback URLs are minted once and stored only as a digest (#1910).** A waitpoint's token was both its id — shown in the inbox, the pending list, notification payloads and run results — and the credential for the unauthenticated `POST /api/v1/waitpoint-tokens/{token}` callback, stored in the clear. Any workspace member could read a working callback URL from the pending list, and anyone who could read the database could approve any pending gate. The token is now a public id (`wp_…`) that completes nothing; the callback secret is separate, minted by a MANAGER with `crewship routine waitpoints callback-url <token>` (`POST …/pipelines/waitpoints/{token}/callback-token`), shown once, audited, rotated by minting again, and stored as a SHA-256 digest. At startup, the migration updates waitpoint IDs and their Inbox, read-marker, notification and audit references. Historical ADMIN CLI request paths can retain an old, invalidated token.
- ⚠️ **Behaviour change:** `GET …/pipelines/waitpoints` no longer returns `callback_url` (it returns `callback_available`), `routine waitpoints show` no longer prints a URL, and the public callback no longer accepts the listed token. Integrations that read `callback_url` from the list must mint it instead. **Callback URLs handed out before the upgrade stop working** (any member could read them, so they are not carried forward): for each waitpoint pending at upgrade time that an external system completes, mint a new URL with `crewship routine waitpoints callback-url <token>`. Token values captured before the upgrade no longer name the waitpoint; read the new one from `routine waitpoints list`.
