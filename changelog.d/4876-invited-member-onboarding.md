- **An invited member of an existing workspace was sent into the "Set up Crewship" wizard, and the onboarding API let them set up that workspace.** Onboarding picked the caller's *oldest* workspace, whatever their role in it. An invited MEMBER or VIEWER was therefore treated as "not onboarded". The status read created the Crewship Guide in the shared workspace. `POST /api/v1/onboarding/setup` with a template or an applied proposal could rename that workspace and deploy crews wired to its owner's model credential, and `POST /api/v1/onboarding/setup-agent/start` created the Guide there. Every onboarding route now acts on the oldest workspace the caller **owns**. The web wizard and the `crewship pair` credential handoff pick the same workspace, so a user invited first who later created a workspace of their own is onboarded into theirs. `GET /api/v1/onboarding/status` reports `completed: true` for someone who owns no workspace and creates nothing. The dashboard no longer redirects anyone whose role in the current workspace is not `OWNER`. (#4876)
- ⚠️ **Behaviour change:** template setup, applied-proposal setup and `setup-agent/start` now answer `403` to a caller who owns no workspace (previously any member could run them). Blank setup (`crewship system onboarding setup --crew … --agent …`) still works for an ADMIN or MANAGER of a workspace they do not own, as before. It now leaves that workspace's name, language and telemetry settings alone. MEMBER and VIEWER still get `403`. A caller with no workspace at all still gets `400`. (#4876)
